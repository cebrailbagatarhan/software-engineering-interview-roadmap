## Paket 1 — Senior/Staff Backend & Concurrency: Python 3.14 Free-Threading, GIL Boundaries & Migration
**Süre:** 20–30 dk

### Konu anlatımı
Python 3.14'te free-threaded CPython artık deneysel değil, resmi olarak desteklenen fakat opsiyonel bir build modudur. Amaç GIL'i devre dışı bırakabilen CPython ile CPU-bound Python thread'lerinin gerçek paralellikten yararlanabilmesidir. Bu, `threading` kullanan her programın otomatik hızlanacağı anlamına gelmez: paylaşılan mutable state, lock contention, allocator/GC maliyeti ve C extension uyumluluğu yeni sınırlar yaratır. Bazı extension modülleri GIL'i yeniden etkinleştirebilir.

Mental model:

```text
GIL build:       T1 ----> Python bytecode
                  \       (one-at-a-time)
                   T2 --> [ GIL ]

free-threaded:   T1 ---> core 1
                 T2 ---> core 2
                    \ shared state /
                     locks + atomics
```

GIL'in kalkması thread safety'nin kalkması değil, gizli global serialization'ın kalkmasıdır. Eskiden tesadüfen güvenli görünen compound operations artık açık synchronization gerektirebilir. Migration önce workload profiling, sonra dependency/extension compatibility, sonra correctness stress tests ve ancak ardından throughput benchmark şeklinde yapılmalıdır.

### Mülakat soruları
- GIL neyi serialize eder, neyi etmez?
- Free-threaded build CPU-bound workload'u ne zaman hızlandırır?
- I/O-bound servis neden büyük fark görmeyebilir?
- C extension GIL'i yeniden açarsa ne olur?
- Race condition ile data corruption arasındaki ilişki nedir?
- Senior: lock granularity ve contention nasıl ölçülür?
- Staff: production migration için canary ve rollback planı nasıl kurulur?

### Beklenen cevap derinliği
Junior: thread/process ve race condition. Mid: GIL, CPU-vs-I/O workload. Senior: synchronization, C extensions, benchmark. Staff: compatibility matrix, observability ve rollout. Principal/CTO: compute economics, ecosystem risk ve migration ROI.

### Kısa alıştırma
CPU-bound bir worker için 1/2/4/8 thread benchmark planı yaz; throughput, CPU utilization, lock contention ve correctness invariant'larını belirt.

### Proje fikri
`free-threaded-bench`: aynı workload'u normal ve free-threaded CPython ile çalıştır; extension compatibility ve race stress testleri ekle.

### Failure modes / trade-off / production
Free-threading'i 'locks artık gereksiz' sanmak; yalnız microbenchmark kullanmak; extension'ın GIL'i yeniden etkinleştirdiğini kaçırmak; shared mutable cache'i korumasız bırakmak. Production'da throughput/core, p99, CPU, RSS, lock contention, race/error rate ve dependency compatibility izlenmeli.

## Paket 2 — Senior/Staff SRE & Observability: OpenTelemetry Profiles, Continuous Profiling & Cross-Signal Correlation
**Süre:** 20–30 dk

### Konu anlatımı
OpenTelemetry Profiles sinyali 26 Mart 2026'da public Alpha'ya geçti. Amaç traces, metrics ve logs yanına düşük-overhead continuous profiling ekleyerek 'hangi request yavaş?' sorusunu 'o request sırasında CPU/off-CPU zamanı hangi kodda harcandı?' sorusuyla birleştirmektir. Collector pprof receiver, Kubernetes metadata enrichment ve OTTL transform/filter desteği kazanmıştır; eBPF profiler OTLP Profiles destekleyen backend'lere veri gönderebilir.

```text
request -> trace/span ---------+
service -> metrics             |
process -> logs                +--> shared resource/context --> incident diagnosis
CPU/offCPU -> profile ---------+
```

Profile bir trace değildir: stack/sample dağılımı resource consumption'ı gösterir; trace causal request path'i gösterir. En yüksek değer korelasyondan gelir. Alpha maturity kritik production dependency için dikkat gerektirir; sampling overhead, symbolization, cardinality/storage ve privacy ayrıca tasarlanmalıdır.

### Mülakat soruları
- Continuous profiling hangi soruyu traces'tan daha iyi cevaplar?
- CPU profile ile off-CPU profile farkı nedir?
- Symbolization neden gereklidir?
- Profile ile span nasıl korele edilir?
- eBPF yaklaşımının avantaj/sınırları nelerdir?
- Senior: profiling overhead nasıl budget edilir?
- Staff: telemetry pipeline'da retention ve cost nasıl yönetilir?

### Beklenen cevap derinliği
Junior: stack/profile kavramı. Mid: CPU/off-CPU ve sampling. Senior: eBPF, symbolization, correlation. Staff: pipeline, cost, privacy, rollout. Principal/CTO: observability ROI ve vendor-neutral telemetry strategy.

### Kısa alıştırma
p99 latency incident'ında trace + CPU profile + off-CPU profile ile teşhis ağacı çiz; her sinyalin hangi hipotezi doğruladığını yaz.

### Proje fikri
`otel-profile-lab`: CPU ve lock contention üreten servis + OTel Collector + profiling backend; Kubernetes metadata ile profile enrichment yap.

### Failure modes / trade-off / production
Alpha sinyali kritik bağımlılık yapmak; profiling overhead'i ölçmemek; symbols/build IDs saklamamak; profile cardinality/storage maliyetini sınırsız bırakmak; sensitive stack metadata'yı filtrelememek. Production'da agent CPU/RSS overhead, dropped samples, symbolization success, ingest bytes, retention cost ve trace-profile correlation coverage izlenmeli.
