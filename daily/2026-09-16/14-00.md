## Paket 1 — Senior/Staff Cloud & AI Infrastructure: Kubernetes Dynamic Resource Allocation (DRA)
**Süre:** 20–30 dk

### Konu anlatımı
GPU, NIC, FPGA gibi cihazları yalnız `vendor.com/gpu: 1` şeklinde bir integer kaynak olarak görmek modern accelerator filoları için yetersiz kalır. Kubernetes Dynamic Resource Allocation (DRA), storage dünyasındaki StorageClass/PVC modeline benzeyen bir cihaz talep ve tahsis katmanı getirir: cluster yöneticisi/driver `DeviceClass` ile uygun cihaz sınıfını tanımlar, workload `ResourceClaim` üzerinden ihtiyacını ifade eder, scheduler ise claim ile eşleşen cihazı erişilebilir node üzerinde tahsis eder.

Kubernetes'in çekirdek DRA mekanizması v1.35'ten beri Stable. v1.37'de DRA Extended Resource desteği de GA oldu; böylece mevcut `example.com/gpu` biçimindeki workload'lar değişmeden kalırken backend allocation DRA driver'a taşınabilir. Device taints/tolerations da v1.37'de Stable hale geldi. Bu, brownfield GPU platformlarında migration için kritik bir köprüdür.

```text
workload
   | ResourceClaim / extended resource
   v
DeviceClass ---- CEL/selectors ----> candidate devices
   |                                  |
   +------------ scheduler -----------+
                    |
                 allocate
                    v
              node + DRA driver
                    |
                    v
          configured device -> Pod
```

### İçeride ne oluyor?
DRA scheduling-time allocation problemidir. DeviceClass policy/selection yüzeyidir; ResourceClaim allocation lifecycle'ını taşır. Scheduler yalnız CPU/memory değil cihaz uygunluğu ve claim durumunu da hesaba katar. Driver cihazı node üzerinde hazırlar. DRA'nın değeri yalnız GPU saymak değil; cihaz attribute'ları, paylaşım/partitioning, admin access, prioritized alternatives ve device health/taint gibi daha zengin semantics sağlamaktır.

v1.37 Extended Resource GA özellikle migration stratejisini değiştirir: application manifest'lerini bir anda ResourceClaim modeline çevirmeden, eski extended-resource API ile DRA-backed allocation kullanılabilir. Ancak bu compatibility yüzeyi DRA'nın tüm gelişmiş claim semantics'ini otomatik olarak workload'a kazandırmaz.

### Yüksek getirili mülakat soruları
- DRA hangi problemi klasik extended resources/device plugin modelinden daha iyi çözer?
- `DeviceClass` ile `ResourceClaim` sorumlulukları nasıl ayrılır?
- Scheduler neden cihaz allocation lifecycle'ına dahil olmak zorundadır?
- DRA ile PVC/StorageClass mental modeli nerede benzer, nerede ayrılır?
- Extended Resource GA brownfield migration'ı nasıl kolaylaştırır?
- Device taints hangi production failure mode'unu azaltır?
- Senior: scarce GPU için queueing, quota ve DRA'yı nasıl birlikte tasarlarsın?
- Staff: multi-tenant heterogeneous accelerator fleet'te class, policy ve observability standardını nasıl kurarsın?

### Seviyeye göre cevap derinliği
Junior: request, scheduling ve device kavramı. Mid: DeviceClass/ResourceClaim lifecycle. Senior: fragmentation, health, quota ve scheduler failure modes. Staff: heterogeneous fleet, migration, tenancy ve driver governance. Principal/CTO: accelerator utilization, vendor portability, capacity economics ve platform standardizasyonu.

### Kısa alıştırma
A100, H100 ve iki farklı NIC sınıfı bulunan cluster için üç workload tanımla: training, latency-sensitive inference ve batch embedding. Hangi ihtiyaçları DeviceClass selector/policy'ye, hangilerini workload claim'ine koyacağını yaz.

### Proje fikri
`dra-gpu-scheduler-lab`: kind/test cluster + örnek DRA driver ile iki fake device class oluştur. Claim allocation, unavailable device, taint ve extended-resource compatibility senaryolarını test edip allocation latency ve pending-reason dashboard'u üret.

### Failure modes / trade-off / production
DeviceClass'ı uygulama-specific policy çöplüğüne çevirmek; scarce device için quota/admission katmanını unutmamak; driver failure'ını scheduler failure'ı sanmak; tainted/unhealthy cihazı yeni workload'a vermek; claim lifecycle leak'i; brownfield migration'da iki allocation modelinin observability'sini ayırmamak. Production'da allocation latency, pending reason, device utilization/fragmentation, claim leak, driver error, unhealthy/tainted device ve queue wait izlenir.

## Paket 2 — Senior/Staff Backend & Concurrency: Java Scoped Values, Request Context & Structured Lifetime
**Süre:** 20–30 dk

### Konu anlatımı
Request ID, authenticated principal, tracing metadata gibi context bilgilerini call stack boyunca her metoda parametre olarak geçirmek gürültülüdür; global/static mutable state ise concurrency açısından tehlikelidir. `ThreadLocal` bu problemi uzun süre çözdü fakat thread pool ve özellikle milyonlarca virtual thread dünyasında lifetime/cleanup hataları ve unconstrained mutation maliyeti yaratabilir. Java `ScopedValue`, bir değeri sınırlı bir dynamic scope boyunca immutable binding olarak paylaşmayı hedefler.

```text
request entry
   |
ScopedValue.where(USER, alice)
   |
   +--> service()
   |      +--> repository() -> USER.get()
   |
   +--> structured subtasks
          -> inherited binding

scope exits => binding no longer visible
```

### İçeride ne oluyor?
Scoped value binding lexical değişken değildir; çağrı zincirinin dinamik kapsamı boyunca görünür. Binding'in kendisi immutable'dır: aynı scoped value alt scope'ta yeniden bind edilebilir ama mevcut binding mutate edilmez. Structured concurrency ile birlikte kullanıldığında scope açılırken mevcut scoped-value bindings yakalanabilir ve child tasks bunları inherit eder. Böylece context lifetime task tree ile hizalanır.

Bu mekanizma shared mutable state'i güvenli yapmaz. Scoped value içine mutable object koyup child task'larda eşzamanlı mutate etmek yine synchronization gerektirir. Ayrıca API/version durumunu kontrol etmek önemlidir: platform özelliklerinin preview/stable statüsü JDK sürümüne göre değişebilir; production adoption'da hedef JDK dokümantasyonu esas alınmalıdır.

### Yüksek getirili mülakat soruları
- ScopedValue hangi ThreadLocal problemlerini hedefler?
- Dynamic scope ile lexical scope farkı nedir?
- Binding immutable olması ne kazandırır?
- Child task context inheritance neden structured lifetime ile daha güvenlidir?
- ScopedValue içine mutable map koyarsan thread safety kazanır mısın?
- Senior: tracing/request context için explicit parameter mı ScopedValue mı seçersin?
- Staff: framework API'sinde ambient context kullanımını hangi sınırlarla standardize edersin?

### Seviyeye göre cevap derinliği
Junior: thread-local context ve scope. Mid: binding/lifetime/inheritance. Senior: virtual threads, cleanup, observability context ve mutable-value riski. Staff: framework boundary, compatibility ve API governance. Principal/CTO: concurrency model standardı, migration maliyeti ve ecosystem readiness.

### Kısa alıştırma
`requestId`, `principal` ve `deadline` taşıyan bir HTTP request düşün. Hangisini explicit parametre, hangisini scoped context yapacağını gerekçelendir; iki paralel subtask'ın hangi değerleri inherit edeceğini çiz.

### Proje fikri
`scoped-context-lab`: aynı HTTP fan-out servisini ThreadLocal ve ScopedValue varyantlarıyla kur. Virtual threads altında context propagation, exception, cancellation ve nested rebind testleri yaz; stale-context invariant testi ekle.

### Failure modes / trade-off / production
Ambient context'i business dependency gizlemek için kullanmak; mutable payload'ı thread-safe sanmak; scope dışına referans/lifetime beklentisi taşımak; library'nin desteklemediği JDK/preview seviyesine bağlanmak; tracing framework propagation modelini doğrulamamak. Production'da context-missing errors, trace continuity, cancellation latency, virtual-thread count ve migration regressions izlenir.
