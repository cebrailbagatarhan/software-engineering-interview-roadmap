## Paket 1 — Senior/Staff Networking & Distributed Systems: QUIC Connection Migration, Connection IDs & Path Validation
**Süre:** 20–30 dk

### Konu anlatımı
TCP bağlantısı pratikte source/destination IP ve port tuple'ına sıkı bağlıdır; mobil cihaz Wi-Fi'dan LTE'ye geçtiğinde path değişimi bağlantıyı bozabilir. QUIC, connection identity'yi yalnız IP/port tuple'ına bağlamak yerine Connection ID (CID) kullanır. Böylece handshake tamamlandıktan sonra endpoint adresi değişse bile aynı logical connection yeni network path üzerinde devam edebilir.

```text
Wi-Fi path: client:50000 ----> server
              CID = A
                    |
              network changes
                    v
LTE path:   client:62000 ----> server
              CID = B
                    |
             PATH_CHALLENGE
             PATH_RESPONSE
                    v
             validated path
```

### İçeride ne oluyor?
Endpoint peer'e birden fazla CID sağlayabilir. Migration sırasında yeni path yeni/uygun CID ile kullanılır; eski CID'ler retire edilebilir. Yeni source address'e trafik göndermeden önce path validation, PATH_CHALLENGE/PATH_RESPONSE ile return-routability kontrolü yapar ve amplification riskini sınırlar. Migration congestion-control state'ini de etkileyebilir; RFC 9000 adres değişiminin congestion state reset'ine yol açabileceğini belirtir. RFC 9002'de congestion control path özelliğidir; loss detection ise packet-number space'lere göre ayrılır. CID havuzu tükenirse migration/probing aksayabilir.

### Yüksek getirili mülakat soruları
- QUIC Connection ID neden IP/port tuple'ından ayrıdır?
- Path validation hangi saldırı/failure class'ını azaltır?
- `NEW_CONNECTION_ID` ve `RETIRE_CONNECTION_ID` ne işe yarar?
- CID privacy açısından neden rotate edilebilir?
- Migration sırasında congestion state neden dikkat ister?
- Senior: Wi-Fi → LTE geçişini packet-level anlat.
- Staff: load balancer CID routing ve backend affinity'yi nasıl tasarlarsın?
- Principal/CTO: mobil reliability kazancı ile protocol/observability complexity'sini nasıl değerlendirirsin?

### Seviyeye göre cevap derinliği
Junior: connection identity ve network path. Mid: CID ve path validation. Senior: migration, loss/congestion state, NAT. Staff: LB routing, CID lifecycle, privacy. Principal/CTO: fleet compatibility, mobile UX ve operational complexity.

### Kısa alıştırma
Bir mobil video-call client'ının Wi-Fi'dan LTE'ye geçtiğini varsay. Eski path, yeni CID, PATH_CHALLENGE/PATH_RESPONSE ve congestion state adımlarını sırala.

### Proje fikri
`quic-migration-lab`: QUIC client/server kur; network namespace veya interface değişimiyle path migration üret. RTT, loss, PTO ve connection survival ölç.

### Failure modes / trade-off / production
CID'yi user/session ID gibi tasarlayıp privacy leak üretmek; yeni path'i doğrulamadan yüksek hacimli trafik göndermek; CID pool'u tüketmek; migration'ı reconnect sanmak; per-path congestion telemetry tutmamak. Production'da migration success rate, path-validation latency/failure, RTT delta, PTO/loss, CID exhaustion ve reconnect fallback izlenir.

### Kaynaklar
- RFC 9000 — QUIC Transport: https://www.rfc-editor.org/rfc/rfc9000.html
- RFC 9002 — QUIC Loss Detection and Congestion Control: https://www.rfc-editor.org/rfc/rfc9002.html

## Paket 2 — Staff/Principal/CTO Leadership & SRE: Error Budgets as a Product-Control Loop
**Süre:** 20–30 dk

### Konu anlatımı
SLO yalnız dashboard hedefi değildir. Error budget, product velocity ile reliability arasındaki çatışmayı ölçülebilir bir kontrol döngüsüne dönüştürür. Bir SLO %99.9 ise izin verilen failure budget %0.1'dir. Esas değer matematikten çok policy'dedir: bütçe sağlıklıysa kontrollü risk ve release devam eder; bütçe hızla yanıyorsa rollout yavaşlatılır, reliability işi öne alınır; bütçe tükenmişse policy önceden tanımlanmış aksiyonları tetikler.

```text
user expectations -> SLI -> SLO
                         |
                         v
                  error budget
                    /        \
               healthy      burning
                 |             |
          feature velocity   guardrails
                               |
                         reliability work
                               |
                         budget recovers
```

### İçeride ne oluyor?
İyi SLI user-visible outcome'u ölçer; CPU utilization gibi internal metric doğrudan SLI olmak zorunda değildir. Budget window ve burn rate farklı soruları cevaplar: kalan toplam risk ile bu riskin ne hızla tüketildiğini ayır. Policy punishment değil decision mechanism olmalıdır. Google'ın örnek policy'si dört haftalık budget aşıldığında P0/security dışı değişiklikleri durdurmayı ve tek incident budget'ın %20'sinden fazlasını tüketirse postmortem istemeyi örnekler. Her şirket aynı threshold'u kopyalamamalı; kullanıcı etkisi, traffic ve business riskine göre kalibre etmelidir.

### Yüksek getirili mülakat soruları
- SLI, SLO, SLA ve error budget farkı nedir?
- Neden %100 reliability genellikle yanlış hedeftir?
- Burn rate neden yalnız kalan budget'tan daha actionable olabilir?
- Hangi değişiklikler freeze sırasında yine yapılabilmelidir?
- Low-traffic serviste SLO alerting neden zorlaşır?
- Staff: dependency-caused outage budget'a nasıl yansıtılır?
- Principal: reliability investment'larını budget impact ile nasıl sıralarsın?
- CTO: product ve SRE hedeflerini aynı incentive'a nasıl bağlarsın?

### Seviyeye göre cevap derinliği
Junior: SLI/SLO ve availability. Mid: budget hesabı ve alert. Senior: burn-rate, incident attribution, rollout. Staff: policy ve cross-team dependency. Principal/CTO: product economics, risk appetite, governance ve incentive design.

### Kısa alıştırma
Ayda 10 milyon eligible request alan %99.95 success SLO'lu servis için error budget'ı hesapla. Bir incident 1,500 failed request üretirse budget'ın yüzde kaçını tükettiğini ve hangi policy aksiyonunu tetikleyeceğini öner.

### Proje fikri
`slo-policy-simulator`: traffic, SLO, incidents ve rollout rate girdilerinden budget/burn-rate hesaplayan; canary/freeze/reliability-work kararlarını simüle eden küçük dashboard.

### Failure modes / trade-off / production
SLO'yu user expectation yerine kolay ölçülen metric'ten seçmek; %100 hedef; budget'ı ceza mekanizması yapmak; ownership tanımlamamak; dependency failures'ı keyfi saymak/saymamak; low-traffic noise; release freeze'in reliability fix'lerini de engellemesi. Production'da SLI compliance, remaining budget, multi-window burn rate, change failure, incident budget share ve reliability-work allocation izlenir.
