## Paket 1 — Mid/Senior Mobile: Android Adaptive Layouts, Window Size Classes & State Preservation
**Süre:** 20–30 dk

### Konu anlatımı
Modern Android uygulaması artık yalnız portrait telefon ekranına göre tasarlanamaz. Aynı process; telefon, tablet, foldable, desktop windowing ve multi-window içinde çok farklı kullanılabilir pencere boyutları görebilir. Bu nedenle layout kararı fiziksel cihaz modelinden değil uygulamaya ayrılan gerçek window alanından türetilmelidir. Window size classes, ham ölçüleri az sayıda anlamlı breakpoint'e dönüştürerek UI kararlarını sadeleştirir.

Android 16/API 36 ile büyük ekranlarda orientation/aspect-ratio/resizability kısıtlarının sistem tarafından daha fazla override edilmesi adaptive tasarımı production zorunluluğuna yaklaştırdı; Android 17/API 37'de >600dp display'lerde bu kısıtlamalar artık uygulanmıyor. Sonuç: configuration/window değişimi istisna değil normal lifecycle olayıdır.

### Mental model
```text
physical device != layout decision

available app window
        |
        v
 window metrics
        |
        v
 window size class + posture
        |
        +--> compact: single pane
        +--> medium: reflow / rail
        +--> expanded: list + detail
        |
        v
 state survives resize/recreation
```

### İçeride ne oluyor?
Responsive layout aynı yapıyı mevcut alana göre esnetir; adaptive layout ise breakpoint'te yapıyı değiştirebilir. Örneğin compact window'da listeden detail route'una navigation yapılırken expanded window'da iki pane aynı anda gösterilebilir. Material 3 Adaptive kütüphanesi `ListDetailPaneScaffold` gibi canonical layout building block'ları sağlar.

En kritik correctness konusu state'tir. Rotation, fold/unfold, split-screen veya desktop resize activity recreation ya da composition değişimi yaratabilir. UI state ile domain/data state ayrılmalı; ViewModel/saved-state mekanizmaları doğru lifetime'a bağlanmalıdır. Pane sayısı değişince selection/navigation state kaybolmamalıdır.

### Yüksek getirili mülakat soruları
- Window size class neden device type kontrolünden daha iyi abstraction'dır?
- Responsive ve adaptive layout arasındaki fark nedir?
- List-detail pattern compact ve expanded window'da nasıl davranır?
- Configuration change sırasında hangi state nerede tutulmalıdır?
- Foldable posture layout kararını nasıl etkileyebilir?
- Senior: multi-window resize sırasında expensive recomposition/work nasıl kontrol edilir?
- Staff: legacy phone-only app'i adaptive'e nasıl aşamalı migrate edersin?
- Principal/CTO: adaptive UX yatırımının product reach ve QA matrix maliyeti nasıl dengelenir?

### Seviyeye göre cevap derinliği
Junior: orientation ve responsive layout. Mid: window metrics/size classes ve state preservation. Senior: lifecycle, navigation, performance ve testing matrix. Staff: design-system/canonical-layout standardizasyonu ve migration. Principal/CTO: device reach, accessibility, engineering investment ve product economics.

### Kısa alıştırma
Bir mail uygulamasını compact/medium/expanded window için çiz. Inbox selection state'inin fold/unfold ve split-screen resize boyunca nasıl korunacağını belirt.

### Proje fikri
`adaptive-mail-lab`: Compose + Material 3 Adaptive ile list/detail app. Window resize testleri, state restoration, keyboard/mouse input ve foldable emulator senaryoları ekle.

### Failure modes / trade-off / production
Device modeline göre layout seçmek; orientation lock'a güvenmek; pane değişiminde selection state kaybetmek; tablet için yalnız UI'ı stretch etmek; her breakpoint için ayrı business logic üretmek. Production'da window-class dağılımı, resize/crash telemetry, state-restoration failures, rendering jank ve form-factor bazlı funnel ölçülür.

- Orientation/aspect ratio/resizability: https://developer.android.com/develop/adaptive-apps/guides/app-orientation-aspect-ratio-resizability

## Paket 2 — Mid/Senior Backend/System Design: HTTP Idempotency, Retry Safety & Idempotency Keys
**Süre:** 20–30 dk

### Konu anlatımı
Distributed API'de en tehlikeli belirsizliklerden biri şudur: client request'i gönderdi, server side effect'i yaptı, fakat response network'te kayboldu. Client işlemin gerçekleşip gerçekleşmediğini bilemez. Retry availability'yi artırabilir fakat operation non-idempotent ise duplicate payment/order/message yaratabilir.

HTTP semantics'e göre GET/HEAD gibi safe methods ile PUT ve DELETE idempotent kabul edilir: aynı isteğin birden çok uygulanmasının hedeflenen server etkisi tek uygulamayla aynıdır. POST ise varsayılan olarak idempotent değildir. Uygulama seviyesinde idempotency key, non-idempotent business operation'ı retry-safe yapmak için request identity yaratır.

### Mental model
```text
client -- POST(k=abc) --> service
                         | business write
                         | result store
response X network       v

client -- retry(k=abc) -> lookup key
                         |
                         +--> same request: replay result
                         +--> conflicting payload: reject

retry safety = stable operation identity + atomic outcome
```

### İçeride ne oluyor?
Idempotency key yalnız cache key değildir. Güvenli tasarımda key tenant/user scope'unda unique olmalı, request fingerprint/hash ile bağlanmalı ve business mutation ile key sonucu arasında yarış penceresi bırakılmamalıdır. İki eşzamanlı aynı-key request için unique constraint/transaction veya equivalent serialization gerekir.

Stored result'in TTL'i retry horizon'dan kısa olursa geç retry duplicate side effect yaratabilir. Aynı key farklı payload ile gelirse eski sonucu körlemesine döndürmek correctness/security bug'ıdır. Downstream side effect'ler de düşünülmelidir: DB transaction idempotent görünse bile email, payment provider veya queue publish duplicate olabilir; outbox/deduplication gibi ek pattern'ler gerekebilir.

### Yüksek getirili mülakat soruları
- HTTP idempotency ile business idempotency arasındaki fark nedir?
- POST neden varsayılan olarak retry-safe değildir?
- Idempotency key hangi scope'ta unique olmalıdır?
- Aynı key farklı payload ile gelirse ne yaparsın?
- Key/result kaydı ile business write nasıl atomik hale getirilir?
- TTL nasıl seçilir?
- Senior: DB commit oldu ama response kayboldu senaryosunu çöz.
- Staff: multi-region active-active idempotency store nasıl tasarlanır?
- Principal/CTO: stronger dedupe guarantee'in latency/cost/complexity trade-off'u nedir?

### Seviyeye göre cevap derinliği
Junior: idempotent method ve duplicate side effect. Mid: retry, key, unique constraint. Senior: atomicity, request fingerprint, TTL, downstream effects. Staff: multi-region consistency ve abuse controls. Principal/CTO: guarantee seviyesi, platform standardı ve ekonomik maliyet.

### Kısa alıştırma
`POST /orders` için tablo şeması ve transaction sırası tasarla. Aynı key ile eşzamanlı iki request ve commit-sonrası response-loss senaryolarını yürüt.

### Proje fikri
`retry-safe-api-lab`: order API + idempotency table + request hash + unique constraint. Timeout/fault injection ile 100 retry gönder ve yalnız bir order oluştuğunu invariant testiyle doğrula.

### Failure modes / trade-off / production
Key'i global scope'ta yanlış paylaşmak; payload mismatch kontrol etmemek; business write ile key insert arasında crash window bırakmak; TTL'i kısa tutmak; downstream side effect'leri dedupe etmemek; key cardinality/storage abuse. Production'da duplicate-key rate, conflict rate, replay latency, store size/TTL eviction, retry count ve duplicate-business invariant violation izlenir.

- RFC 9110 method semantics: https://www.rfc-editor.org/rfc/rfc9110.html#section-9
