## Paket 1 — Senior/Staff Distributed Systems & Cloud: Kubernetes Lease, Leader Election & Fencing
**Süre:** 20–30 dk

### Konu anlatımı
Leader election'ın amacı bütün replikaları durdurmak değil, belirli bir side-effect'i aynı anda tek aktif actor'ın yürütmesini sağlamaktır. Kubernetes bunu `coordination.k8s.io/v1` `Lease` nesneleriyle destekler. Lease; `holderIdentity`, `renewTime`, `leaseDurationSeconds` ve leadership transition bilgisi gibi alanlarla kimin lider olduğunu ve lease'in ne kadar süre geçerli sayılacağını temsil eder. Kubernetes node heartbeat ve HA control-plane component leader election için de Lease kullanır.

Temel akış acquire → renew → expire → takeover'dır. Adaylar Lease'i optimistic concurrency ile günceller; aynı `resourceVersion` üzerinden yarışan update'lerden yalnız biri başarılı olur. Fakat kritik mülakat ayrımı şudur: **leader election tek başına fencing değildir**. Eski leader network partition veya uzun GC pause sonrası kendini hâlâ leader sanıp external database/queue'a write edebiliyorsa iki actor side-effect üretebilir. External resource destekliyorsa monoton epoch/fencing token ile stale leader write'ı reddedilmelidir; desteklemiyorsa idempotency, ownership/version checks veya başka domain-specific guard gerekir.

### Mental model
```text
candidate A ---- CAS ----> Lease <---- CAS ---- candidate B
                    |
               holder=A
               renewTime=t
                    |
             renew / expire
                    v
              new holder=B

Election: "kim leader?"
Fencing:  "eski leader hâlâ write edebilir mi?"

old A -- epoch 41 --> storage: REJECT
new B -- epoch 42 --> storage: ACCEPT
```

### İçeride ne oluyor?
Lease bir lightweight coordination record'dur. Leader deadline içinde renew edemezse leadership bırakmalıdır; follower'lar lease expiration sonrası acquisition yarışına girer. Timeout seçimi availability ile false takeover riskini dengeler: çok kısa timeout pause/network jitter altında churn, çok uzun timeout failure sonrası yavaş recovery üretir. Clock assumptions, API-server availability ve external side-effect semantics threat model'in parçasıdır. Güncel Kubernetes ayrıca `LeaseCandidate` ile coordinated leader election mekanizmasını geliştiriyor; fakat uygulama tasarımındaki temel election/fencing ayrımı değişmez.

### Yüksek getirili mülakat soruları
- Lease ile mutex arasındaki temel fark nedir?
- `renewTime` ve `leaseDurationSeconds` hangi problemi çözer?
- Optimistic concurrency iki adayın acquisition yarışını nasıl çözer?
- Leader election neden exactly-once side-effect garantisi değildir?
- GC pause sonrası eski leader hangi split-brain davranışını gösterebilir?
- Senior: lease duration / renew deadline / retry period trade-off'u nasıl seçilir?
- Staff: external datastore fencing token desteklemiyorsa stale leader riskini nasıl azaltırsın?

### Seviyeye göre cevap derinliği
Junior/Mid: leader/follower, lease expiration, heartbeat. Senior: CAS/resourceVersion, renew deadline, jitter ve failover. Staff: fencing, stale leader, external side effects, control-plane outage ve blast radius. Principal: ortak leader-election library, observability standardı ve multi-cluster failure semantics.

### Kısa alıştırma
3 controller replica'nın aynı billing reconciliation job'ını çalıştırdığını düşün. Leader 8 saniye stop-the-world pause yaşarken lease expire olup başka replica leader oluyor. Eski leader geri geldiğinde duplicate charge'ı nasıl engelleyeceğini epoch/fencing veya idempotency modeliyle çiz.

### Proje fikri
`lease-fencing-lab`: Kubernetes Lease kullanan üç worker kur. Lider monoton epoch ile PostgreSQL satırına write etsin; DB tarafında stale epoch reject edilsin. Process pause, API timeout ve leader kill fault injection'larında duplicate side-effect ve failover latency ölç.

### Failure modes / trade-off / production
Election'ı distributed lock ile eşitlemek; stale leader'ı fence etmemek; timeout'u gerçek pause/jitter dağılımından bağımsız seçmek; leader-only job'ı idempotent yapmamak; API-server outage'ında davranışı tanımlamamak. Production'da leadership transitions, renew latency/failure, acquisition latency, stale-epoch rejection ve duplicate-side-effect metriği izlenmelidir.

## Paket 2 — Senior/Staff MLOps: Model Registry Aliases, Promotion & Rollback Discipline
**Süre:** 20–30 dk

### Konu anlatımı
Model registry yalnız `.pkl`/weights saklayan artifact deposu değildir; model version, lineage, metadata ve deployment referanslarını yöneten control plane'dir. MLflow Model Registry'de registered model birden fazla immutable-ish version içerir; alias ise `champion` gibi değiştirilebilir isimli referansı belirli version'a bağlar. Serving code `models:/fraud-model@champion` gibi bir URI kullanarak deployment referansını model version numarasından ayırabilir.

Bu ayrım promotion ve rollback'i basitleştirir: challenger validation'dan geçer, alias kontrollü biçimde yeni version'a taşınır; regression görülürse alias eski known-good version'a geri alınabilir. Fakat alias değiştirmek tek başına güvenli rollout değildir. Serving process model'i startup'ta cache'liyorsa alias update anında trafik davranışını değiştirmeyebilir. Schema/feature compatibility, artifact immutability, model signature, canary traffic, audit trail ve rollback verification ayrıca tasarlanmalıdır.

### Mental model
```text
training run -> model v17 -- validation --+
training run -> model v18 -- validation --+--> registry
                                             |
                         champion ----------> v17
                         challenger --------> v18
                                             |
                                      canary / compare
                                             |
                         champion ----------> v18

regression? champion -> v17

alias = mutable pointer
version = reproducible deployment identity
```

### İçeride ne oluyor?
Registry version'ı source run/model lineage ile bağlar. Tags validation status, dataset snapshot veya governance metadata taşıyabilir; aliases deployment intent'i ifade eder. MLflow güncel workflow'ları legacy stage yaklaşımı yerine aliases/tags ve ayrı environment modellerini öne çıkarır. Mature pipeline'da CI/CD yalnız alias değişikliğine bakmaz: model signature/schema checks, offline eval, integration/smoke test, canary metrics ve approval policy gate'leri promotion öncesi çalışır. Rollback için önceki artifact ve feature contract gerçekten erişilebilir olmalıdır.

### Yüksek getirili mülakat soruları
- Model registry artifact store'dan nasıl ayrılır?
- Version ile alias arasındaki fark nedir?
- `champion` alias neden deployment code'unu version'dan ayırır?
- Alias rollback hangi durumlarda yeterli değildir?
- Model signature ve feature schema neden promotion gate'idir?
- Senior: canary sırasında hangi model/system/business metriklerini izlersin?
- Staff: dev/staging/prod ayrımında registry permission ve promotion workflow'unu nasıl kurarsın?

### Seviyeye göre cevap derinliği
Mid: experiment → registered model → version → deploy. Senior: aliases, lineage, schema, canary, rollback. Staff: environment isolation, RBAC, approval gates, auditability ve reproducibility. EM/CTO: model risk tiering, release governance, rollback SLO ve compliance evidence.

### Kısa alıştırma
Fraud model v17 production'da, v18 challenger. v18 offline AUC'de daha iyi fakat p99 inference latency %35 yüksek. Promotion gate, canary yüzdesi, rollback trigger ve `champion` alias geçiş sırasını yaz.

### Proje fikri
`model-registry-release-lab`: MLflow registry'de champion/challenger aliases, version tags ve model signatures kullan. Basit serving service alias'tan model resolve etsin; CI smoke test + metric gate sonrası promotion yapsın; synthetic regression ile otomatik rollback'i doğrula.

### Failure modes / trade-off / production
`latest` version'ı körlemesine deploy etmek; alias değişimini deployment tamamlandı sanmak; feature schema drift'i atlamak; rollback artifact'ını retention ile silmek; registry write yetkisini geniş bırakmak; yalnız offline metric ile promotion yapmak. Production'da deployed version/alias, prediction quality proxy, latency/error, feature drift ve rollback time izlenmelidir.
