## Paket 1 — Senior/Staff Algorithms & Runtime: C++26 Hazard Pointers, RCU & Safe Memory Reclamation
**Süre:** 20–30 dk

### Konu anlatımı
Lock-free veri yapılarında atomik pointer güncellemek tek başına yeterli değildir: başka bir thread eski pointer'ı hâlâ okuyorken node'u `delete` etmek use-after-free üretir. Safe memory reclamation bu access-deletion race'i çözer. C++26 standard library bu alan için `<hazard_pointer>` ve `<rcu>` başlıklarını getirir.

Hazard pointer modelinde reader erişeceği objeyi bir hazard slot ile yayınlar; remover objeyi logical structure'dan çıkarır ama hemen free etmez, retire eder. Reclamation ancak hiçbir hazard pointer objeyi korumadığında yapılır. RCU'da reader ucuz bir protection/read-side region içinde çalışır; writer eski objeyi retire eder ve ilgili reader'ların grace period'u bitmeden reclaim etmez. İki teknik de lifetime safety sağlar ama cost profile farklıdır.

### Mental model
```text
Hazard Pointer
reader: load p -> publish hazard(p) -> validate -> use p -> clear
writer: unlink p -> retire p -> scan hazards -> reclaim if unprotected

RCU
reader: [ read-side critical section ---- ]
writer: replace old -> retire old -> grace period -> reclaim old

atomic visibility != safe object lifetime
```

### İçeride ne oluyor?
Lock-free stack düşün: reader `head` pointer'ını okuduktan sonra writer CAS ile head'i değiştirebilir. Reader'ın pointer'ı hâlâ dereference etmesi mümkündür. Hazard pointer protokolünde reader pointer'ı hazard slot'a koyduktan sonra source pointer'ı yeniden doğrular; arada değiştiyse tekrar dener. Retired objeler per-thread/domain listelerinde birikebilir ve scan maliyeti amortize edilir. RCU read-mostly workload'larda reader path'ini çok ucuz tutar; buna karşılık reclamation gecikebilir ve writer/memory pressure trade-off'u oluşur.

### Yüksek getirili mülakat soruları
- Atomic pointer neden use-after-free problemini tek başına çözmez?
- Hazard pointer'da publish-sonrası validate neden gerekir?
- Retire ile delete arasındaki fark nedir?
- Hazard pointer ve epoch/RCU hangi workload'larda ayrışır?
- ABA ile reclamation aynı problem midir?
- Senior: reclamation backlog büyürse hangi sinyalleri izlersin?
- Staff: lock-free complexity hangi durumda mutex'ten daha kötü engineering choice olur?

### Seviyeye göre cevap derinliği
Mid: atomics, lifetime ve use-after-free. Senior: protect/validate/retire/reclaim protokolü ve ABA ayrımı. Staff: reclamation latency, memory pressure, contention ve operational complexity. Principal: standard primitive seçimi, library boundary ve fleet/compiler compatibility.

### Kısa alıştırma
Treiber stack pop akışını çiz. `load head` ile dereference arasına writer'ın `pop + delete` yaptığı interleaving ekle; sonra hazard publish + validation ile hatayı kapat.

### Proje fikri
`safe-reclamation-lab`: mutex stack, hazard-pointer stack ve RCU/read-mostly yapı için throughput, p99 operation latency, retired-object backlog ve peak memory benchmark'ı.

### Failure modes / trade-off / production
Lock-free'ı wait-free sanmak; atomics'i lifetime guarantee sanmak; hazard publish sonrası pointer'ı validate etmemek; retired list'i sınırsız büyütmek; ABA ile reclamation'ı karıştırmak; compiler/library C++26 desteğini varsaymak. Production'da retired backlog, reclaim latency, memory high-water mark, CAS retry ve tail latency izlenir.

## Paket 2 — Senior/Staff AI/LLM: Prompt Caching, Prefix Architecture & Inference Economics
**Süre:** 20–30 dk

### Konu anlatımı
LLM serving maliyetinde tekrar tekrar aynı uzun system instructions, tool schemas ve workspace context'i prefill etmek latency ve compute tüketir. Prompt caching, daha önce hesaplanmış ortak prefix'in inference computation'ını yeniden kullanmayı hedefler. Temel design invariant'i exact/shared prefix'i prompt'un başında stabil tutmak; request'e özgü değişken içeriği sona taşımaktır.

2026 GPT-5.6 builder guidance prompt-cache TTL'nin model ailesinde en az 30 dakikaya uzatıldığını ve deterministic cache breakpoints desteğini anlatıyor. `prompt_cache_key` benzer prefix kullanan request'lerin aynı inference engine'e yönelme olasılığını artırabilir. Bu özellik correctness cache'i değildir: response sonucunu cache'lemez; prompt processing compute'unu optimize eder.

### Mental model
```text
[stable instructions][tool schemas][shared context] | [user/request delta]
<----------- cacheable prefix -------------------->   variable suffix
                         |
                    cache hit
                         |
              lower repeated prefill work
                         |
                latency + cost benefit

prompt cache != response cache
```

### İçeride ne oluyor?
Cache hit exact prefix identity'ye bağlıdır; prompt başındaki küçük ve sık değişen metadata bütün downstream prefix reuse'u bozabilir. Tool definitions ve images gibi input parçalarının da reuse için aynı kalması gerekir. Bu nedenle prompt architecture bir cost/performance concern olur: stable policy/examples/tool schemas önce, tenant/request-specific context sonra. Cache hit rate tek başına hedef değildir; cached input, uncached input, end-to-end latency, output quality ve routing/tenant isolation birlikte ölçülmelidir.

### Yüksek getirili mülakat soruları
- Prompt caching ile semantic/response caching farkı nedir?
- Exact-prefix requirement prompt tasarımını nasıl değiştirir?
- Dynamic timestamp'i prompt başına koymak neden pahalı olabilir?
- Tool schema değişikliği cache hit'i nasıl etkiler?
- Cache hit rate yükselirken latency neden yine kötüleşebilir?
- Senior: multi-tenant prompt layout'u nasıl tasarlarsın?
- Staff/CTO: cache economics'i model routing ve quality budget ile nasıl birleştirirsin?

### Seviyeye göre cevap derinliği
Mid: stable prefix ve cache hit sezgisi. Senior: prompt ordering, instrumentation, tool/context identity. Staff: tenant routing, cache-key strategy, latency/cost model. CTO: unit economics, quality guardrails ve vendor portability.

### Kısa alıştırma
29k token shared instructions/context ve 1k token request delta içeren agent için iki layout çiz: dynamic metadata başta ve sonda. Hangisinin prefix reuse'u koruduğunu ve hangi metriklerle doğrulayacağını açıkla.

### Proje fikri
`prompt-cache-profiler`: prompt bölümlerini fingerprint'leyen, cached/uncached token oranını ve p50/p95 latency/cost'u version bazında raporlayan küçük bir gateway/dashboard.

### Failure modes / trade-off / production
Cache'i correctness mekanizması sanmak; volatile field'ları prefix başına koymak; cache hit uğruna yanlış tenant context'i paylaşmak; tool schema churn'ünü ölçmemek; yalnız hit rate optimize etmek; quality/latency/cost'u birlikte izlemeden rollout yapmak. Production'da cached_tokens ratio, uncached input, TTFT/end-to-end latency, cost/request, quality eval ve cache-key cardinality izlenir.
