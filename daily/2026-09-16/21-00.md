## Paket 1 — Mid/Senior Frontend: React 19.3 View Transitions, UI State & Rendering Boundaries
**Süre:** 20–30 dk

### Konu anlatımı
React 19.3, 9 Eylül 2026'da yayımlandı ve daha önce experimental/canary olan `<ViewTransition>` API'sini stable hale getirdi. Bileşen, React Transition ile işaretlenmiş bir update child'ın mount/unmount, move veya resize davranışını değiştirdiğinde browser View Transition API ile animasyon kurar.

Buradaki önemli ayrım animasyon ile state lifecycle'dır. View transition görsel süreklilik sağlar; state'i kendi başına persist etmez, data consistency çözmez ve pahalı render'ı ortadan kaldırmaz. UI mimarisinde üç farklı concern ayrı düşünülmelidir: state'in sahibi, render scheduling ve görsel geçiş.

```text
user intent
   |
startTransition(update)
   |
React reconciliation ----> state/data semantics
   |
<ViewTransition>
   |
browser snapshot/animate -> visual continuity
```

### Mülakat soruları
- View Transition ile normal CSS transition arasındaki temel lifecycle farkı nedir?
- React Transition neden görsel transition ile aynı kavram değildir?
- Mount/unmount sırasında shared visual identity nasıl düşünülür?
- Animasyon sırasında accessibility/reduced-motion nasıl ele alınır?
- Senior: router navigation ile async data fetch nasıl koordine edilir?
- Staff: design-system seviyesinde transition policy ve performance budget nasıl kurulur?

### Beklenen cevap derinliği
Junior: render/state/CSS ayrımı. Mid: mount-unmount ve browser transition lifecycle. Senior: async navigation, interruption, accessibility ve profiling. Staff: design-system contract, rollout ve cross-team performance budget. Principal/CTO: UX kazanımı, browser compatibility, complexity ve product metrics.

### Kısa alıştırma
Liste → detay navigasyonu için shared-card geçişi tasarla. State owner, loading boundary, transition trigger ve reduced-motion fallback'ini işaretle.

### Proje fikri
`react19-view-transition-lab`: gallery/list-detail uygulaması; transition açık/kapalı senaryolarda interaction latency, dropped frames ve navigation completion ölç.

### Failure modes / trade-off / production
Animasyonu state-management sanmak; her update'i transition yapmak; layout thrash; unstable identity/key; reduced-motion'u yok saymak; browser fallback test etmemek. Production'da INP, long task, dropped-frame proxy'leri, navigation latency ve transition-abort oranı izlenebilir.

## Paket 2 — Senior/Staff Distributed Systems & Databases: Redis Atomic Slot Migration, Hot Slots & Rebalancing
**Süre:** 20–30 dk

### Konu anlatımı
Redis Cluster keyspace'i hash slot'lara böler. Rebalancing sırasında klasik slot migration yaklaşımında slot ownership ile key hareketinin ara durumları client redirect/retry davranışını karmaşıklaştırabilir. Redis 8.4'te gelen `CLUSTER MIGRATION` atomic slot migration modeli, slot içeriğini destination'a kopyalayıp canlı delta'yı takip eder; ownership handoff ancak kopyalama tamamlandığında atomik olarak yapılır. Client'lar kopyalama boyunca source ile konuşmaya devam eder.

Redis 8.2'de eklenen `CLUSTER SLOT-STATS`, slot başına key count, CPU ve network I/O gibi sinyaller sağlar. Böylece rebalancing yalnız key-count eşitleme değil, workload-aware bir control loop olarak düşünülebilir.

```text
SLOT-STATS -> detect hot slot -> choose destination
                                  |
source ===== bulk copy ======> destination
source ===== live delta ======> destination
clients -> source              destination ready
                                  |
                         ATOMIC OWNERSHIP HANDOFF
                                  |
clients ----------------------> destination
```

### Mülakat soruları
- Redis Cluster hash slot neden vardır?
- Hot key ile hot slot arasındaki fark nedir?
- Atomic migration sırasında live delta neden gerekir?
- Ownership'i bulk copy başında değiştirmek neden risklidir?
- Slot CPU/network metriği key count'tan neden daha değerlidir?
- Senior: migration sırasında node failure olursa invariant'lar nelerdir?
- Staff: automatic rebalancer'da hysteresis, cooldown ve blast-radius nasıl tasarlanır?

### Beklenen cevap derinliği
Junior: sharding/hash-slot/redirect. Mid: migration ve load skew. Senior: copy+delta+handoff invariant'ları, failure recovery ve client semantics. Staff: control loop, capacity headroom ve safe automation. Principal/CTO: operational simplicity, availability risk ve platform economics.

### Kısa alıştırma
Üç node ve altı slot için CPU-skew senaryosu oluştur; hangi slotu nereye taşıyacağını ve migration sırasında koruyacağın üç invariant'ı yaz.

### Proje fikri
`redis-slot-rebalancer-lab`: SLOT-STATS okuyup hot-slot adayları çıkaran dry-run controller; migration öncesi/sonrası p99 latency, CPU skew ve network throughput raporu üret.

### Failure modes / trade-off / production
Key count'u load sanmak; destination headroom kontrol etmemek; birden çok migration ile network'ü doyurmak; hot key'i slot migration ile çözülecek sanmak; cooldown/hysteresis olmadan oscillation yaratmak. Production'da per-slot CPU/network, node memory, replication/migration throughput, p95/p99 latency, redirect/error ve migration duration izlenmelidir.
