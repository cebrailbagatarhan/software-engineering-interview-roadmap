## Paket 1 — Mid/Senior Backend & Cybersecurity: Node.js Permission Model, Least Privilege & Sandbox Boundaries
**Süre:** 20–30 dk

### Konu anlatımı
Node.js Permission Model, process'in filesystem gibi kaynaklara erişimini allowlist yaklaşımıyla kısıtlar. `--permission` etkinleştirildiğinde izin verilmeyen erişimler default-deny davranışıyla `ERR_ACCESS_DENIED` üretir. Güncel Node.js dokümantasyonunda model Stable durumdadır ve enforce yanında audit mode da bulunur.

Mental model: bunu container sandbox veya OS account isolation'ın yerine değil, uygulama process'i içinde ek bir least-privilege katmanı olarak düşün. Bir dependency compromise olduğunda process'in sahip olduğu bütün OS yetkilerini otomatik olarak güvenli hale getirmez; yalnız modelin kapsadığı resource erişimlerini sınırlar.

```text
request -> Node process -> permission check -> resource
                         | allow
                         +-------------------->
                         | deny
                         +--> ERR_ACCESS_DENIED

OS/container boundary
        ^
        +-- ayrı ve daha dış güvenlik katmanı
```

### İçeride ne oluyor?
Filesystem read/write izinleri path bazında verilebilir. Audit mode migration için değerlidir: önce hangi erişimlerin reddedileceğini telemetry üzerinden gözlemle, allowlist'i daralt, sonra enforce et. Ancak permission model'i mutlak security boundary sanmak hatadır. 29 Temmuz 2026 güvenlik sürümünde permission model ile ilgili birden fazla bypass düzeltildi; örneğin radix split node yetki hatası ve trace-event write enforcement düzeltmeleri Node 24.18.1'e girdi. Bu, defense-in-depth ve patch hygiene'in neden gerekli olduğunu gösterir.

### Yüksek getirili mülakat soruları
- Application-level permission model ile container/OS sandbox arasındaki fark nedir?
- Default deny neden allow-by-default'tan daha güvenlidir?
- Audit mode'dan enforce mode'a migration nasıl yapılır?
- Path allowlist symlink/normalization gibi hangi edge case'leri doğurabilir?
- Dependency compromise senaryosunda permission model neyi azaltır, neyi azaltmaz?
- Senior: worker/child process ve native addon boundary'lerini nasıl threat-model edersin?
- Staff: yüzlerce serviste permission policy rollout'unu nasıl standardize edersin?
- CTO: platform guardrail ile developer friction arasındaki ekonomik trade-off nedir?

### Seviyeye göre cevap derinliği
Junior: least privilege ve allow/deny. Mid: resource/path izinleri ve audit. Senior: bypass surface, dependency risk, OS/container katmanı. Staff: fleet policy, observability ve rollout. Principal/CTO: supply-chain risk, platform ownership ve friction/risk dengesi.

### Kısa alıştırma
Bir image-processing worker için gereken minimum filesystem read/write alanlarını çıkar. Önce audit, sonra enforce rollout planı yaz; denied access alarmını tanımla.

### Proje fikri
`node-permission-lab`: upload worker'ı permission model ile çalıştır; allowed input/output dizinleri dışındaki erişimleri test et. Audit telemetry ve container-level read-only filesystem ile defense-in-depth ekle.

### Failure modes / trade-off / production
Permission model'i sandbox sanmak; wildcard allowlist'i gereğinden geniş tutmak; audit bulgularını temizlemeden enforce etmek; patch seviyesini ihmal etmek; dependency/native boundary'leri unutmak. Production'da denied/audit event rate, permission-policy drift, Node patch compliance, startup failures ve unexpected filesystem access izlenir.

## Paket 2 — Senior/Staff Cloud & System Design: S3 Conditional Writes, Optimistic Concurrency & Object-Store Coordination
**Süre:** 20–30 dk

### Konu anlatımı
Object storage'a yazmak her zaman last-writer-wins olmak zorunda değildir. Amazon S3 conditional writes, HTTP precondition'ları ile write sırasında state doğrulaması yapar. `If-None-Match: *` aynı key mevcutsa create'i reddederek create-if-absent sağlar. `If-Match: <ETag>` ise mevcut object's ETag'i beklenen değerle eşleşmiyorsa write'ı reddeder; bu optimistic compare-and-swap benzeri bir primitive'dir.

```text
reader -> GET object + ETag=v7
   | modify
   v
writer -> PUT If-Match:v7
              |
      current ETag == v7 ?
          /          \
       yes            no
       write       412 fail

conflict -> reread -> recompute -> retry
```

### İçeride ne oluyor?
`If-None-Match: *` aynı object key'e yarışan create'lerde yalnız ilk tamamlanan write'ın başarılı olmasını sağlayabilir; diğerleri 412 Precondition Failed alır. Concurrent delete gibi yarışlarda 409 Conflict de görülebilir. `If-Match` read-modify-write workflow'unda stale writer'ı tespit eder.

Bu primitive database transaction değildir: birden çok key üzerinde atomic invariant sağlamaz. ETag'i her bağlamda içerik hash'i varsaymak da yanlıştır. Bucket policy ile conditional-write kullanımını zorunlu kılmak mümkündür; böylece correctness yalnız client convention'ına bırakılmaz.

### Yüksek getirili mülakat soruları
- `If-None-Match:*` ile `If-Match:ETag` farkı nedir?
- Conditional write lost-update problemini nasıl azaltır?
- 412 ile 409 nasıl ele alınmalıdır?
- ETag neden genel amaçlı business version number değildir?
- Retry loop'ta reread/recompute neden gerekir?
- Senior: manifest/catalog pointer update'ında CAS nasıl kullanılır?
- Staff: multi-object invariant gerekiyorsa hangi ek coordination layer gerekir?
- Principal/CTO: DB yerine object-store coordination seçmenin cost/complexity sınırı nedir?

### Seviyeye göre cevap derinliği
Junior: overwrite ve precondition. Mid: ETag, 412, create-if-absent. Senior: optimistic concurrency ve retry. Staff: multi-writer coordination, policy enforcement ve failure semantics. Principal/CTO: storage architecture, operational simplicity ve consistency budget.

### Kısa alıştırma
`catalog/current.json` için GET+ETag → modify → conditional PUT akışını yaz. İki writer aynı ETag'i okuduğunda hangi writer'ın ne yapacağını adım adım göster.

### Proje fikri
`s3-cas-catalog-lab`: object-store üzerinde manifest pointer tut. 20 concurrent writer çalıştır; stale writes'ın 412 aldığını ve retry sonrası invariant'ın korunduğunu test et.

### Failure modes / trade-off / production
Unconditional PUT ile lost update; 412'yi generic transient error sanıp kör retry; reread etmeden aynı stale payload'u göndermek; ETag semantics'ini yanlış varsaymak; multi-key transaction beklemek; bucket policy guardrail'i olmadan client convention'ına güvenmek. Production'da 412/409 rate, retry count, CAS latency, hot-key contention ve invariant violations izlenir.

- Enforcing conditional writes with bucket policy: https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes-enforce.html
