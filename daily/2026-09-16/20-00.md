## Paket 1 — Mid/Senior Backend & Language Design: Go 1.27 Generic Methods, API Design & Migration
**Süre:** 20–30 dk

### Konu anlatımı
Go 1.27, 19 Ağustos 2026'da yayımlandı ve generic method desteğini dile ekledi. Önceden generic type tanımlanabilse de method'un kendi type parameter listesi olamıyordu; bu sınır bazı API'lerde her concrete integer/type ailesi için ayrı method veya top-level generic function tasarımına itiyordu.

Mental model:

```text
before: receiver[T] -> fixed method signature
                    -> helper generic function

after:  receiver[T] -> Method[U](...) -> U
                         ^ method-local type parameter
```

Generic method, her API'yi generic yapmak anlamına gelmez. Type inference okunabilirliği, constraint tasarımı, binary/source compatibility, interface ergonomics ve compile-time maliyeti birlikte düşünülmelidir. Migration'da yeni generic method eski concrete method'ları hemen silmek için gerekçe değildir; public API deprecation ve consumer migration ayrı lifecycle'dır.

### Mülakat soruları
- Generic type ile generic method arasındaki fark nedir?
- Method-local type parameter ne zaman receiver type parameter'dan daha doğrudur?
- Constraint'i gereğinden geniş/dar tasarlamanın bedeli nedir?
- Generic API ile interface-based polymorphism nasıl ayrılır?
- Senior: mevcut `IntN`, `Int32N`, `Int64N` benzeri API nasıl migrate edilir?
- Staff: büyük Go monorepo'da language-version rollout ve compatibility policy nasıl kurulur?

### Beklenen cevap derinliği
Junior: type parameter ve compile-time type safety. Mid: inference, constraints ve API ergonomics. Senior: compatibility, migration ve benchmark. Staff: organization-wide language-version policy. Principal/CTO: developer velocity, support window ve ecosystem risk.

### Kısa alıştırma
Üç concrete numeric method içeren küçük bir API'yi generic method'a dönüştür; eski caller'lar için compatibility planı ve iki kötü constraint örneği yaz.

### Proje fikri
`go127-generics-lab`: concrete, interface ve generic-method API'lerini aynı domain üzerinde karşılaştır; API yüzeyi, benchmark, compile time ve caller ergonomics ölç.

### Failure modes / trade-off / production
Her şeyi generic yapmak; constraint'i implementation detail'e bağlamak; inference'ın her çağrıda açık olduğunu varsaymak; eski API'yi ani silmek; Go version/toolchain drift. Production bağlantısı: SDK/library API tasarımı, shared platform packages, rollout telemetry ve dependency compatibility.

## Paket 2 — Senior/Staff Mobile, Networking & Cybersecurity: Android 17 Local Network Permission & Encrypted Client Hello
**Süre:** 20–30 dk

### Konu anlatımı
Android 17 / API 37 hedefleyen uygulamalarda yerel ağa erişim `ACCESS_LOCAL_NETWORK` runtime permission ile korunuyor. Smart-home discovery, casting ve LAN cihazlarıyla doğrudan konuşan uygulamalar artık ya sistem aracılı privacy-preserving picker kullanmalı ya da runtime permission istemeli. Android 16'daki opt-in model Android 17 target'ında zorunlu hale geliyor.

Android 17 ayrıca destekleyen networking library ve server kombinasyonlarında TLS Encrypted Client Hello (ECH) kullanarak ClientHello içindeki SNI bilgisinin ağ gözlemcilerince kolayca görülmesini azaltıyor. Negotiation mümkün değilse ECH GREASE davranışı devreye girebilir. Bunlar farklı katmanlardır: LAN permission cihaz üzerindeki capability/access policy; ECH ise ağ üzerindeki metadata privacy problemidir.

```text
App
 |-- capability gate --> ACCESS_LOCAL_NETWORK --> LAN device
 |
 +-- HTTPS stack --> TLS ClientHello + ECH --> Internet server
                         |
                         +-- hides/protects hostname metadata when negotiated
```

### Mülakat soruları
- Local-network permission hangi threat model'i azaltır?
- System-mediated picker neden permission istemeden daha privacy-preserving olabilir?
- ECH neyi şifreler; DNS veya hedef IP'yi otomatik olarak gizler mi?
- ECH negotiation başarısız olduğunda uygulama availability'si nasıl korunur?
- Permission denial UX ile network failure nasıl ayrıştırılır?
- Senior: mDNS/SSDP discovery kullanan uygulamayı API 37'ye nasıl migrate edersin?
- Staff: privacy, compatibility ve observability arasında rollout stratejisi nasıl kurulur?

### Beklenen cevap derinliği
Junior: runtime permission ve TLS/SNI. Mid: discovery/connect akışı ve fallback. Senior: threat model, ECH capability negotiation, telemetry. Staff: fleet rollout, OEM/network variance ve privacy-safe observability. Principal/CTO: privacy posture, ecosystem compatibility ve product conversion etkisi.

### Kısa alıştırma
Bir smart-TV casting uygulaması için permission state machine çiz: unknown → picker/permission → granted/denied → discovery → connect. ECH destekli ve desteksiz server yollarını ayrıca işaretle.

### Proje fikri
`android17-lan-privacy-lab`: LAN discovery + explicit permission/picker akışı; test server ile TLS/ECH capability gözlemi; denial, offline ve unsupported-path telemetry'sini PII toplamadan tasarla.

### Failure modes / trade-off / production
Permission'ı startup'ta bağlamsız istemek; denial ile timeout'u aynı hata yapmak; ECH'nin IP/DNS metadata'sını tamamen gizlediğini varsaymak; networking library desteğini kontrol etmemek; targetSdk yükseltmesini yalnız compile problemi sanmak. Production'da permission funnel, discovery success, connect latency/error class, OS/library version ve privacy-safe ECH capability metrikleri izlenmeli.
