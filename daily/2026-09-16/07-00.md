## Paket 1 — Mid/Senior Frontend: React 19.2 Activity, State Preservation & Hidden Work
**Süre:** 20–30 dk

### Konu anlatımı
React 19.2 `<Activity>` ile bir UI alt ağacını yalnızca mount/unmount ikiliğine sıkıştırmadan görünür veya gizli activity olarak yönetebilir. `hidden` modunda children görünmez, Effect'ler unmount edilir ve güncellemeler görünür işlere göre düşük önceliğe ertelenir; buna karşın UI state korunabilir. Bu, geri navigasyonda form state'ini korumak veya muhtemel sonraki ekranı background'da hazırlamak gibi durumlarda conditional rendering'den farklı bir araçtır.

### Mental model
```text
visible Activity
  state + DOM + effects + normal priority
          |
          v
hidden Activity
  state preserved
  effects unmounted
  updates deprioritized
          |
          v
visible again -> preserved state + effects remount
```

### İçeride ne oluyor?
Activity'yi cache sanmak hatadır: asıl primitive UI lifecycle ve scheduling üzerindedir. Hidden subtree'nin state'i korunurken side-effect lifecycle değişir. Bu nedenle subscription, timer ve external connection mantığı Effect cleanup/remount semantiğine dayanıklı olmalıdır. Pre-render faydası memory ve background CPU/network işiyle ödenir; her route'u Activity altında tutmak otomatik optimizasyon değildir.

### Yüksek getirili mülakat soruları
- `<Activity hidden>` ile `{visible && <Page/>}` arasındaki fark nedir?
- Hidden olduğunda state ve Effect'lere ne olur?
- CSS `display:none` ile neden aynı primitive değildir?
- Back-navigation UX'i nasıl iyileştirebilir?
- Hangi durumda memory maliyeti faydayı aşar?
- Staff: route-level Activity kullanımını hangi telemetry ile rollout edersin?

### Seviyeye göre cevap derinliği
Junior: mount/unmount ve component state. Mid: hidden/visible lifecycle ve Effect cleanup. Senior: scheduling, pre-render, memory/network trade-off. Staff/Principal: route policy, device class, performance budget ve rollout metrics. CTO: UX kazanımı ile frontend complexity/cost dengesini ürün metriğine bağlar.

### Kısa alıştırma
Üç tab'lı editörde tab değişiminde form state'i korunmalı ama websocket subscription yalnız görünür tab'da açık kalmalı. Activity lifecycle'ına göre component sınırlarını çiz.

### Proje fikri
`activity-route-lab`: conditional render ile Activity yaklaşımını back-navigation latency, state preservation, memory ve effect-count açısından karşılaştıran küçük React uygulaması.

### Failure modes / trade-off / production
Hidden subtree'yi ücretsiz cache sanmak; Effect cleanup'ı yanlış yazıp bağlantı sızıntısı oluşturmak; çok fazla ekranı pre-render ederek memory/network tüketmek; düşük güçlü cihazları hesaba katmamak. Production'da navigation latency, memory, long tasks, background request sayısı ve state-loss hata oranı izlenir.

- React Labs Activity background: https://react.dev/blog/2025/04/23/react-labs-view-transitions-activity-and-more

## Paket 2 — Senior/Staff Observability & Backend: OpenTelemetry Stable Database Semantic Conventions
**Süre:** 20–30 dk

### Konu anlatımı
Observability yalnız span üretmek değildir; producer ile dashboard/alert/query tüketicileri arasında bir telemetry contract yönetmektir. OpenTelemetry database client span semantic conventions artık genel olarak stable'dır. Stable model `db.system.name`, `db.namespace`, `db.collection.name`, `db.operation.name` ve `db.query.summary` gibi düşük-cardinality ve anlamlı alanlarla vendorlar arası sorgulanabilirlik hedefler.

Eski experimental convention kullanan instrumentation'lar için bir anda field rename yapmak dashboard ve alert'leri kırabilir. OpenTelemetry bu geçiş için `OTEL_SEMCONV_STABILITY_OPT_IN=database` ve aşamalı dual-emission için `database/dup` yaklaşımını tanımlar.

### Mental model
```text
DB client
   |
 instrumentation
   |
 semantic contract
   +-> stable spans
   +-> stable metrics
   |
 collector/backend
   |
 dashboards + alerts + SLO queries

schema change -> consumer migration -> old field retirement
```

### İçeride ne oluyor?
Database span `CLIENT` kind kullanır ve mümkünse logical operation'ı temsil eder. Span name için `db.query.summary` varsa tercih edilir; aksi durumda düşük-cardinality operation/target bilgisi kullanılır. Raw SQL'i span name veya yüksek-cardinality attribute olarak gelişigüzel kullanmak maliyet, PII/secrets ve cardinality riski yaratır. `db.client.operation.duration` stable histogram metriğidir; connection-pool metriklerinin bazıları hâlâ Development durumundadır, dolayısıyla 'database conventions stable' ifadesini bütün alanlara genellememek gerekir.

### Yüksek getirili mülakat soruları
- Semantic convention neden instrumentation detayı değil contract'tır?
- `db.query.summary` ile raw statement arasında cardinality/security farkı nedir?
- Stable convention migration dashboard'ları nasıl kırabilir?
- `database/dup` ne zaman kullanılır?
- Span ve `db.client.operation.duration` metriğini nasıl birlikte kullanırsın?
- Staff: yüzlerce serviste telemetry schema migration'ını nasıl yönetirsin?

### Seviyeye göre cevap derinliği
Mid: span/attribute/metric ve DB client telemetry. Senior: cardinality, PII, stable schema ve phased migration. Staff: fleet-wide compatibility, dual-write window, dashboard inventory ve cost. Principal/CTO: observability contract ownership, vendor portability ve telemetry economics.

### Kısa alıştırma
Eski dashboard `db.system`, `db.name` ve custom operation span adlarına bağlı olsun. Stable conventions'a geçiş için dual-emission, query migration ve retirement adımlarını sırala.

### Proje fikri
`otel-db-contract-lab`: PostgreSQL client instrumentation'ı, stable DB spans/metrics, cardinality guard ve eski/yeni dashboard karşılaştırması içeren küçük servis.

### Failure modes / trade-off / production
Tek seferde field rename; raw SQL ile PII veya cardinality patlaması; stable ve Development alanları ayırmamak; dual emission'ı süresiz bırakıp telemetry cost'u ikiye katlamak; dashboard/alert inventory olmadan migration. Production'da unknown attribute rate, series cardinality, telemetry bytes, dashboard query errors ve migration coverage izlenir.

- OpenTelemetry SQL database conventions: https://opentelemetry.io/docs/specs/semconv/db/sql/
- OpenTelemetry versioning/stability: https://opentelemetry.io/docs/specs/otel/versioning-and-stability/
