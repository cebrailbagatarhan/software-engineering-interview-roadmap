## Paket 1 — Mid/Senior Backend & Language Design: Python 3.14 t-strings, Structured Templates & Safe Processing
**Süre:** 20–30 dk

### Konu anlatımı
Python 3.14 ile gelen template string literals (`t"..."`), f-string'e benzeyen sözdizimini kullanır fakat hemen `str` üretmez. Sonuç immutable bir `string.templatelib.Template` nesnesidir; literal parçalar ve interpolation nesneleri ayrı tutulur. Böylece render etmeden önce interpolation değerini, expression bilgisini, conversion ve format spec'i inceleyen bir processor yazılabilir.

```text
source: t"Hello {user}!"
          |
          v
      Template
      /      \
 strings   interpolations
    |            |
    +---- processor ----+
              |
      escape / validate /
      transform / render
              |
              v
          final output
```

F-string mental modeli `expression -> formatting -> final string` iken t-string mental modeli `expression -> structured template -> policy-aware processor -> output` şeklindedir. Bu ayrım HTML escaping, SQL builder, logging/telemetry, shell-like DSL veya domain-specific rendering gibi alanlarda policy'yi string interpolation'dan ayırmayı sağlar.

### İçeride ne oluyor?
`Template.strings` statik parçaları, `Template.interpolations` dinamik parçaları taşır; `values` interpolation değerlerini kolayca verir. Template immutable'dır. Processor interpolation'ları sırayla ele alıp context'e göre escape/validate edebilir. Ancak t-string tek başına güvenlik mekanizması değildir: güvenlik processor'ın doğru context-sensitive policy uygulamasına bağlıdır. SQL'de doğru çözüm hâlâ değerleri driver parameter binding'e dönüştürmek; HTML'de doğru escaping context'e göre değişir.

### Yüksek getirili mülakat soruları
- t-string ile f-string arasındaki semantik fark nedir?
- Structured template neden final string'den daha güçlü bir abstraction'dır?
- `Template.strings`, `interpolations` ve `values` neyi temsil eder?
- t-string SQL injection'ı otomatik önler mi? Neden?
- HTML escaping neden processor katmanında yapılmalıdır?
- Senior: logging için structured template processor nasıl tasarlanır?
- Staff: şirket çapında safe templating API'si nasıl standardize edilir?

### Seviyeye göre cevap derinliği
Junior: f-string/t-string çıktı farkı. Mid: Template ve interpolation modeli. Senior: context-sensitive escaping, SQL parameterization ve API ergonomisi. Staff: framework boundary, policy enforcement ve migration. Principal/CTO: güvenli varsayılanlar, ecosystem adoption ve platform standardizasyonu.

### Kısa alıştırma
`user`, `query` ve `limit` alanları içeren bir t-string düşün. HTML renderer ve SQL renderer için hangi interpolation'ın nasıl işleneceğini yaz; neden aynı escaping fonksiyonunun iki context'te kullanılamayacağını açıkla.

### Proje fikri
`tstring-safe-renderer`: küçük bir Python 3.14 kütüphanesi yaz. HTML processor interpolated değerleri escape etsin; SQL processor literal SQL parçalarını korurken interpolation'ları DB-API parameter listesine dönüştürsün. Property-based test ile payload'ların syntax boundary'yi aşmadığını test et.

### Failure modes / trade-off / production
T-string'i otomatik sanitizer sanmak; expression metadata'yı güvenilir input sanmak; HTML/URL/JS/SQL context'lerini tek escape policy ile işlemek; processor bypass eden raw-string API bırakmak; observability'de secret/PII interpolation'larını loglamak. Production'da processor bypass oranı, rejected template, escaping error, sensitive-field redaction ve migration coverage izlenir.

## Paket 2 — Senior Algorithms & Data Structures: Rollback Union-Find & Offline Dynamic Connectivity
**Süre:** 20–30 dk

### Konu anlatımı
Klasik Disjoint Set Union (DSU / Union-Find), `find` ve `union` ile yalnız birleşen connectivity problemlerinde çok etkilidir. Zorluk edge silme geldiğinde başlar: DSU geçmiş birleşmeleri doğal olarak geri alamaz. Offline dynamic connectivity yaklaşımı, tüm add/remove/query olayları önceden biliniyorsa zamanı bir boyut olarak kullanır.

Her edge'in aktif olduğu zaman aralığını çıkar; bu aralığı segment tree üzerindeki zaman düğümlerine ekle. DFS ile tree'yi gezerken düğümde aktif edge'leri rollback-capable DSU'ya `union` et. Leaf'te o andaki connectivity query'sini cevapla; düğümden çıkarken DSU'yu snapshot'a geri sar.

```text
time: 0 1 2 3 4 5 6 7
edge A:   [=======)
edge B:       [===========)

segment tree over time
          [0,8)
         /     \
      [0,4)   [4,8)
        |        |
   active edges stored

DFS enter -> union changes
leaf      -> answer query
DFS exit  -> rollback(snapshot)
```

### İçeride ne oluyor?
Rollback DSU parent/size değişikliklerini bir stack'e yazar. `snapshot()` stack uzunluğunu döndürür; `rollback(s)` o uzunluğa kadar değişiklikleri tersine çevirir. Union-by-size/rank tree yüksekliğini logaritmik tutar. Buradaki kritik trade-off: klasik path compression rollback'i zorlaştırır çünkü tek `find` çok sayıda parent mutation üretir. Bu yüzden rollback DSU genellikle path compression kullanmaz; union-by-size ile `find` O(log n) sınırında kalır.

Bir edge'in aktif interval'i segment tree'de O(log Q) düğüme eklenir. Toplam Q operasyon için tipik karmaşıklık O(Q log Q log N) civarındadır; implementation ayrıntısına göre analiz sıkılaştırılabilir. Online cevap gerekiyorsa bu teknik uygun değildir; link-cut tree gibi daha karmaşık dynamic-tree yapıları gündeme gelebilir.

### Yüksek getirili mülakat soruları
- Klasik DSU edge deletion'ı neden kolay desteklemez?
- Rollback için hangi state'i history stack'e yazarsın?
- Path compression neden rollback ile çatışır?
- Union-by-size tek başına `find` yüksekliğini nasıl sınırlar?
- Edge active interval'lerini segment tree'ye neden koyuyoruz?
- Offline varsayımı algoritmayı nasıl basitleştiriyor?
- Senior: duplicate add/remove veya multiedge semantics'i nasıl ele alırsın?
- Staff: online requirement gelirse hangi alternatifleri değerlendirirsin?

### Seviyeye göre cevap derinliği
Junior: DSU parent/find/union. Mid: union-by-size ve connectivity. Senior: rollback invariants, interval decomposition ve complexity. Staff: offline/online trade-off, multigraph semantics ve test strategy. Principal: complexity bütçesi, implementation risk ve daha genel dynamic graph seçenekleri.

### Kısa alıştırma
8 zaman adımında `add(1,2)`, `add(2,3)`, `query(1,3)`, `remove(2,3)`, `query(1,3)` olaylarını yerleştir. Edge interval'lerini çıkar; segment-tree DFS sırasında history stack'in nasıl değiştiğini elle izle.

### Proje fikri
`offline-connectivity-lab`: add/remove/connected event stream'i alan CLI yaz. Naive BFS oracle ile random küçük graph testleri üret; rollback DSU sonucunu oracle ile karşılaştır. Operation count ve maximum history depth ölç.

### Failure modes / trade-off / production
Path compression kullanıp rollback log'unu eksik tutmak; no-op union için history invariant'ını bozmak; half-open interval sınırlarını karıştırmak; duplicate edge semantics tanımlamamak; recursion depth; offline varsayımını gerçek zamanlı ürüne taşımak. Production bağlantısı: zaman aralıklı network topology analizi, historical access graph sorguları, batch graph audit ve event-log replay. Gerçek online topology için daha farklı data structure veya recomputation stratejisi gerekebilir.
