## Paket 1 — Mid/Senior Backend & Runtime: Python 3.14 Free-Threading, GIL & Thread Safety
**Süre:** 20–30 dk

### Konu anlatımı
CPython'ın klasik build'inde GIL aynı anda yalnızca bir thread'in Python object/C API üzerinde çalışmasını sınırlar; blocking I/O sırasında bırakılabilir. Free-threaded build, GIL'i devre dışı bırakabilen ayrı bir CPython yapılandırmasıdır ve CPU-bound thread'lerin birden fazla çekirdekte gerçekten paralel ilerlemesine izin verir. Python 3.14 ile free-threaded build artık experimental değil, officially supported fakat hâlâ optional'dır. 3.14'te specializing adaptive interpreter da free-threaded modda etkinleştirilmiştir; resmi release notes tek-thread kod için platform/compiler'a bağlı yaklaşık %5–10 overhead bildirir.

GIL'in kalkması 'thread safety artık sorun değil' anlamına gelmez. Shared mutable application state için invariants hâlâ lock/queue/ownership ile korunmalıdır. Bazı üçüncü taraf extension modülleri free-threading'e hazır değilse GIL'i yeniden etkinleştirebilir. Dolayısıyla production rollout yalnız benchmark değil dependency compatibility, race testing ve observability problemidir.

### Mental model
```text
classic CPython
T1 ---- Python ----> [ GIL ] <---- Python ---- T2
                     one at a time

free-threaded build
T1 ---- Python ------------------> CPU core 1
T2 ---- Python ------------------> CPU core 2

parallelism gained != shared-state safety gained
```

### İçeride ne oluyor?
Free-threaded build source'tan `--disable-gil` ile üretilebilir. Runtime'da `sys._is_gil_enabled()` GIL'in etkin olup olmadığını, `sysconfig.get_config_var("Py_GIL_DISABLED")` build'in free-threading desteğini kontrol etmek için kullanılabilir. C extension'lar özellikle önemlidir: interpreter-wide GIL varsayımına dayanan native code yeni concurrency modelinde ayrıca incelenmelidir. Thread-safe container operation ile multi-step business invariant aynı şey değildir; `if key not in cache: cache[key]=...` gibi compound operation'lar explicit synchronization gerektirebilir.

### Yüksek getirili mülakat soruları
- GIL nedir, neyi garanti eder ve neyi garanti etmez?
- CPU-bound ve I/O-bound thread workload'ları klasik CPython'da nasıl ayrılır?
- Free-threading multiprocessing ihtiyacını tamamen kaldırır mı?
- Bir library neden GIL'i tekrar etkinleştirebilir?
- Built-in operation thread-safe olsa bile business invariant neden race edebilir?
- Senior: rollout öncesi dependency/race/performance validation planın nedir?
- Staff: mixed classic/free-threaded fleet'te capacity modelini nasıl kurarsın?

### Seviyeye göre cevap derinliği
Junior: thread, race, lock ve GIL sezgisi. Mid: CPU/I/O ayrımı ve shared state. Senior: extension compatibility, compound invariants, benchmark. Staff: fleet rollout, observability, capacity ve fallback.

### Kısa alıştırma
Dört CPU-bound worker'ın shared dictionary'de `read -> compute -> write` yaptığı bir örnek düşün. Hangi invariant'ların lock gerektirdiğini ve lock scope'unu küçültmek için work partitioning/queue yaklaşımını çiz.

### Proje fikri
`free-threading-bench-lab`: classic ve free-threaded CPython'da CPU-bound thread pool benchmark'ı; throughput, CPU utilization, p95 latency ve dependency compatibility raporu üret.

### Failure modes / trade-off / production
GIL'i application mutex sanmak; free-threading ile bütün kodun otomatik hızlanacağını varsaymak; native extension compatibility'sini atlamak; race testlerini yalnız unit test ile sınırlamak; tek-thread overhead ve memory/lock contention'ı ölçmemek. Production'da CPU saturation, throughput/core, latency, error/race sinyalleri ve GIL-enabled fallback oranı izlenmelidir.

## Paket 2 — Senior/Staff Cybersecurity & System Design: Post-Quantum Cryptography Migration & Crypto Agility
**Süre:** 20–30 dk

### Konu anlatımı
Post-quantum migration 'algoritmayı değiştir' işi değil, cryptographic dependency inventory + protocol interoperability + staged rollout problemidir. NIST'in finalized PQC standartları FIPS 203 ML-KEM (key establishment), FIPS 204 ML-DSA ve FIPS 205 SLH-DSA (digital signatures) olarak 2024'ten beri hazırdır; NIST 2026'da organizasyonların migration'a şimdi başlamasını öneriyor. NIST IR 8547 transition çizgisinde quantum-vulnerable algoritmaların standartlardan 2035'e kadar kaldırılması hedefleniyor; high-risk sistemler daha erken geçmelidir.

Önce nerede RSA/ECC/DH kullandığını keşfet: TLS termination, PKI/certificates, service identity, VPN, firmware/code signing, secrets/key wrapping, long-lived encrypted archives ve vendor appliances. Sonra data lifetime + exposure risk ile önceliklendir. 'Harvest now, decrypt later' nedeniyle bugün ele geçirilen uzun ömürlü ciphertext gelecekte risk taşıyabilir. Crypto agility; algorithm/version'ı protocol ve data model'e hard-code etmemek, dual-stack/hybrid geçişi, rollback ve telemetry sağlayabilmektir.

### Mental model
```text
inventory -> classify data lifetime/risk -> choose target standard
    |                                      |
    +-> protocol/vendor dependencies ------+
                         |
                  dual/hybrid rollout
                         |
              interop + perf + telemetry
                         |
                 deprecate legacy
```

### İçeride ne oluyor?
ML-KEM bir KEM'dir: public channel üzerinden shared secret establish etmek için kullanılır; doğrudan bulk data encryption algoritması değildir. Symmetric encryption hâlâ established secret ile yapılır. Migration'da key/ciphertext/signature boyutları, handshake bandwidth, certificate/profile değişiklikleri, HSM/KMS/library desteği ve protocol negotiation test edilmelidir. NIST'in Haziran 2026 PIV çalışma taslakları classical credential'ları koruyup PQC key/certificate objects ekleyen dual-stack yaklaşımını incremental deployment örneği olarak gösteriyor. HQC, ML-KEM'in yerine değil farklı matematik tabanlı gelecekteki backup KEM olarak seçildi; finalized ML-KEM migration'ını bekletme nedeni değildir.

### Yüksek getirili mülakat soruları
- KEM ile encryption primitive arasındaki fark nedir?
- ML-KEM, ML-DSA ve SLH-DSA hangi problemi çözer?
- Harvest-now-decrypt-later hangi veri sınıflarında önemlidir?
- Crypto inventory nasıl çıkarılır?
- Dual-stack/hybrid migration neden gerekir?
- Senior: certificate/HSM/vendor compatibility nasıl test edilir?
- Staff/CTO: 2035 hedefini portfolio roadmap'e nasıl çevirirsin?

### Seviyeye göre cevap derinliği
Mid: asymmetric/symmetric, KEM/signature ayrımı. Senior: inventory, interoperability, key sizes ve staged rollout. Staff: crypto agility, vendor/protocol dependencies, rollback. CTO: data-lifetime risk, compliance, investment sequencing ve organization-wide ownership.

### Kısa alıştırma
TLS edge, internal mTLS, code signing ve 10 yıl saklanan encrypted backup içeren şirket için migration priority matrix çıkar: confidentiality lifetime, exploit impact, dependency readiness ve rollback zorluğu.

### Proje fikri
`crypto-inventory-pqc-readiness`: repo/config/certificate metadata'sından algorithm inventory çıkaran scanner; owner, expiry, data lifetime, PQC-ready dependency ve migration status raporu üret.

### Failure modes / trade-off / production
Yalnız TLS edge'i taramak; library/HSM/appliance dependency'lerini atlamak; PQC'yi bulk cipher sanmak; algorithm identifiers'ı schema'ya hard-code etmek; packet/certificate size artışını ölçmemek; rollback olmadan big-bang migration. Production'da handshake failure, negotiation result, cert/signature size, CPU/latency, fallback ve legacy-algorithm usage izlenmelidir.
