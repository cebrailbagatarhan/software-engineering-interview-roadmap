## Paket 1 — Senior/Staff Databases: PostgreSQL 18 Generated Columns & Logical Replication Semantics
**Süre:** 20–30 dk

### Konu anlatımı
Generated column, değeri başka kolonlardan türetilen ve uygulamanın doğrudan yazmadığı kolondur. PostgreSQL 18 iki önemli davranışı birlikte getiriyor: generated column varsayılanı artık `VIRTUAL`; ayrıca `STORED` generated column değerleri logical replication üzerinden yayınlanabiliyor. Buradaki kritik mülakat ayrımı `expression'ı replike etmek` ile `hesaplanmış değeri replike etmek` arasındadır.

```text
publisher row
  base columns ----> generation expression ----> stored generated value
       |                                      |
       | publication default                  | opt-in: publish_generated_columns=stored
       v                                      v
 logical stream -----------------------> subscriber
                                           |
                         subscriber target is GENERATED?
                         -> local expression wins
                         regular column?
                         -> published value can land
```

### İçeride ne oluyor?
Generated columns doğrudan yazılamaz. `STORED` değer write-time'da hesaplanıp saklanır; `VIRTUAL` read-time'da hesaplanır. PostgreSQL 18 logical replication'da generated columns varsayılan olarak yayınlanmaz; publication `publish_generated_columns=stored` veya explicit column list ile stored generated değerleri yayınlayabilir. Ancak subscriber hedef kolonu da generated ise publisher'dan gelen generated değeri uygulanmaz; subscriber kendi generation expression'ını kullanır. Published generated değeri regular subscriber column'a taşımak, örneğin generated-column yeteneği olmayan heterojen target'larda faydalıdır. Pre-18 subscriber initial sync de önemli compatibility sınırıdır.

### Yüksek getirili mülakat soruları
- `VIRTUAL` ve `STORED` generated column farkı nedir?
- PostgreSQL 18'de default hangisidir ve bunun read/write maliyeti nedir?
- Generated column neden doğrudan INSERT/UPDATE edilemez?
- `publish_generated_columns=stored` ne yapar?
- Subscriber'daki hedef de generated ise hangi expression sonucu kazanır?
- Explicit publication column list ile publication option nasıl etkileşir?
- Senior: PostgreSQL -> non-PostgreSQL CDC target'ında bu özellik neden değerlidir?
- Staff: mixed-version upgrade sırasında initial sync ve schema compatibility nasıl yönetilir?

### Seviyeye göre cevap derinliği
Junior: derived data ve read-vs-write compute. Mid: virtual/stored ve publication. Senior: subscriber semantics, schema drift, CDC. Staff: mixed-version rollout, heterojen targets ve observability. Principal/CTO: storage/CPU economics, migration risk ve platform standardı.

### Kısa alıştırma
`price`, `quantity`, `total GENERATED ALWAYS AS (price*quantity) STORED` tablosunu düşün. `total` değerini regular column kullanan analytics subscriber'a taşımak için publication tasarla; subscriber generated olursa davranışın neden değiştiğini açıkla.

### Proje fikri
`pg18-generated-repl-lab`: iki PostgreSQL 18 instance kur; aynı base kolonlara farklı generated expression tanımla. Default publication, `publish_generated_columns=stored` ve explicit column-list senaryolarını karşılaştır; ardından regular target column deneyi yap.

### Failure modes / trade-off / production
Generated değeri source-of-truth sanmak; virtual değerin publish edileceğini varsaymak; subscriber expression drift'ini görmezden gelmek; pre-18 initial sync davranışını unutmak; column-list değişikliklerini birden fazla publication'da koordine etmemek. Production'da replication lag, apply conflicts, schema/version drift, publication definitions ve generated-expression migrations izlenir.

## Paket 2 — Staff/Principal AI Engineering & Leadership: Coding-Agent Context Architecture, Custom Instructions & Tool Boundaries
**Süre:** 20–30 dk

### Konu anlatımı
Coding agent performansını yalnız model seçimi belirlemez. Büyük repository'lerde asıl sistem tasarımı problemi doğru bağlamı, doğru scope'ta ve doğru araç yetkileriyle agente vermektir. GitHub Copilot ekosisteminde repo-wide custom instructions, path-specific instructions, `AGENTS.md`, reusable prompt/skill ve custom agent farklı lifetime ve scope'lara sahiptir. Bunları tek dev prompt'a yığmak context pollution ve çelişkili talimat üretir.

```text
organization policy
       |
repo-wide instructions ------> always-on invariants
       |
path-specific instructions ---> subsystem conventions
       |
custom agent -----------------> role + scoped tools + isolated context
       |
task prompt ------------------> current objective
       v
 agent actions -> tests/build/review -> human/policy gate
```

### İçeride ne oluyor?
Repository-wide instructions sürekli geçerli standartları taşır; path-specific instruction yalnız eşleşen dosya alanında uygulanır. `AGENTS.md` repository context/conventions için kullanılabilir. Custom agent ise kendi prompt'u, tool restrictions ve isteğe bağlı MCP server'ları olan uzman rolüdür; sub-agent kullanımı ana context'i gereksiz ayrıntıdan koruyabilir. Kritik güvenlik sınırı talimat değil tool capability'dir: `asla production'a yazma` demek yerine production-write aracını vermemek daha güçlü kontroldür. Agent çıktısı deterministic correctness garantisi değildir; test, build, static analysis, code review ve deployment policy bağımsız verifier katmanlarıdır.

### Yüksek getirili mülakat soruları
- Repo-wide instruction ile path-specific instruction ne zaman ayrılmalıdır?
- `AGENTS.md` ile custom agent hangi farklı problemi çözer?
- Neden her kuralı tek dev instruction dosyasına koymak kötü olabilir?
- Tool restriction neden yalnız prompt prohibition'dan daha güçlüdür?
- Sub-agent isolated context ne kazandırır, ne kaybettirir?
- Senior: agent-generated PR için verifier pipeline nasıl kurarsın?
- Staff: monorepo'da instruction precedence ve ownership nasıl tasarlanır?
- Principal/CTO: agent productivity kazanımını defect/security riskine karşı nasıl ölçersin?

### Seviyeye göre cevap derinliği
Junior: prompt/context ve tests. Mid: repo/path scope. Senior: tool permissions, verifier pipeline. Staff: monorepo governance, agent specialization, observability. Principal/CTO: developer productivity, security boundaries, auditability ve platform economics.

### Kısa alıştırma
Backend + mobile + Terraform içeren monorepo için hangi kuralların repo-wide, hangilerinin path-specific, hangilerinin security custom-agent içinde olacağını sınıflandır. Agent'e verilmeyecek iki destructive tool capability belirt.

### Proje fikri
`agent-context-lab`: küçük monorepo oluştur; `.github/copilot-instructions.md`, iki path-specific instruction ve security-review custom agent ekle. Aynı refactor görevini minimal ve overloaded context ile çalıştırıp test pass rate, edit churn ve review findings karşılaştır.

### Failure modes / trade-off / production
Çelişkili/stale instructions; her şeyi always-on context'e koymak; broad tool permissions; agent output'unu verifier sanmak; generated PR'larda ownership kaybı; secret-bearing context'i gereksiz taşımak. Production engineering'de test/build pass rate, revert/defect rate, review latency, agent edit churn, security findings ve human override oranı izlenir.
