## Paket 1 — Mid/Senior Cloud/SRE: Linux PSI, Resource Pressure & Load Shedding
**Süre:** 20–30 dk

### Konu anlatımı
CPU utilization tek başına sistemin sağlıklı olup olmadığını söylemez. Linux Pressure Stall Information (PSI), CPU, memory ve I/O contention yüzünden task'ların ne kadar süre ilerleyemediğini ölçer. `/proc/pressure/{cpu,memory,io}` altında `some` ve `full` sinyalleri ile 10/60/300 saniyelik ortalamalar ve toplam stall süresi sunulur.

`some`, en az bir task'ın kaynak beklediği zamanı; `full`, non-idle task'ların tamamının aynı anda stalled olduğu ağır thrashing durumunu ifade eder. PSI'nin değeri resource usage'dan productivity loss'a geçmesidir: %95 memory usage tek başına alarm olmayabilir, fakat artan memory `full` pressure latency ve OOM riskinin daha doğrudan sinyalidir. Kernel ayrıca threshold trigger'ları ile `poll/epoll` üzerinden event üretmeyi destekler; cgroup v2 altında pressure workload bazında da görülebilir.

### Mental model
```text
resource usage:  "ne kadar dolu?"
PSI:             "bu doluluk isi ne kadar durduruyor?"

requests -> workers -> CPU / memory / IO
                     | contention
                     v
                stalled time
                     |
             some / full PSI
                     |
       shed / throttle / scale / debug
```

### İçeride ne oluyor?
PSI scheduler ve reclaim/I/O wait yollarındaki stall zamanını aggregate eder. `avg10` kısa spike'lara, `avg60/avg300` daha kalıcı pressure'a bakmayı kolaylaştırır. Threshold monitor örneğin 1 saniyelik pencerede 150 ms memory stall olduğunda userspace'i uyandırabilir. Cgroup PSI sayesinde node genel olarak sağlıklı görünürken belirli container/service'in resource pressure yaşadığı ayrıştırılabilir.

### Yüksek getirili mülakat soruları
- CPU utilization ile CPU pressure farkı nedir?
- `some` ve `full` PSI nasıl yorumlanır?
- Memory usage yüksek ama PSI düşükse ne düşünürsün?
- PSI ile OOM kill arasındaki ilişki nedir?
- cgroup PSI multi-tenant node'da neden değerlidir?
- Senior: PSI sinyalini autoscaling veya load shedding'e nasıl bağlarsın?
- Staff: yanlış threshold oscillation/thundering-herd riskini nasıl azaltırsın?

### Seviyeye göre cevap derinliği
Junior/Mid: utilization vs stall ayrımı ve üç resource. Senior: some/full, windows, cgroup attribution, SLO correlation. Staff: adaptive load shedding, hysteresis, capacity policy ve noisy-neighbor isolation. Principal/CTO: utilization economics ile reliability headroom arasındaki denge.

### Kısa alıştırma
Bir API node'unda CPU %55, memory %92, memory `some avg10=18`, `full avg10=6` ve p99 latency 4 kat artmış olsun. İlk üç hipotezi ve load-shed/scale kararını yaz.

### Proje fikri
`psi-slo-guard`: `/proc/pressure` ve cgroup pressure dosyalarını okuyup p99 latency ile korele eden; configurable hysteresis ile low-priority request shedding simüle eden küçük agent/dashboard.

### Failure modes / trade-off / production
PSI'yi utilization sanmak; tek spike'ta scale etmek; system-level pressure ile workload attribution'ı karıştırmak; cgroup limitlerini hesaba katmamak; pressure azalınca kapasiteyi hemen geri çekip oscillation üretmek. Production'da PSI, queue depth, p95/p99 latency, OOM/reclaim, CPU steal ve shed rate birlikte izlenir.

### Kaynaklar

- cgroup v2 documentation: https://docs.kernel.org/admin-guide/cgroup-v2.html

## Paket 2 — Senior/Staff Data Engineering: Apache Iceberg Snapshot Retention, Branches & Safe Maintenance
**Süre:** 20–30 dk

### Konu anlatımı
Iceberg'de her write yeni bir table snapshot üretir. Snapshot'lar time travel, rollback ve reader isolation sağlar; fakat sonsuza kadar tutulursa metadata ve storage büyür. `expire_snapshots` eski snapshot'ları metadata'dan çıkarır ve artık hiçbir geçerli snapshot tarafından referans edilmeyen data files'ın temizlenmesini mümkün kılar.

Branches ve tags snapshot'lara named reference verir ve bağımsız retention policy taşıyabilir. Bu nedenle retention yalnızca “7 günden eskiyi sil” değildir: audit tag'i veya test branch'i bir snapshot'ı canlı tutabilir. `delete orphan files` ise farklı problemdir; failed distributed writes gibi nedenlerle hiçbir table metadata'sında referans edilmeyen dosyaları temizler. Orphan cleanup'ta retention cutoff'u çok agresif seçmek in-flight write dosyalarını silme riski taşır.

### Mental model
```text
main -> S10 -> S11 -> S12
         ^             ^
       audit-tag      current

expire snapshots:
  unreachable + retention dışı snapshots -> metadata'dan çıkar
  unreferenced files -> silinebilir

delete orphan files:
  metadata graph'ında hiç referans yok -> age guard -> delete
```

### İçeride ne oluyor?
Iceberg table metadata snapshot log, manifests ve data/delete file referanslarını izler. Snapshot expiration yalnızca artık gerekli olmayan dosyaları temizler; branch/tag tarafından referans edilen snapshot korunur. Streaming workload'larda sık commit snapshot/manifest sayısını hızla büyütebilir; snapshot expiration, metadata cleanup, data-file compaction ve manifest rewrite ayrı maintenance eksenleridir. Maintenance concurrency ve delete parallelism de catalog/object-store load'u açısından sınırlandırılmalıdır.

### Yüksek getirili mülakat soruları
- Snapshot expiration ile orphan-file deletion farkı nedir?
- Time travel retention storage cost'u nasıl etkiler?
- Tag neden eski snapshot'ın expire edilmesini engelleyebilir?
- Streaming table neden daha sık maintenance ister?
- Compaction ile snapshot expiration aynı problem midir?
- Senior: orphan cleanup cutoff'unu nasıl güvenli seçersin?
- Staff: yüzlerce table için maintenance scheduler'ı nasıl tasarlarsın?

### Seviyeye göre cevap derinliği
Mid: snapshot/time travel ve expiration. Senior: refs, orphan safety, streaming metadata growth, compaction ayrımı. Staff: fleet-wide scheduler, concurrency, object-store/catalog load ve observability. Principal/CTO: audit/compliance retention ile storage/query economics dengesi.

### Kısa alıştırma
Main son 7 günü, `audit-month-end` tag'i 180 günü ve test branch'i 3 günü tutuyor. 120 günlük tagged snapshot'ın neden silinmediğini ve orphan cleanup için neden ayrı age guard gerektiğini açıkla.

### Proje fikri
`iceberg-maintenance-planner`: table metadata/snapshot/ref envanteri çıkaran, dry-run expiration planı, estimated reclaim bytes, protected refs ve orphan candidates raporlayan scheduler.

### Failure modes / trade-off / production
Snapshot expiration'ı backup sanmak; branch/tag retention'ı unutmak; orphan cleanup'u çok düşük age threshold ile çalıştırmak; streaming commit rate'i sınırsız bırakmak; compaction ile metadata cleanup'u karıştırmak; bütün tabloları aynı anda maintain ederek catalog/object-store'u boğmak. Production'da snapshot count, metadata size, small-file count, orphan candidate age, maintenance duration/failure ve reclaimed bytes izlenir.
