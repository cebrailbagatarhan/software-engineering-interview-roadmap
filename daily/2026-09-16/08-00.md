## Paket 1 — Senior/Staff Cloud/SRE: Kubernetes In-Place Pod Resize, Vertical Scaling & Runtime Reality
**Süre:** 20–30 dk

### Konu anlatımı
Kubernetes'te CPU ve memory request/limit değiştirmek tarihsel olarak Pod recreation gerektiriyordu. In-Place Pod Resize, container CPU/memory kaynaklarını çalışan Pod üzerinde `/resize` subresource aracılığıyla değiştirebilir. Container-level özellik Kubernetes v1.35'ten beri stable'dır. v1.36 ile Pod-level aggregate resource budget'ın in-place resize edilmesi de Beta'ya yükseldi.

Temel ayrım desired state ile actuated state arasındadır: `spec.containers[*].resources` istenen değeri, `status.containerStatuses[*].resources` ise runtime'a uygulanmış mevcut değeri temsil eder. Resize anlık garanti değildir; node kapasitesi yetersizse `PodResizePending` görülebilir. `resizePolicy` değişiklikte container restart gerekip gerekmediğini belirlemeye yardım eder.

### Mental model
```text
metrics / operator / autoscaler
          |
          v
 desired CPU + memory
      Pod /resize
          |
          v
      scheduler/kubelet
       |          |
       |          +--> Pending / InProgress
       v
 container runtime / cgroup
          |
          v
 actual resources in Pod status

resource resize != application adapts automatically
```

### İçeride ne oluyor?
Control plane isteği kabul ettikten sonra kubelet node üzerindeki gerçek kapasite ve runtime kabiliyetleriyle değişikliği uygular. Bu nedenle API'deki desired resource ile kernel/runtime'daki actual resource arasında geçici fark olabilir. CPU resize çoğu uygulama için memory resize'dan daha güvenlidir; özellikle memory limit azaltma sırasında mevcut kullanım yeni limitin üzerindeyse OOM riski vardır. Kubernetes v1.35 memory decrease için best-effort güvenlik kontrolü ekledi, ancak bu mutlak garanti değildir.

Daha kritik production noktası runtime davranışıdır. Container cgroup limiti değişmiş olsa bile JVM, Python allocator, worker-pool veya uygulama içi cache yeni bütçeye otomatik uyum sağlamayabilir. Dolayısıyla vertical scaling yalnız orchestration problemi değildir; runtime ergonomics ve application feedback-loop problemidir.

### Yüksek getirili mülakat soruları
- In-place resize ile Pod recreation arasındaki temel availability farkı nedir?
- Desired ve actual resources neden ayrı izlenmelidir?
- `PodResizePending` hangi durumlarda görülebilir?
- CPU request artırmak ile CPU limit artırmak aynı etkiyi yaratır mı?
- Memory limit küçültmenin failure mode'u nedir?
- `resizePolicy` neden gereklidir?
- Senior: HPA ile vertical resize aynı anda çalışırsa hangi feedback-loop problemleri oluşabilir?
- Staff: stateful workload için resize rollout'unu hangi guardrail ve telemetry ile yaparsın?
- Principal/CTO: daha iyi utilization ile operasyonel karmaşıklık arasındaki ekonomik trade-off nedir?

### Seviyeye göre cevap derinliği
Junior: request, limit ve cgroup temelini açıklar. Mid: desired/actual state ve resize lifecycle'ını bilir. Senior: OOM, runtime adaptation, autoscaler interaction ve observability'yi tartışır. Staff: fleet rollout, admission policy, workload sınıfları ve blast radius tasarlar. Principal/CTO: utilization kazanımını reliability, platform complexity ve compute maliyetiyle ilişkilendirir.

### Kısa alıştırma
2 CPU / 4 GiB çalışan bir API'nin CPU throttling yaşadığını ama memory headroom'u bulunduğunu varsay. Pod recreation yapmadan 3 CPU'ya çıkış için desired→actual akışını, başarısız resize sinyallerini ve rollback koşullarını yaz.

### Proje fikri
`k8s-resize-lab`: CPU-bound servis + metrics collector + güvenli resize controller. Controller desired/actual resource farkını, resize latency'yi, throttling'i ve p99'u ölçsün; unsupported veya deferred durumda recreate/fallback politikası uygulasın.

### Failure modes / trade-off / production
API update başarılı diye runtime'ın adapte olduğunu varsaymak; memory limitini agresif küçültüp OOM yaratmak; HPA/VPA/custom controller feedback loop'larını koordine etmemek; Pending resize'ı gözlemlememek; Java/Python gibi runtime'ların memory davranışını hesaba katmamak. Production'da resize latency, Pending/InProgress conditions, throttled CPU, RSS/working-set, OOMKill, p95/p99 latency ve desired-vs-actual drift izlenir.

- Kubernetes resource management: https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/
- Resize container resources: https://kubernetes.io/docs/tasks/configure-pod-container/resize-container-resources/
- Kubernetes v1.35 GA announcement: https://kubernetes.io/blog/2025/12/19/kubernetes-v1-35-in-place-pod-resize-ga/
- Kubernetes v1.36 Pod-level resize Beta: https://kubernetes.io/blog/2026/04/30/kubernetes-v1-36-inplace-pod-level-resources-beta/

## Paket 2 — Senior/Staff Databases & Security: PostgreSQL 18 OAuth, Federated DB Authentication & Token Boundaries
**Süre:** 20–30 dk

### Konu anlatımı
PostgreSQL 18, OAuth tabanlı authentication desteği ekledi. PostgreSQL SASL katmanında `OAUTHBEARER` mekanizmasını destekler; istemci bearer token ile gelir, server token'ı yapılandırılmış validator modülü üzerinden doğrular ve başarılıysa PostgreSQL user identity'siyle bağlantıyı kurar. Bu, uzun ömürlü database password dağıtımı yerine merkezi identity provider ve kısa ömürlü token tabanlı erişim modellerinin önünü açar.

OAuth burada authorization'ın tamamını PostgreSQL dışına taşımak anlamına gelmez. Token bağlantı kurma kimliğini kanıtlar; database içindeki object privileges, roles, row-level security ve application authorization hâlâ ayrı katmanlardır.

### Mental model
```text
user / workload
      |
      v
 Identity Provider
      |
 access token
      |
      v
 libpq -- OAUTHBEARER --> PostgreSQL
                           |
                           v
                    OAuth validator
                           |
                    token accepted
                           |
                           v
                    DB role / grants

federated authentication != database authorization
```

### İçeride ne oluyor?
SASL exchange sırasında server kabul ettiği mechanism'leri bildirir; client `OAUTHBEARER` seçebilir. Client'ta token yoksa discovery metadata ve scope bilgisi kullanılarak OAuth flow yürütülebilir, ardından token ile yeni bağlantı açılır. PostgreSQL 18 libpq, opsiyonel olarak OAuth 2.0 Device Authorization flow desteği sağlar; custom client flow'ları hook API ile uygulanabilir.

Server tarafında `oauth_validator_libraries` token doğrulama modüllerini seçer. PostgreSQL varsayılan validator implementation'ı dağıtmaz; doğrulayıcı ayrıca sağlanmalıdır. Bu mimari önemli bir trust boundary yaratır: issuer, audience/scope, expiry ve identity mapping doğrulaması yanlışsa merkezi identity kullanmak güvenliği otomatik sağlamaz.

### Yüksek getirili mülakat soruları
- OAuth DB password probleminde neyi iyileştirir?
- Authentication ile PostgreSQL role authorization neden ayrı tutulmalıdır?
- `OAUTHBEARER` SASL exchange'in rolü nedir?
- Bearer token sızarsa temel risk nedir?
- Token expiry connection pool'ları nasıl etkiler?
- Validator hangi claim'leri ve trust boundary'leri kontrol etmelidir?
- Senior: password→OAuth migration sırasında break-glass erişimini nasıl tasarlarsın?
- Staff: yüzlerce servis için workload identity→DB role mapping'i nasıl standardize edersin?
- Principal/CTO: federated DB auth'un güvenlik kazanımını IdP dependency/blast-radius maliyetiyle nasıl dengelersin?

### Seviyeye göre cevap derinliği
Junior: authentication vs authorization ve bearer token kavramı. Mid: SASL/OAuth flow, expiry ve scopes. Senior: validator, pool refresh, identity mapping ve failure modes. Staff: fleet migration, break-glass, auditability ve least privilege. Principal/CTO: identity platform dependency, compliance, operational resilience ve credential-management ekonomisi.

### Kısa alıştırma
Bir servis bugün static PostgreSQL password kullanıyor. Workload identity + OAuth'a geçiş için token acquisition, validation, DB role mapping, pool refresh, audit ve break-glass adımlarını sıralayan migration planı çiz.

### Proje fikri
`pg-oauth-lab`: PostgreSQL 18 + test IdP + libpq client ile kısa ömürlü token authentication demosu. Token expiry, invalid audience, IdP outage ve validator failure senaryolarını fault-injection ile test et; DB grants'in OAuth'tan ayrı kaldığını göster.

### Failure modes / trade-off / production
OAuth'u authorization sanmak; token'ı loglamak; audience/issuer/scope doğrulamasını gevşek yapmak; pool içindeki uzun ömürlü connection'larla token lifecycle'ını karıştırmak; IdP outage için kontrollü strateji olmaması; break-glass hesabını kalıcı bypass'a çevirmek. Production'da auth success/failure, validator latency/error, token acquisition latency, expired-token rate, identity→role mapping failures ve privileged role usage izlenir.
