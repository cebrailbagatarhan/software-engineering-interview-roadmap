## Paket 1 — Senior/Staff Cybersecurity & DevOps: Build Provenance, Artifact Attestations & Deployment Policy
**Süre:** 20–30 dk

### Konu anlatımı
Bir container image'in registry'de bulunması onun güvenilir kaynaktan üretildiğini kanıtlamaz. Supply-chain güvenliğinde temel soru yalnız `bu digest değişmedi mi?` değil, `bu digest hangi repository, commit ve CI workflow tarafından, hangi identity ile üretildi?` sorusudur. Artifact attestation, build artifact ile provenance claim arasında kriptografik doğrulanabilir bağ kurar.

GitHub Actions artifact attestations OIDC tabanlı identity ve Sigstore kullanarak build provenance üretebilir. Attestation; artifact digest'i ile repository/workflow/commit gibi build context'ini ilişkilendirir. Kritik nokta: attestation tek başına artifact'ın güvenli olduğunu kanıtlamaz; deployment policy hangi provenance'ın kabul edilebilir olduğuna karar vermelidir.

```text
source commit -> trusted CI workflow -> build artifact
                      |                    |
                      +---- OIDC ----------+
                              |
                        signed attestation
                              |
registry artifact + provenance verification
                              |
                      admission/deploy policy
```

### İçeride ne oluyor?
Artifact digest subject olur; workflow identity provenance statement üretir ve imzalanır. Consumer `gh attestation verify` gibi verifier ile artifact'ın beklenen repository/identity'den geldiğini kontrol edebilir. Kubernetes admission katmanı bu doğrulamayı deploy-time policy'ye çevirebilir. SBOM attestation provenance'dan farklı soruyu cevaplar: provenance `nerede/nasıl build edildi?`, SBOM `içinde hangi bileşenler var?` der. İkisi birlikte daha güçlüdür ama vulnerability-free garantisi vermez.

### Yüksek getirili mülakat soruları
- Artifact signing ile build provenance arasındaki fark nedir?
- Digest integrity neden tek başına supply-chain trust sağlamaz?
- OIDC burada hangi long-lived secret problemini azaltır?
- Provenance ile SBOM hangi farklı soruları cevaplar?
- Attestation üretmek ama verify etmemek neden az değer sağlar?
- Senior: CI compromise edilmişse attestation neyi kanıtlar/neye yetmez?
- Staff: Kubernetes admission'da provenance policy nasıl rollout edilir?
- Principal/CTO: developer velocity ile mandatory verification arasındaki denge nasıl kurulur?

### Seviyeye göre cevap derinliği
Junior: hash, signature, artifact. Mid: provenance, OIDC, SBOM. Senior: trust root, CI compromise, verifier. Staff: admission policy, exception/break-glass, rollout. Principal/CTO: organization-wide trust policy, audit ve supply-chain risk economics.

### Kısa alıştırma
Bir container deployment için şu policy'yi tasarla: yalnız `org/payments` reposunun protected branch'inden trusted workflow ile üretilmiş ve attestation'ı doğrulanan digest'ler production'a girebilsin. Verification failure ve break-glass davranışını yaz.

### Proje fikri
`provenance-gate-lab`: GitHub Actions ile image build + artifact attestation üret; CI'da verify et; test Kubernetes cluster'ında admission policy ile unsigned/untrusted image'i reddet.

### Failure modes / trade-off / production
Attestation'ı vulnerability scanner sanmak; mutable tag'i identity kabul etmek; verifier/policy koymadan yalnız provenance üretmek; aşırı geniş workflow permissions; compromised trusted workflow; break-glass audit'ini unutmak. Production'da verification pass/fail, rejected deployments, exception usage, unattested artifact rate, workflow identity drift ve SBOM coverage izlenir.

- GitHub Docs — Establish build provenance: https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations
- GitHub Docs — Kubernetes enforcement: https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/enforce-artifact-attestations

## Paket 2 — Senior/Staff Data Engineering: Apache Kafka Tiered Storage, Hot/Cold Logs & Remote Fetch Economics
**Süre:** 20–30 dk

### Konu anlatımı
Kafka broker diskini uzun retention için sürekli büyütmek pahalıdır; fakat eski event'ler backfill, audit ve recovery için tutulmak istenebilir. Tiered Storage log'u iki katmana ayırır: active/recent segment'ler local broker storage'da, tamamlanmış eski segment'ler remote object/storage katmanında tutulur. Böylece compute/broker lifecycle ile uzun süreli storage lifecycle kısmen ayrışır.

```text
producer -> broker partition log
                 |
          active/local segments  <- hot tail reads
                 |
            segment rolls
                 v
          RemoteStorageManager
                 |
          remote object storage  <- old/backfill reads
                 |
        remote metadata + indexes
```

### İçeride ne oluyor?
Broker-level `remote.log.storage.system.enable` remote-log servislerini açar; topic-level `remote.storage.enable` hangi topic'in tiered storage kullandığını belirler. `local.retention.*` local hot window'u, normal `retention.*` toplam retention'ı yönetir. RemoteLogMetadataManager remote segment lifecycle metadata'sını tutar. Remote read ucuz storage kapasitesi kazandırırken latency/throughput ve egress/object-request maliyeti yaratır. Güncel Kafka dokümantasyonunda compacted topic desteği hâlâ limitation olarak listeleniyor; remote fetch davranışı workload tasarımında dikkate alınmalıdır.

### Yüksek getirili mülakat soruları
- Tiered storage broker disk maliyetini nasıl değiştirir?
- `local.retention.ms` ile `retention.ms` farkı nedir?
- Active segment neden doğrudan remote'a taşınmaz?
- Remote log metadata neden kritik correctness state'idir?
- Backfill workload'u tail-read workload'undan nasıl farklıdır?
- Senior: remote-store outage consumer'ı nasıl etkiler?
- Staff: local hot-window'u hangi metriklerle boyutlandırırsın?
- Principal/CTO: broker SSD, object storage, egress ve recovery economics'i nasıl modelliyorsun?

### Seviyeye göre cevap derinliği
Junior: partition/log segment/retention. Mid: local vs remote tier. Senior: metadata, remote fetch, failure recovery. Staff: capacity, backfill isolation, rollout. Principal/CTO: storage economics, vendor/plugin risk ve compliance retention.

### Kısa alıştırma
Günde 5 TB ingest, 7 günlük hot window ve 90 günlük total retention olan cluster için local vs remote logical storage büyüklüğünü yaklaşık hesapla. Backfill'in p99 latency ve network maliyetine etkisini belirt.

### Proje fikri
`kafka-tiered-storage-lab`: test cluster'da kısa segment roll ve local retention ayarla; eski offset'ten consume ederek remote fetch latency/throughput'u local tail-read ile karşılaştır.

### Failure modes / trade-off / production
Object storage'u local disk kadar düşük latency varsaymak; remote metadata'yı kritik state saymamak; backfill'in live consumers'ı boğmasına izin vermek; retention/delete semantics'i test etmemek; unsupported compacted-topic varsayımı; remote provider/plugin lock-in. Production'da local/remote bytes, copy lag/failure, remote fetch latency/rate, cache hit, object-store error/egress ve consumer lag izlenir.
