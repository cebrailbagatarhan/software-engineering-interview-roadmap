## Paket 1 — Junior → Staff Algorithms & Data Structures / Databases: Cuckoo Filters, Approximate Membership & Deletion Economics
**Süre:** 20–30 dk

### Konu anlatımı
Approximate membership problemi “x bu sette kesinlikle yok mu, yoksa muhtemelen var mı?” sorusunu az bellek ve yüksek throughput ile cevaplar. Bloom filter false positive üretebilir ama false negative üretmemesi beklenir; standart Bloom filter güvenli deletion sunmaz. Cuckoo filter ise tam key yerine kısa fingerprint saklar ve her fingerprint için iki olası bucket kullanır. Insert sırasında iki bucket doluysa mevcut fingerprint’lerden biri alternatif bucket’a taşınarak yer açılmaya çalışılır.

Deletion’ın mümkün olmasının nedeni bit paylaşımı yerine fingerprint entry’lerinin ayrı tutulmasıdır. Fakat bu bedelsiz değildir: bucket size, fingerprint width ve load factor false-positive oranını, memory footprint’i ve insertion failure riskini birlikte belirler. Yük çok yükseldiğinde relocation zinciri uzayabilir ve insert başarısız olabilir; resize/rebuild gerekir.

### Mental model
```mermaid
flowchart LR
  K[Key] --> F[Fingerprint f]
  K --> H[Bucket i1]
  F --> A[Alt bucket i2 = i1 XOR hash(f)]
  H --> B1[Bucket i1]
  A --> B2[Bucket i2]
  B1 <-->|relocate fingerprint| B2
```
**Invariant:** Lookup yalnız iki candidate bucket’ta fingerprint arar; “yok” güçlü cevaptır, “var” false positive olabilir.

### İçeride ne oluyor?
- Key’den kısa fingerprint ve ilk bucket index’i türetilir.
- Alternatif index fingerprint’ten deterministik hesaplanır; relocation sonrası geri bulunabilir.
- Lookup iki bucket’ı kontrol ettiği için beklenen erişim sabittir.
- Delete yalnız eşleşen fingerprint entry’sini kaldırır; collision nedeniyle uygulama seviyesinde exact identity kanıtı değildir.
- Fingerprint bit sayısı büyüdükçe false-positive olasılığı düşer fakat memory artar.
- Load factor yükseldikçe space efficiency artar fakat insertion tail latency ve failure riski büyür.

### Yüksek getirili mülakat soruları
1. Bloom filter ile Cuckoo filter’ın temel farkı nedir?
2. Cuckoo filter deletion’ı neden daha doğal destekler?
3. False positive neden vardır; false negative hangi bug’larla ortaya çıkabilir?
4. İki candidate bucket nasıl hesaplanır ve relocation neden çalışır?
5. Load factor %95’e yaklaşırken hangi failure mode’ları beklersin?
6. Senior: resize sırasında concurrent read/write correctness’i nasıl korursun?
7. Staff: LSM-tree negative lookup, cache admission veya network dedup için hangi approximate structure’ı seçersin?

### Seviyeye göre cevap derinliği
- **Junior:** approximate membership, false positive ve deletion farkını açıklar.
- **Mid:** fingerprint, iki bucket ve relocation mekanizmasını anlatır.
- **Senior:** sizing, concurrency, rebuild ve adversarial-key risklerini tartışır.
- **Staff:** workload/FPR/memory/latency hedeflerinden veri yapısı seçer ve production rollout tasarlar.

### Kısa alıştırma
4 slot’lu bucket’larla küçük bir Cuckoo filter simüle et. 12 key ekle; her insert için iki candidate bucket’ı ve relocation sayısını kaydet. Sonra 3 key silip lookup sonuçlarını karşılaştır.

### Proje fikri
`cuckoo-filter-lab`: configurable fingerprint width/bucket size ile filter yaz; Bloom filter’a memory/key, lookup throughput, false-positive rate ve insert failure açısından benchmark et. Load factor sweep grafiği üret.

### Failure modes / trade-off / production bağlantısı
Fingerprint’i fazla kısaltmak yüksek false positive; table’ı aşırı doldurmak relocation storm; sınırsız kick loop latency spike; unsafe concurrent mutation false negative; hash-flood/adversarial input CPU amplification yaratabilir. Production’da load factor, kicks/insert, insert-failure, FPR sample, rebuild duration ve memory/key izlenir. LSM-tree, cache ve dedup katmanlarında filter sonucu çoğunlukla pahalı exact lookup’tan önce ucuz negative gate olarak kullanılır.

### Kaynaklar
- Fan, Andersen, Kaminsky, Mitzenmacher — *Cuckoo Filter: Practically Better Than Bloom*, CoNEXT 2014: https://www.cs.cmu.edu/~dga/papers/cuckoo-conext2014-abstract.html
- CMU ISTC publication page: https://istc-cc.cmu.edu/publications/papers/2014/cuckoo-conext2014_abs.shtml

## Paket 2 — Mid → Principal Backend / Distributed Systems: GCRA Rate Limiting, Virtual Scheduling & Distributed Quota Correctness
**Süre:** 20–30 dk

### Konu anlatımı
Rate limiter yalnız “dakikada N request” sayacı değildir; burst davranışı, fairness, retry semantics ve distributed coordination sözleşmesidir. Generic Cell Rate Algorithm (GCRA), her key için geçmiş request listesini tutmak yerine teorik bir sonraki uygun zamanı (TAT, theoretical arrival time) izleyerek leaky-bucket benzeri pacing sağlar.

Her kabul edilen request TAT’i emission interval kadar ileri iter. Yeni request, izin verilen burst tolerance hesaba katıldığında çok erken gelmişse reddedilir ve `Retry-After` türetilebilir. Bu model tek timestamp benzeri state ile çalışabildiğinden Redis gibi merkezi store’da atomic compare/update için uygundur.

### Mental model
```text
real time ---- t ------------------------------>
               | request arrives
TAT -----------|----------- next ideal slot --->
               ^
        burst tolerance kadar erken geliş kabul edilebilir

allow => TAT = max(TAT, now) + cost * interval
reject => state değişmez; retry_after = admissible_time - now
```
**Invariant:** Aynı quota key’i için karar ve TAT update’i atomik olmalıdır; aksi halde iki replica aynı kapasiteyi eşzamanlı harcayabilir.

### İçeride ne oluyor?
- `interval = period / rate`; weighted request için `cost * interval` ilerleme uygulanabilir.
- Burst tolerance kısa süreli kümelenmeye izin verir fakat uzun dönem ortalama rate’i değiştirmez.
- Merkezi Redis + Lua/module atomik decision/update sağlar; network hop latency ekler.
- Local limiter düşük latency verir fakat replica sayısıyla aggregate quota aşılabilir.
- Credit leasing merkezi QPS’yi azaltır ama failover sırasında bounded overshoot tasarımı gerektirir.
- Clock source ve unit conversion kritik; wall-clock jump limiter correctness’ini bozabilir.

### Yüksek getirili mülakat soruları
1. Fixed window neden boundary burst üretir?
2. Token bucket ile GCRA’yı mental model açısından karşılaştır.
3. GCRA neden tek zaman state’iyle uygulanabilir?
4. `Retry-After` nasıl hesaplanır?
5. Multi-replica API’de local limiter neden global quota garantilemez?
6. Senior: Redis outage sırasında fail-open mı fail-closed mu seçersin?
7. Staff: hierarchical tenant/user/endpoint quota’yı nasıl atomik veya bounded-overshoot tasarlarsın?
8. Principal: strict global quota ile availability/latency/cost arasındaki sözleşmeyi nasıl ürünleştirirsin?

### Seviyeye göre cevap derinliği
- **Mid:** rate, burst, TAT ve retry semantics’i doğru açıklar.
- **Senior:** atomicity, clock, Redis failure ve hot-key problemlerini çözer.
- **Staff:** multi-dimensional quota, sharding, leasing ve observability tasarlar.
- **Principal:** quota correctness seviyesini SLO, abuse risk, revenue protection ve infra cost ile bağlar.

### Kısa alıştırma
10 req/s, burst=5 için 0–1000 ms arasında 12 arrival timestamp üret. Her request için allow/reject, yeni TAT ve retry-after hesapla. Aynı workload’u fixed-window ile karşılaştır.

### Proje fikri
`gcra-distributed-limiter-lab`: Redis-backed atomic GCRA limiter kur; 3 API replica ile load test et. Redis latency/partition enjekte et; strict, fail-open ve local-credit fallback modlarında overshoot, p99 ve availability ölç.

### Failure modes / trade-off / production bağlantısı
Non-atomic GET/SET quota overshoot, hot tenant Redis hotspot, yanlış clock/unit hesapları unfair throttling, unlimited key cardinality memory blow-up, fail-open abuse ve fail-closed outage amplification yaratır. Production’da allow/deny rate, retry-after distribution, per-key hotness, store p99, limiter error rate, observed overshoot ve quota-config version izlenir.

- `go-redis/redis_rate` — Redis-backed GCRA implementation: https://github.com/go-redis/redis_rate
