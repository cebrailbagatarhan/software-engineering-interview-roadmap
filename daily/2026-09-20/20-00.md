## Paket 1 — Junior → Principal Databases: B+Tree — fan-out, page split, range scan ve index economics
**Süre:** 20–30 dk

### Konu anlatımı
B+Tree, disk/page tabanlı ordered index için temel mental modeldir. Binary tree gibi her node iki child taşımaz; bir page çok sayıda separator key ve child pointer taşıdığı için **fan-out** yüksektir ve tree height küçülür. Internal page arama yönlendirir; leaf page gerçek index entry'lerini taşır. Leaf'lerin key order'ında komşu olması range scan'i verimli yapar. PostgreSQL B-tree equality/range predicate'lerini ve sıralı output'u destekler; güncel PostgreSQL 18 internals dokümanı yapıyı multi-level pages, internal/leaf pages ve leaf-level sibling ilişkileriyle açıklar.

```text
                 [20 | 50]
               /     |      \
      [2 8 14] <-> [20 31 44] <-> [50 61 79]
          leaf           leaf            leaf

point lookup: root -> internal -> leaf
range scan: seek once -> leaf siblings boyunca ilerle
insert full leaf -> split -> parent separator ekle
```

### İçeride ne oluyor?
- Page size ve key/pointer boyutu fan-out'u belirler; yüksek fan-out az I/O seviyesine yardım eder.
- Point lookup root'tan leaf'e iner; cache hit/miss gerçek maliyeti değiştirir.
- Range query başlangıç leaf'ini bulduktan sonra ordered leaf pages boyunca ilerleyebilir.
- Full page insert split doğurabilir; split parent'a separator ekler ve yukarı propagate olabilir.
- Index write path ekstra page work, WAL/logging ve cache pressure yaratır: read hızının write/storage bedeli vardır.
- PostgreSQL B-tree sorted output verebildiği için bazı `ORDER BY ... LIMIT n` sorgularında explicit sort'tan kaçınabilir.
- Selectivity düşükse planner sequential scan'i index traversal + heap access'ten daha ucuz bulabilir.

### Yüksek getirili mülakat soruları
1. B+Tree neden binary search tree yerine database indexlerinde yaygındır?
2. Fan-out neden önemlidir?
3. Point lookup ile range scan path'i nasıl farklıdır?
4. Mid: page split ne zaman olur ve maliyeti nedir?
5. Senior: index neden her sorguyu hızlandırmaz?
6. Staff: random UUID benzeri key ile monotonic key write pattern'larını page locality/split açısından karşılaştır.
7. Principal: read latency, write amplification, storage ve operational complexity arasında index budget nasıl yönetilir?

### Seviyeye göre cevap derinliği
- **Junior:** ordered tree, root/internal/leaf ve lookup sezgisi.
- **Mid:** fan-out, page I/O, split ve range scan.
- **Senior:** selectivity, cache locality, write amplification, composite index ve planner.
- **Staff/Principal:** workload economics, hot pages, concurrency, index governance ve capacity.

### Kısa alıştırma
8 KiB page'de ortalama 32-byte key+pointer entry ile kaba fan-out tahmini yap. Fan-out 200 ise 1 milyar entry için kaç tree seviyesi gerektiğini yaklaşık hesapla; neden `O(log n)` ifadesinin tek başına I/O maliyetini anlatmadığını açıkla.

### Proje fikri
`bptree-lab`: sabit-size page kullanan küçük in-memory/on-disk B+Tree yaz. Point/range lookup, leaf split ve root split ekle; sorted-array ve hash-map baseline ile point/range/write benchmark karşılaştır.

### Failure modes / trade-off / production bağlantısı
Her kolona index eklemek write amplification ve storage'ı büyütür. Low-selectivity query, stale statistics, random-write pattern ve cache miss index avantajını silebilir. Production'da index hit/read latency, buffer-cache hit, page split/bloat, index size, write throughput ve query plans birlikte izlenir.

## Paket 2 — Mid → Principal Backend/SRE: Distributed Tracing Sampling — head, tail, cardinality ve cost
**Süre:** 20–30 dk

### Konu anlatımı
Her trace'i saklamak yüksek hacimli sistemlerde pahalıdır. Sampling, observability signal ile ingestion/storage cost arasında kontrollü kayıp yaratır. **Head sampling** trace başında karar verir; ucuz ve stateless'tir fakat henüz oluşmamış error/latency bilgisini bilemez. **Tail sampling** trace'in span'ları görüldükten sonra karar verebilir; error veya yüksek latency gibi sonuçları koruyabilir fakat buffering, memory, decision latency ve trace-affinity gerektirir. OpenTelemetry Collector probabilistic ve tail sampling processor'larını destekler.

```text
request -> trace id -> spans -----------+
                                        |
 head sampling: karar başta             |
 keep/drop ---------------------------> backend

 tail sampling:
 spans -> trace-aware collector -> buffer -> policy
                                  |        | error?
                                  |        | slow?
                                  +------> keep/drop -> backend

signal quality <---- trade-off ----> telemetry cost
```

### İçeride ne oluyor?
- Head sampler SDK tarafında erken karar vererek downstream telemetry hacmini azaltabilir.
- Tail sampler karar için trace'in yeterli kısmını bekler; state ve memory tüketir.
- Aynı trace'in span'ları farklı collector'lara dağılırsa tail decision eksik bağlamla yapılabilir; trace-aware routing önemlidir.
- Error/latency policy rare-but-important traces'i koruyabilir; yalnız probabilistic sampling bunları kaçırabilir.
- Sampling oranı metric değildir: sampled trace'lardan doğrudan request count/SLO hesaplamak bias yaratabilir.
- Attribute cardinality sampling'den ayrı bir maliyet eksenidir; user/request ID gibi sınırsız dimensions backend maliyetini büyütebilir.

### Yüksek getirili mülakat soruları
1. Head ve tail sampling farkı nedir?
2. Neden yüzde 1 random sampling bütün incident'lar için yeterli değildir?
3. Mid: tail sampling neden daha fazla memory ister?
4. Senior: distributed collector fleet'te trace affinity neden gerekir?
5. Staff: errors + slow traces + baseline random sample policy'sini nasıl tasarlarsın?
6. Principal: telemetry budget, compliance, SLO debugging ve vendor cost arasında governance nasıl kurulur?

### Seviyeye göre cevap derinliği
- **Mid:** trace/span, sampling ve cost gerekçesi.
- **Senior:** head/tail, buffering, bias ve trace completeness.
- **Staff:** collector topology, routing, backpressure, policy composition ve cardinality.
- **Principal:** telemetry economics, privacy, retention, SLO/debugging coverage ve platform standards.

### Kısa alıştırma
100k req/s sistemde her trace ortalama 20 KiB ise ham telemetry throughput'u hesapla. %1 head sample ile hacmi karşılaştır. Error rate %0.05 ise random sample'ın rare failures'ı seyrek görmesinin incident response etkisini tartış.

### Proje fikri
`otel-sampling-lab`: üç servisli demo kur; normal, slow ve error trace üret. Collector'da probabilistic ve tail policies karşılaştır; kept traces, collector memory, decision latency ve backend ingest hacmini ölç.

### Failure modes / trade-off / production bağlantısı
Aggressive sampling incident kanıtını silebilir; tail sampler overload/drop yaşayabilir; yanlış routing fragmented trace yaratabilir; high-cardinality attributes maliyeti sampling'e rağmen patlatabilir. Production'da collector queue/memory, dropped spans, export failures, kept/dropped trace oranı, decision latency ve telemetry spend izlenir.
