## Paket 1 — Junior → Staff Foundations/Runtime: Compiler Pipeline — Lexer, Parser, AST, IR ve Codegen
**Süre:** 20–30 dk

### Konu anlatımı
Compiler'ı tek bir `source -> machine code` kara kutusu gibi düşünmek mülakatta çabuk duvara çarpar. Daha kullanışlı model, her aşamanın bir representation'ı daha yapılandırılmış veya hedefe daha yakın hale getirdiği pipeline'dır. Lexer karakterleri token'lara ayırır; parser token dizisini grammar'a göre yapısal hale getirir; AST kaynak dilin semantiğine yakın bir ağaçtır; semantic analysis isim/type gibi kuralları doğrular; IR optimizasyon ve target-independent dönüşümler için ara katmandır; backend ise instruction selection, register allocation ve object-code üretimine yaklaşır. Linker ayrı object/library parçalarını semboller üzerinden birleştirir; loader executable/shared objects'i process address space'e yerleştirir.

LLVM'nin resmi Kaleidoscope tutorial'ı bu zinciri lexer → parser/AST → LLVM IR → optimizer/JIT/object code olarak somutlaştırır. Kritik mülakat fikri şudur: **syntax, semantics, optimization ve execution aynı problem değildir.**

### Mental model
```text
source text
   |
   v
 [lexer] ----> tokens
   |
 [parser] ---> AST
   |
 [semantic analysis]
   |
 [IR lowering] ---> LLVM IR / başka IR
   |
 [optimizer] ----> equivalent but cheaper IR
   |
 [backend] ------> object code
   |
 [linker] -------> executable / shared object
   |
 [loader] -------> process memory -> execution

Her ok bir representation boundary'dir; her boundary farklı invariant taşır.
```

### İçeride ne oluyor?
- Lexer `identifier`, `number`, punctuation ve keyword gibi token sınıfları üretir; whitespace/comment çoğunlukla syntax tree'ye taşınmaz.
- Parser grammar'a göre token'lardan yapı kurar. Recursive descent sezgiseldir; expression precedence için precedence climbing/operator-precedence gibi teknikler gerekir.
- AST parse tree'nin birebir kopyası olmak zorunda değildir; sonraki semantic/codegen aşamalarının ihtiyaç duyduğu anlamlı düğümleri taşır.
- Semantic analysis scope/name resolution, type rules ve dilin parser'ın tek başına ifade etmediği invariants'larını kontrol eder.
- IR, source language ile CPU arasında optimization-friendly kontrattır. LLVM tutorial'ında AST LLVM IR'ye lowered edilir.
- Optimization semantiği korumalıdır. Constant folding, dead-code elimination ve inlining gibi dönüşümler performans/binary-size/debuggability trade-off'ları taşır.
- Object code henüz tek başına runnable olmayabilir; unresolved symbols ve relocation kayıtları linker tarafından çözülür.
- Static linking dependency code'unu artifact'a alabilir; dynamic linking shared library kullanımını ve runtime symbol resolution'ı mümkün kılar. ABI uyumu burada kritik hale gelir.

### Yüksek getirili mülakat soruları
1. Lexer ile parser arasındaki fark nedir?
2. AST neden source code'un birebir ağacı değildir?
3. Syntax error ile semantic error'a örnek ver.
4. Mid: IR neden doğrudan AST'den machine code üretmeye tercih edilebilir?
5. Senior: optimization neden debug deneyimini değiştirebilir?
6. Senior: compile error, link error ve runtime loader error'ı ayır.
7. Staff: ABI değişikliği neden source-compatible olduğu halde binary compatibility'yi bozabilir?
8. Staff: JIT ile AOT arasında latency, peak performance, memory ve deployment trade-off'larını tartış.

### Seviyeye göre cevap derinliği
- **Junior:** token, parser, AST ve machine code kavramlarını doğru sıraya koyar.
- **Mid:** semantic analysis, IR, optimizer, object code ve linker rollerini ayırır.
- **Senior:** symbol resolution, relocation, static/dynamic linking, debug/optimization ve JIT/AOT trade-off'larını açıklar.
- **Staff:** ABI, multi-language IR, profile-guided optimization, build/release reproducibility ve production observability etkilerini tartışır.

### Kısa alıştırma
`x = 2 + 3 * 4` ifadesi için yaklaşık token dizisini ve AST'yi çiz. Ardından constant folding sonrası nasıl bir IR beklediğini yaz. `*` ile `+` aynı precedence olsaydı AST nasıl değişebilirdi?

### Proje fikri
`tiny-expr-compiler`: sayılar, değişkenler, `+ - * /` ve parantez destekleyen küçük bir dil yaz. Lexer + recursive-descent parser + AST oluştur; önce AST interpreter ekle, sonra basit stack bytecode'a lower et. Golden tests ile parse tree ve execution sonuçlarını doğrula.

### Failure modes / trade-off / production bağlantısı
Compiler pipeline'ını ezberlenmiş aşamalar olarak bilip representation invariants'larını açıklayamamak; parse error ile type error'ı karıştırmak; linker ve loader'ı aynı şey sanmak; optimization'ın her zaman bedelsiz olduğunu varsaymak tipik hatalardır. Production'da build time, binary size, startup/JIT warmup, crash symbolization, debug-info availability, ABI compatibility ve reproducible-build çıktıları önemlidir.

## Paket 2 — Mid → Principal Testing Engineering: Property-Based Testing, Fuzzing ve Sanitizers
**Süre:** 20–30 dk

### Konu anlatımı
Example-based test belirli girdiler için beklenen çıktıyı doğrular. Property-based testing ise tek tek örneklerden ziyade geniş bir input uzayı üzerinde korunması gereken invariant'ı tanımlar; generator çok sayıda örnek üretir ve başarısız örneği küçültme/shrinking yaklaşımı debugging'i kolaylaştırabilir. Fuzzing de input uzayını otomatik keşfeder fakat özellikle parser, protocol, codec ve native-code yüzeylerinde crash, hang ve sanitizer violation gibi sinyaller üzerinden yeni execution path'leri aramakta güçlüdür.

Bunlar birbirinin alternatifi değildir: unit tests bilinen davranışı, property tests genel invariants'ı, fuzzing beklenmeyen state/input kombinasyonlarını, sanitizers ise memory/undefined-behavior sınıflarını görünür kılar. İyi production mühendisliği bu katmanları risk modeline göre birleştirir.

### Mental model
```text
              known examples
                    |
               unit tests
                    |
        invariants + generators
                    |
            property tests
                    |
 corpus -> coverage-guided fuzzer -> new paths
                    |
           ASan / UBSan / TSan
                    |
        crash + minimal reproducer
                    |
              regression test

Bulunan bug tekrar corpus/regression suite'e beslenir: öğrenen test döngüsü.
```

### İçeride ne oluyor?
- Property, implementation detail yerine invariant ifade eder: `decode(encode(x)) == x`, sort sonrası sıralılık + permutation korunması gibi.
- Generator input domain'ini temsil eder; kötü generator yalnız kolay örnekleri üretip sahte güven yaratabilir.
- Shrinking, failing input'u daha küçük ve açıklanabilir counterexample'a indirgemeyi hedefler.
- Coverage-guided fuzzing mutation'ları yeni control-flow edge'leri keşfetme sinyaline göre seçebilir; seed corpus kalitesi başlangıç verimliliğini etkiler.
- libFuzzer process içinde hedef fonksiyonu tekrar çağırır; hedef deterministik, hızlı ve mümkün olduğunca side-effect kontrollü olmalıdır.
- AddressSanitizer heap/stack/global out-of-bounds ve use-after-free gibi memory bug'larını instrumentation + runtime ile yakalar; resmi Clang dokümanı tipik slowdown'ın yaklaşık 2x olabileceğini belirtir.
- Fuzzer crash'i bulduğunda iş bitmez: reproducer saklanmalı, root cause düzeltilmeli ve regression test/corpus'a eklenmelidir.

### Yüksek getirili mülakat soruları
1. Example-based test ile property-based test farkı nedir?
2. İyi bir property nasıl yazılır? `sort()` için iki invariant söyle.
3. Shrinking neden değerlidir?
4. Mid: coverage-guided fuzzer random input generator'dan nasıl farklıdır?
5. Senior: parser fuzz target'ını nasıl tasarlarsın?
6. Senior: ASan ne tür bug'ları bulur; neden production binary'sinde varsayılan açık tutulmaz?
7. Staff: CI'da 5 dakikalık fuzz budget ile nightly 6 saatlik campaign'i nasıl ayırırsın?
8. Principal: monorepo'da fuzzing ROI'sini hangi risk ve telemetry sinyalleriyle önceliklendirirsin?

### Seviyeye göre cevap derinliği
- **Mid:** property/invariant, generator, seed corpus ve sanitizer kavramlarını ayırır.
- **Senior:** harness determinism, corpus management, crash deduplication, shrinking/minimization ve CI budget tasarlar.
- **Staff:** service/library riskine göre continuous fuzzing, sanitizer matrix ve ownership kurar.
- **Principal:** güvenlik sınırları, exploitability, fleet cost, developer feedback latency ve program-level quality metrics'i dengeler.

### Kısa alıştırma
Bir URL parser için üç property yaz: parse/serialize round-trip, normalization idempotence ve malformed input'ta bounded execution. Sonra fuzzer'ın hangi byte/string mutation'larıyla edge case bulabileceğini düşün. Bir crash için minimal reproducer'ı regression test'e nasıl dönüştüreceğini yaz.

### Proje fikri
`parser-fuzz-lab`: küçük bir binary message parser yaz; libFuzzer harness ekle, ASan/UBSan ile derle. Seed corpus oluştur, kasıtlı length bug'ı ekle, crash'i bul/minimize et, fix sonrası reproducer'ı regression corpus'a al. İkinci aşamada aynı parser için property-based round-trip tests ekle.

### Failure modes / trade-off / production bağlantısı
`100% coverage = doğru sistem` sanmak; oracle/property tanımlamadan rastgele input üretmek; fuzzer target'ında network/database gibi yavaş nondeterministic dependency tutmak; crash corpus'unu kaybetmek; sanitizer overhead'ini production workload'uyla karıştırmak tipik hatalardır. Production bağlantısı özellikle untrusted-input parser'ları, image/media codecs, serialization, protocol gateways ve native extensions'ta güçlüdür. İzlenecek sinyaller: unique crashes, time-to-reproduce, coverage growth, flaky harness rate, sanitizer findings, fix SLA ve tekrar eden bug sınıflarıdır.
