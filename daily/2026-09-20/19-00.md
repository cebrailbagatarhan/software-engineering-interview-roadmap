## Paket 1 — Junior → Staff Foundations: Filesystem Internals — inode, page cache, writeback, fsync ve crash consistency
**Süre:** 20–30 dk

### Konu anlatımı
Dosya sistemi yalnız `open/read/write` API'si değildir. Kullanıcı uzayındaki file descriptor, kerneldeki open-file state üzerinden VFS nesnelerine; oradan inode/dentry ve filesystem implementation'ına bağlanır. Buffered I/O'da okuma/yazma çoğu zaman doğrudan diske gitmez: file data page cache/folio'larda tutulur. Write dirty cache state üretir; writeback bunu daha sonra storage'a taşır. Bu yüzden `write()` başarılı oldu ile `power loss sonrası veri kalıcı` aynı garanti değildir.

`fsync()` durability boundary kurmak için kritik primitive'dir; fakat doğru crash-consistent update çoğu zaman temporary file, file fsync, atomic rename ve gerektiğinde directory fsync gibi ordering düşüncesi ister. Storage device'ın volatile write-back cache'i de zincirin parçasıdır; kernel/filesystem gerektiğinde flush/FUA ile kalıcılık talep eder.

### Mental model
```text
process
  |
 fd -> open file -> dentry -> inode
                         |
                      address_space
                         |
                    page/folio cache
                    |            |
                 clean         dirty
                                  |
                              writeback
                                  |
                           filesystem/journal
                                  |
                         block layer + cache
                                  |
                         non-volatile media

write() success != durable
fsync() = persistence boundary talebi
```

### İçeride ne oluyor?
- **dentry** pathname component'lerini isim çözümleme/cache tarafında temsil eder; **inode** dosyanın identity/metadata ve operations tarafını temsil eder.
- VFS farklı filesystem implementation'larını ortak object/operation modeli altında toplar.
- Linux `address_space` file-backed page/folio cache'i ve Dirty/Writeback state'ini yönetir.
- Buffered read page cache hit olabilir; miss'te filesystem I/O başlatır ve readahead ardışık erişimi ucuzlatabilir.
- Buffered write cache'i dirty yapıp syscall'ı storage persistence'dan önce tamamlayabilir; background writeback dirty folio'ları daha sonra gönderir.
- `mmap` file-backed sayfaları process address space'e bağlar; değişiklikler yine dirty/writeback yaşam döngüsüne girebilir.
- Journaling metadata/data ordering ve recovery'yi kolaylaştırabilir ama `write()` çağrısını otomatik olarak durable transaction yapmaz.
- Device write-back cache I/O completion'ı non-volatile media'ya gerçek yazımdan önce bildirebilir; durability operation'larında flush/FUA gerekir.

### Yüksek getirili mülakat soruları
1. inode ile file descriptor aynı şey midir?
2. Page cache neden vardır?
3. `write()` döndüğünde veri mutlaka diskte midir?
4. Mid: buffered I/O ile direct I/O trade-off'u nedir?
5. Senior: `fsync()` neden latency spike üretebilir?
6. Senior: crash-safe config-file replacement nasıl tasarlanır?
7. Staff: page cache, application cache ve database buffer pool birlikteyken double caching ne zaman problem olur?
8. Staff: power-loss durability ile replication durability neden farklı failure domain'leridir?

### Seviyeye göre cevap derinliği
- **Junior:** fd, inode, directory ve page cache rollerini ayırır.
- **Mid:** dirty page, writeback, readahead, mmap ve fsync'i açıklar.
- **Senior:** journaling, ordering, atomic rename, device cache ve crash windows'u tartışır.
- **Staff:** DB/storage engine I/O policy, direct I/O, observability, tail latency ve failure-domain tasarımını bağlar.

### Kısa alıştırma
Bir servis `config.json.tmp` yazıp `rename()` ile `config.json` yapıyor. Güç kaybı üç farklı noktada olursa hangi sonuçlar görülebilir? `fsync(file)` ve directory durability adımlarını mental timeline'a yerleştir.

### Proje fikri
`durable-kv-lab`: append-only küçük KV store yaz. Her record'a checksum ekle; buffered write, fsync-per-write ve group-commit modlarını karşılaştır. Process kill/crash simulation sonrası recovery yap; throughput ile p99 latency'yi ölç.

### Failure modes / trade-off / production bağlantısı
`write()==len` sonucunu durability sanmak; page cache ile storage cache'i aynı katman sanmak; her write'ta fsync ile throughput'u çökertmek; hiç fsync etmeyip kabul edilemez data-loss window yaratmak; rename atomicity ile persistence'ı karıştırmak tipik hatalardır. Production'da dirty/writeback pressure, fsync latency, I/O queue latency, disk utilization, ENOSPC, inode exhaustion ve recovery süresi izlenir.

## Paket 2 — Mid → Principal Cloud/SRE: Linux CPU Scheduling — CFS'ten EEVDF'ye fairness, latency ve CPU isolation
**Süre:** 20–30 dk

### Konu anlatımı
Scheduler'ın işi sadece runnable process'lerden birini seçmek değildir; fairness, latency, throughput, priority, topology ve preemption arasında sürekli karar verir. Klasik CFS mental modeli ideal bir multitasking CPU'yu yaklaşıklar ve task'ların virtual runtime'ını izler. Güncel Linux dokümantasyonu CFS'in yerini giderek EEVDF'ye bıraktığını belirtir. EEVDF, task'ın hak ettiği CPU payına göre **lag** hesaplar; eligible task'lar arasında en erken **virtual deadline**'ı seçer. Böylece fairness korunurken kısa slice isteyen latency-sensitive işler daha iyi ifade edilebilir.

### Mental model
```text
 runnable tasks
      |
      v
  fairness accounting
   vruntime / lag
      |
 eligible? -------- no -> wait
      |
     yes
      v
 virtual deadline
      |
 earliest deadline wins
      |
      CPU
      |
 preemption / sleep / wakeup -> yeniden değerlendir

CFS sezgisi: kim ideal CPU payının gerisinde?
EEVDF: kim eligible ve virtual deadline'ı en erken?
```

### İçeride ne oluyor?
- Runnable task CPU için adaydır; sleeping/blocked task CPU tüketmez ve wakeup sonrası yeniden yarışa girer.
- CFS virtual runtime ile ideal fair CPU modeline yaklaşır; nice/weight CPU payını etkiler.
- EEVDF lag ile task'ın adil payına göre geride/ileride olmasını temsil eder. Pozitif lag task'a CPU borcu olduğu sezgisidir.
- Eligible task'lar arasında virtual deadline en erken olan seçilir; kısa requested slice latency-sensitive workload'lara yardımcı olabilir.
- Preemption responsiveness sağlar ama context-switch/cache maliyeti yaratır.
- CPU affinity/cpuset placement'ı sınırlar; yanlış pinning load imbalance veya hot CPU yaratabilir.
- Container CPU request/limit kavramları scheduler'ın gerçek CPU zamanı, cgroup accounting/throttling ve node contention ile birlikte düşünülmelidir.

### Yüksek getirili mülakat soruları
1. Runnable ile running process farkı nedir?
2. Context switch neden bedava değildir?
3. Nice değeri neyi etkiler?
4. Mid: CPU-bound ve I/O-bound task scheduler açısından nasıl farklı görünür?
5. Senior: CFS virtual runtime mental modelini açıkla.
6. Senior: EEVDF'de lag ve virtual deadline ne işe yarar?
7. Staff: CPU affinity hangi durumda latency'yi iyileştirir, hangi durumda kötüleştirir?
8. Principal: multi-tenant Kubernetes node'unda noisy-neighbor CPU problemi için scheduler, cgroup ve observability katmanlarını nasıl ayırırsın?

### Seviyeye göre cevap derinliği
- **Mid:** process state, runnable queue, preemption, priority ve context switch.
- **Senior:** vruntime/fairness, EEVDF eligibility/deadline, cache locality ve affinity.
- **Staff:** NUMA/topology, cgroup CPU control, isolation, tail latency ve workload classes.
- **Principal:** fleet utilization, SLO, tenancy, capacity economics ve scheduler policy governance.

### Kısa alıştırma
Aynı CPU'da A ve B CPU-bound, C ise her 5 ms'de kısa I/O sonrası uyanıyor. Fairness ile interactive latency arasında nasıl bir gerilim oluşur? C'nin slice'ını küçültmek throughput/context-switch açısından neye mal olabilir?

### Proje fikri
`scheduler-observer`: Linux'ta CPU-bound ve sleep/wakeup ağırlıklı üç workload çalıştır. `perf`, `/proc`, cgroup metrics ve scheduler tracepoint'leriyle context switches, migrations, CPU time ve latency dağılımını karşılaştır. Affinity açık/kapalı deney yap.

### Failure modes / trade-off / production bağlantısı
CPU utilization yüksek diye scheduler bug'ı varsaymak; load average ile CPU utilization'ı eşitlemek; affinity'yi her durumda optimizasyon sanmak; container CPU limit kaynaklı throttling'i application latency'sinden ayırmamak; yalnız average latency ölçmek tipik hatalardır. Production'da run-queue pressure, CPU utilization, throttled time, context switches, migrations, steal time ve p95/p99 request latency birlikte okunmalıdır.
