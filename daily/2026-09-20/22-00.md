## Paket 1 — Mid → Principal Foundations/SRE: Linux Fair Scheduling — CFS, EEVDF, CPU Isolation ve sched_ext
**Süre:** 20–30 dk

### Konu anlatımı
CPU scheduler'ın görevi yalnız runnable task'lardan birini seçmek değildir; fairness, latency, throughput, cache locality, topology ve isolation arasında politika uygular. CFS, ideal ve kusursuz bir multitasking CPU'yu `vruntime` ile yaklaşıklar. Güncel Linux dokümantasyonunda CFS'in EEVDF'ye yer açtığı belirtilir. EEVDF her task için adil CPU payına göre **lag** hesaplar; lag >= 0 olan eligible task'lar arasından virtual deadline'ı en erken olanı seçer. Böylece kısa slice isteyen latency-sensitive task'ların responsiveness'i fairness modeli içinde ifade edilebilir.

`sched_ext` ise BPF programlarıyla scheduler policy tanımlamaya izin verir. Kritik production özelliği güvenli fallback'tir: BPF scheduler error üretirse veya runnable task stall olursa kernel varsayılan scheduling davranışını geri yükleyebilir.

```text
runnable tasks
      |
fairness accounting
 vruntime / lag
      |
 eligible? ---- no ---> wait
      |
     yes
      v
virtual deadline
      |
earliest deadline
      |
     CPU
      |
preempt / sleep / wakeup

sched_ext: workload -> BPF policy -> dispatch -> CPU
                         | error/stall
                         +-----------> default scheduler
```

### İçeride ne oluyor?
- Runnable task CPU adayıdır; blocked/sleeping task değildir.
- CFS `vruntime` ile task'ın ideal fair CPU'daki ilerlemesini yaklaşıklar; nice/weight payı etkiler.
- EEVDF'de pozitif lag task'a CPU zamanı borçlu olunduğu sezgisidir; eligible task'lar virtual deadline ile seçilir.
- Preemption responsiveness sağlar fakat context-switch ve cache/TLB locality maliyeti yaratır.
- CPU affinity/cpuset placement'ı sınırlar; locality kazanımı load-balancing kaybına dönüşebilir.
- Container CPU throttling ile host scheduler contention aynı problem değildir; telemetry ayrı okunmalıdır.
- `sched_ext` arbitrary BPF scheduling policy'lerine izin verir; production rollout'ta fallback ve starvation detection temel güvenlik mekanizmalarıdır.

### Yüksek getirili mülakat soruları
1. Runnable ile running arasındaki fark nedir?
2. Context switch neden bedava değildir?
3. CFS `vruntime` neyi yaklaşıklar?
4. EEVDF'de lag, eligibility ve virtual deadline ilişkisini açıkla.
5. CPU affinity ne zaman tail latency'yi iyileştirir, ne zaman kapasiteyi bozar?
6. Kubernetes pod CPU throttling ile host run-queue contention nasıl ayrılır?
7. Staff: programmable scheduler rollout'unda starvation, fallback ve blast radius nasıl yönetilir?
8. Principal: multi-tenant fleet'te fairness, SLO ve utilization arasında policy nasıl kurulur?

### Seviyeye göre cevap derinliği
- **Mid:** process state, run queue, preemption, priority, context switch.
- **Senior:** vruntime, EEVDF lag/deadline, locality, affinity ve cgroup throttling.
- **Staff:** NUMA/topology, isolation, sched_ext rollout/fallback ve observability.
- **Principal:** workload classes, fleet utilization, tenancy ve policy governance.

### Kısa alıştırma
A ve B sürekli CPU-bound; C her 5 ms'de uyanıp 500 µs CPU istiyor. Fair-share ile C'nin responsiveness hedefi arasındaki gerilimi çiz. C için kısa slice, dedicated CPU ve programmable scheduler seçeneklerini karşılaştır.

### Proje fikri
`scheduler-policy-lab`: CPU-bound ve bursty workload'larda context switches, migrations, throttled time ve p99 latency ölç. Affinity/cpuset varyantlarını karşılaştır; uygun test hostunda `sched_ext` örnek scheduler'ıyla fallback davranışını doğrula.

### Failure modes / trade-off / production bağlantısı
CPU utilization ile run-queue pressure'ı eşitlemek, load average'ı doğrudan CPU saturation sanmak, affinity'yi evrensel optimizasyon kabul etmek ve custom scheduler'da starvation/fallback test etmemek yaygın hatalardır. Production'da utilization, runnable pressure, throttled time, context switches, migrations, steal time ve p95/p99 latency birlikte okunmalıdır.

## Paket 2 — Junior → Staff Foundations/Backend: Heap Allocators, Fragmentation, Arenas ve Memory Debugging
**Süre:** 20–30 dk

### Konu anlatımı
`malloc(128)` kernel'den tam 128 byte istemek değildir. Userspace allocator daha büyük memory region'larını işletim sisteminden alır, bunları size class/chunk'lara böler, metadata tutar ve allocation/free isteklerini mümkün olduğunca syscall yapmadan karşılar. Hız, memory footprint, fragmentation ve concurrency arasında sürekli trade-off vardır.

**Internal fragmentation**, verilen block'un application'ın istediğinden büyük olmasıdır. **External fragmentation**, toplam free memory yeterli olsa bile uygun contiguous block bulunamamasıdır. Thread-local cache/arena tasarımları lock contention'ı azaltabilir fakat idle thread/arena'larda memory'nin tutulmasına ve RSS'in beklenenden yüksek kalmasına yol açabilir.

```text
application
 malloc/free
    |
thread cache / size classes
    |
 arena / free lists
    |
large mappings / heap regions
    |
 virtual memory
    |
 kernel pages

fast reuse <----> retained memory
low contention <----> more arenas/caches
compact memory <----> allocation CPU cost
```

### İçeride ne oluyor?
- Allocator request'i alignment ve metadata nedeniyle daha büyük bir usable block'a yuvarlayabilir.
- Size classes hızlı lookup/reuse sağlar fakat internal fragmentation yaratabilir.
- Free-list/bin yapıları boş block'ları yeniden kullanım için tutar.
- Coalescing komşu free block'ları birleştirerek external fragmentation'ı azaltabilir; ek CPU/metadata maliyeti vardır.
- Per-thread cache ve multiple arenas lock contention'ı düşürür; memory retention yükseltebilir.
- Büyük allocations ayrı `mmap` benzeri mappings ile ele alınabilir; küçük allocations pooled regions'dan gelebilir.
- Application leak ile allocator retention aynı şey değildir: reachable/owned memory, free-but-retained pages ve kernel'e geri verilmiş pages ayrılmalıdır.
- ASan out-of-bounds/use-after-free gibi memory-safety bug'larını; LeakSanitizer unreachable leak'leri test ortamında yakalamaya yardım eder.

### Yüksek getirili mülakat soruları
1. Stack ve heap allocation farkı nedir?
2. `free()` çağrısı memory'nin hemen OS'e döndüğü anlamına gelir mi?
3. Internal ve external fragmentation farkı nedir?
4. Size classes neden kullanılır?
5. Thread cache/arena concurrency'yi nasıl iyileştirir; RSS'i nasıl kötüleştirebilir?
6. Senior: memory leak ile allocator fragmentation/retention nasıl ayrılır?
7. Staff: latency-sensitive service'te allocator seçimi ve tuning nasıl benchmark edilir?

### Seviyeye göre cevap derinliği
- **Junior:** stack/heap, allocation/free ve leak kavramları.
- **Mid:** size classes, free lists, fragmentation ve syscall amortization.
- **Senior:** arenas, thread caches, RSS vs live heap, mmap/return-to-OS davranışı ve profiling.
- **Staff:** allocator/workload matching, fleet memory economics, tail latency ve safe rollout.

### Kısa alıştırma
10 milyon kez 24 B, 40 B ve 4 KiB allocation yapan üç workload düşün. Her biri için size-class rounding, locality ve fragmentation riskini tahmin et. Ardından allocation/free sırasını değiştirerek external fragmentation'ın nasıl değişebileceğini çiz.

### Proje fikri
`allocator-lab`: fixed-size pool + basit segregated free-list allocator geliştir. System allocator ile throughput, p99 allocation latency, peak RSS ve fragmentation proxy'sini karşılaştır. Ayrı bir buggy target'ı ASan/LSan ile çalıştırıp use-after-free ve leak raporlarını CI artifact'ı yap.

### Failure modes / trade-off / production bağlantısı
RSS artışını otomatik leak saymak, yalnız heap profiler'a bakıp native/runtime memory'yi unutmak, allocator benchmark'ını gerçek allocation-size/lifetime dağılımından koparmak ve sanitizer runtime'ını production binary'ye taşımak hatalıdır. Production'da RSS, anonymous mapped memory, allocation rate, live heap, GC/runtime memory, page faults, OOM kills ve p99 latency birlikte değerlendirilmelidir.
