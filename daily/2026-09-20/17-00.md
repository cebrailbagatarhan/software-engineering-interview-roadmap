## Paket 1 — Mid → Staff Backend/Runtime: Python 3.15 Explicit Lazy Imports (PEP 810)
**Süre:** 20–30 dk

### Konu anlatımı
Python import'u normalde modül gövdesini ilk import anında çalıştırır; büyük CLI, plugin veya server uygulamalarında kullanılmayan ağır dependency'ler startup süresini ve memory footprint'i artırabilir. Python 3.15'in PEP 810 explicit lazy imports özelliği, geliştiricinin belirli import'ları tembel değerlendirmesine izin vererek maliyeti gerçekten ihtiyaç anına ertelemeyi hedefler. Buradaki kritik fikir `lazy = free` değildir: latency startup'tan first-use noktasına taşınır; import-time side effect'leri ve hata zamanı da değişebilir.

Python 3.15.0rc2, 1 Eylül 2026'da yayımlandı; final 3.15.0 1 Ekim 2026 için planlıdır. RC production baseline değil, migration/test hedefidir.

### Mental model
```text
Eager: process start -> import A -> load heavy B -> ready
Lazy : process start -> register lazy B -> ready
                               |
                         first B access
                               v
                         load/evaluate B

Maliyet yok olmaz; startup critical path'inden first-use critical path'ine taşınır.
```

### İçeride ne oluyor?
- Import graph uygulamanın startup dependency graph'idir; eager edge'ler initialization critical path'ine girer.
- Explicit lazy import, dependency'nin çözüm/evaluation maliyetini kullanım anına erteleyebilir.
- Import-time side effect'e güvenen registration/plugin kodu davranış değiştirebilir; bu yüzden migration yalnız benchmark değildir, semantic audit de gerektirir.
- First-use sırasında import failure artık startup'ta değil request/feature path'inde görülebilir.
- Lazy import memory'yi ancak dependency hiç kullanılmazsa veya geç kullanılırsa anlamlı azaltabilir.
- Python 3.15 RC2 ABI açısından final seriye hazırlanma noktasıdır; resmi release sayfası finali 1 Ekim 2026 olarak planlıyor.

### Yüksek getirili mülakat soruları
1. Python import'u neden startup maliyeti yaratır?
2. Lazy import performansı nasıl iyileştirir; maliyet nereye gider?
3. Import-time side effect neden risklidir?
4. Senior: CLI startup'ını optimize ederken hangi import'ları lazy yaparsın?
5. Staff: server'da first-request latency spike'ını nasıl önlersin?
6. Staff: migration rollout'unda correctness ve performance guardrail'leri neler olur?

### Seviyeye göre cevap derinliği
- **Mid:** import cache, module evaluation, startup ve first-use farkını açıklar.
- **Senior:** side effects, error timing, cold path ve benchmark tasarımını bağlar.
- **Staff:** fleet rollout, preload/warmup, observability ve dependency governance tasarlar.

### Kısa alıştırma
CLI startup'ı 500 ms: A=40, B=250, C=120, diğer=90 ms. Komutların yalnız %10'u B'yi, %5'i C'yi kullanıyor. B ve C lazy olursa ideal startup alt sınırını hesapla; ardından B kullanan ilk komutun latency maliyetini yaz. Average yerine p95/p99 neden izlenmeli?

### Proje fikri
`lazy-import-profiler`: küçük CLI/API uygulamasında eager/lazy varyantları karşılaştır; startup, RSS, first-use p50/p99 ve import failures ölç. Import-time side-effect içeren örnek plugin ekleyip regression test yaz.

### Failure modes / trade-off / production bağlantısı
Her import'u refleks olarak lazy yapmak, startup benchmark'ı kazanırken first-request SLO'yu bozmak, import-time registration'ı unutmak ve RC'yi production baseline sanmak tipik hatalardır. Production'da process startup, cold-request p95/p99, RSS, import error rate, warmup süresi ve dependency/version kırılımı izlenmelidir.

## Paket 2 — Mid → Principal Networking/Cybersecurity: HTTP/3 Inspection, QUIC/UDP & Policy Enforcement
**Süre:** 20–30 dk

### Konu anlatımı
HTTP/3, HTTP semantiğini QUIC üzerinde taşır; QUIC ise TCP yerine UDP kullanır ve TLS 1.3'ü protokole entegre eder. Bu, TCP/TLS odaklı secure web gateway ve proxy mimarileri için görünürlük problemi yaratır: gateway yalnız TCP proxy'liyorsa HTTP/3 akışı HTTP inspection katmanını bypass edebilir. Cloudflare'ın 22 Nisan 2026 tarihli resmi dokümanı HTTP/3 inspection için UDP proxy'nin ve HTTPS içeriğini incelemek için TLS decryption'ın etkinleştirilmesi gerektiğini açıkça belirtiyor.

### Mental model
```text
client
  | HTTP/1.1,2 -> TCP -> gateway TCP proxy -> HTTP policy
  |
  + HTTP/3 ----> QUIC/UDP -> [UDP proxy?]
                              | no  -> HTTP inspection bypass
                              | yes -> TLS decrypt -> HTTP policy

Network policy UDP akışını görebilir; application-layer policy için H3-aware inspection gerekir.
```

### İçeride ne oluyor?
- HTTP/3 QUIC/UDP üzerinde çalışır; klasik TCP intercept path otomatik olarak H3'ü kapsamaz.
- Network-layer policy UDP tuple/flow'u görebilir fakat URL/header gibi HTTP semantiği için application-layer inspection gerekir.
- Managed inspection'da client trust store'a gateway certificate deployment ve TLS decryption ayrı bir güvenlik/mahremiyet kararıdır.
- UDP proxy kapalıysa H3 trafik HTTP inspection'ı atlayabilir; güvenlik varsayımı protocol coverage ile doğrulanmalıdır.
- QUIC connection migration ve multiplexing, TCP connection mental modelini birebir taşımayı riskli kılar.
- Fallback davranışı önemlidir: H3 engellendiğinde client HTTP/2'ye düşebilir; policy consistency test edilmelidir.

### Yüksek getirili mülakat soruları
1. HTTP/3 neden TCP proxy'den geçmeyebilir?
2. Network policy ile HTTP policy arasındaki görünürlük farkı nedir?
3. TLS decryption hangi güvenlik ve privacy risklerini getirir?
4. Senior: H3 kapalı/açık client fallback'ını nasıl test edersin?
5. Staff: mixed HTTP/2+HTTP/3 fleet'te policy parity nasıl kanıtlanır?
6. Principal: encrypted transport evolution karşısında inspection, privacy ve endpoint security dengesini nasıl kurarsın?

### Seviyeye göre cevap derinliği
- **Mid:** TCP/UDP, QUIC, TLS 1.3 ve HTTP/3 katmanlarını ayırır.
- **Senior:** proxy path, fallback, certificate trust ve bypass riskini açıklar.
- **Staff:** protocol coverage, rollout, telemetry ve policy parity testleri tasarlar.
- **Principal:** privacy, regulatory boundary, endpoint-vs-network control ve encrypted-traffic strategy kurar.

### Kısa alıştırma
Gateway yalnız TCP proxy'liyor. Trafiğin %35'i H3/UDP, %65'i H2/TCP. HTTP-layer DLP yalnız proxy path'te çalışıyorsa teorik inspection coverage nedir? UDP proxy açıldığında coverage artar ama latency ve failure surface neden de artabilir?

### Proje fikri
`h3-policy-lab`: HTTP/2 ve HTTP/3 endpoint kur; UDP allowed/blocked/proxied varyantlarında protocol negotiation, fallback, latency ve policy decision log'larını karşılaştır. Aynı URL policy'sinin H2/H3 parity testini otomatikleştir.

### Failure modes / trade-off / production bağlantısı
`443 = HTTPS = TCP` varsayımı, yalnız firewall allow/deny ile application inspection yaptığını sanmak, TLS decryption'ın privacy/compliance etkisini modellememek, H3→H2 fallback'ını ölçmemek ve UDP proxy rollout'unu capacity test etmemek tipik hatalardır. Production'da H3 adoption, UDP proxy errors, fallback rate, handshake latency, policy match parity, decrypt failures ve bypass indicators izlenmelidir.
