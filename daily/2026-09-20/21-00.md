## Paket 1 — Junior → Staff Foundations/Backend: ELF, ABI, Linker ve Dynamic Loader
**Süre:** 20–30 dk

### Konu anlatımı
Kaynak kodun executable'a dönüşmesi compiler ile bitmez. Compiler/assembler object file üretir; **linker** symbol reference'larını çözer, section'ları yerleştirir ve executable/shared object üretir. Linux'ta yaygın ELF executable, hangi runtime loader'ın kullanılacağını `.interp` üzerinden belirtebilir. Program başladığında kernel image'ı map eder; dynamic linker/loader gereken shared libraries'i bulur, map eder, relocation/symbol resolution işlerini tamamlar ve kontrolü programa verir. **ABI**, ayrı derlenmiş bileşenlerin binary seviyede anlaşma sözleşmesidir: calling convention, register/stack kullanımı, object format, symbol/interface ve platform kuralları bunun parçalarıdır.

```text
source
  |
compiler / assembler
  v
object files (.o) ----+ shared libs (.so)
                      |
                    linker
                      v
                 ELF executable
                      |
                 execve / kernel
                      |
                .interp -> ld.so
                      |
        map DSOs + relocate + resolve symbols
                      |
                    _start
                      |
                    main

API = source-level contract
ABI = binary-level contract
```

### İçeride ne oluyor?
- Object file code/data sections, symbols ve unresolved references taşıyabilir.
- Static link gerekli code'u executable'a dahil eder; dynamic linking shared objects'i runtime'da bağlar.
- ELF `.interp` dynamic loader yolunu gösterebilir; loader dependency'leri arayıp map eder.
- Relocation, link/load address belli olduğunda address-dependent yerleri düzeltir.
- Symbol resolution aynı isimli reference'ın hangi definition'a bağlanacağını belirler.
- Shared-library search path ve runtime environment davranışı correctness kadar security açısından da önemlidir.
- API compatibility source'un yeniden derlenebilmesiyle; ABI compatibility mevcut binary'nin yeniden derlenmeden çalışabilmesiyle ilgilidir.
- Startup latency dependency sayısı, relocation/symbol work ve storage/cache durumundan etkilenebilir.

### Yüksek getirili mülakat soruları
1. Compiler ile linker farkı nedir?
2. Static ve dynamic linking trade-off'ları nelerdir?
3. ABI ile API arasındaki fark nedir?
4. Mid: relocation neden gerekir?
5. Senior: shared-library version değişimi hangi durumda binary'yi kırar?
6. Senior: loader library'yi nasıl bulur; search path neden security boundary olabilir?
7. Staff: plugin architecture'da ABI stability, rollout ve observability nasıl tasarlanır?

### Seviyeye göre cevap derinliği
- **Junior:** source → object → link → executable zinciri; static/dynamic ayrımı.
- **Mid:** ELF sections/segments, symbols, relocations ve loader.
- **Senior:** ABI compatibility, search path, startup cost ve symbol/versioning failure modes.
- **Staff:** plugin/runtime platformu, compatibility policy, supply-chain risk ve rollout governance.

### Kısa alıştırma
İki C dosyası oluştur: biri `add()` tanımlasın, diğeri çağırsın. Ayrı `.o` üret; `nm`, `readelf -h/-S/-s`, `ldd` ve `readelf -l` ile unresolved/resolved symbol, ELF interpreter ve shared dependencies'i incele. Aynı küçük programın static/dynamic binary boyutlarını karşılaştır.

### Proje fikri
`elf-inspector`: ELF header, program headers, dynamic dependencies ve exported/imported symbols'i özetleyen küçük CLI geliştir. Sonra iki shared-library version'ı üretip ABI-compatible ve ABI-breaking değişiklikleri test eden CI check ekle.

### Failure modes / trade-off / production bağlantısı
Library path hijacking, missing/incompatible `.so`, architecture mismatch, symbol/version uyuşmazlığı ve aşırı dynamic dependency startup failure/latency yaratabilir. Static linking deployment'ı basitleştirebilir ama binary size, patch distribution ve duplication maliyeti yaratır. Production'da startup failure, loader error, cold-start latency, deployed library versions ve crash signatures izlenir.

- GNU Binutils — ld: https://sourceware.org/binutils/docs/ld/
- System V ABI / ELF gABI: https://refspecs.linuxfoundation.org/elf/gabi4+/contents.html

## Paket 2 — Mid → Principal Testing/Distributed Systems: Consumer-Driven Contract Testing
**Süre:** 20–30 dk

### Konu anlatımı
Microservice test stratejisinde unit test tek servisin mantığını, end-to-end test bütün zinciri sınar; aradaki kritik boşluk servislerin **birbirlerinden gerçekten beklediği mesaj sözleşmesidir**. Consumer-driven contract testing'de consumer kendi kullandığı request/response davranışını executable örneklerle tanımlar; contract artifact yayınlanır ve provider CI bu contract'ı kendi implementation'ına karşı doğrular. Bu, bütün ortamı ayağa kaldırmadan interface compatibility sinyali üretir. Contract test functional correctness'in veya E2E'nin yerine geçmez; entegrasyon sınırındaki compatibility riskini hedefler.

```text
Consumer CI
real API client -> mock provider -> contract artifact
                                  |
                                  v
                            contract broker
                                  |
                                  v
Provider CI              replay interactions
provider state --------> real provider
                                  |
                             verification
                                  |
                     compatible? deploy gate

unit <---- contract ----> integration/E2E
fast/local               broad/expensive
```

### İçeride ne oluyor?
- Consumer testi gerçek API client kodunu mock provider'a karşı çalıştırıp kullandığı interaction'ları contract'a yazar.
- Provider verification contract request'lerini provider'a replay edip beklenen response shape/semantics'i kontrol eder.
- Provider state deterministic fixture/setup sağlar; external dependencies mümkün olduğunca izole edilir.
- Schema validation ile consumer-driven contract aynı değildir: schema tüm izin verilen yüzeyi, CDC ise gerçek consumer beklentilerini örnekler üzerinden ifade eder.
- Contract version + consumer/provider version metadata deploy compatibility graph'i oluşturabilir.
- Aşırı strict matcher gereksiz coupling ve brittle tests yaratır; yalnız consumer'ın gerçekten bağımlı olduğu alanlar doğrulanmalıdır.
- Async messaging'de producer/consumer terimleri mesajın üretiminden çok interaction contract'ının taraflarını dikkatli modellemeyi gerektirir.

### Yüksek getirili mülakat soruları
1. Unit, contract, integration ve E2E testleri hangi farklı riski yakalar?
2. Consumer-driven contract neden yalnız OpenAPI schema validation değildir?
3. Mid: provider verification nasıl çalışır?
4. Senior: provider state neden gerekir ve flakiness nasıl azaltılır?
5. Senior: mobile client gibi uzun yaşayan consumer versions nasıl korunur?
6. Staff: onlarca serviste contract broker/deploy gate nasıl ölçeklenir?
7. Principal: independent deployability ile compatibility governance arasında denge nasıl kurulur?

### Seviyeye göre cevap derinliği
- **Mid:** consumer/provider, contract artifact ve verification akışı.
- **Senior:** states, matchers, versioning, async messaging ve false confidence sınırları.
- **Staff:** CI/CD gates, broker topology, backward compatibility ve ownership.
- **Principal:** organization-wide API evolution policy, deployment graph, platform cost ve developer velocity.

### Kısa alıştırma
`orders-ui -> orders-api` için consumer'ın yalnız `id`, `status`, `total` kullandığını varsay. Provider yeni `warehouseId` eklesin, `total` tipini number'dan string'e değiştirsin ve `status` değerlerinden birini yeniden adlandırsın. Hangi değişikliklerin consumer contract'ını kırması gerektiğini gerekçelendir.

### Proje fikri
`contract-ci-lab`: consumer + provider iki küçük servis kur. Consumer contract üretip broker/artifact store'a yayınlasın; provider CI verify etsin. Compatible additive change ve breaking field/type change senaryolarında deploy gate davranışını göster.

### Failure modes / trade-off / production bağlantısı
Contract'ı implementation detail'e aşırı bağlamak testleri brittle yapar; sadece happy-path interaction false confidence üretir; stale contract/deploy metadata yanlış compatibility sinyali verir. Contract tests business correctness, auth/network policy veya gerçek infrastructure failure'larını tek başına doğrulamaz. Production'da incompatible deploy rollback'leri, API error-rate, schema/version adoption, contract verification failures ve E2E incident'ları birlikte izlenir.
