## Paket 1 — Senior Databases: Deadlock, Lock Ordering ve Contention
**Süre:** 20–30 dk

### Konu anlatımı
Transaction concurrency yalnız isolation seviyesi değildir; aynı kaynakları farklı sırayla kilitleyen işlemler cycle oluşturabilir. T1 A'yı tutup B'yi beklerken T2 B'yi tutup A'yı bekliyorsa ilerleme yoktur. PostgreSQL deadlock'u algılar ve transaction'lardan birini abort ederek cycle'ı kırar. Uygulama bunu beklenen bir concurrency failure olarak ele almalı; transaction kısa tutulmalı ve ortak lock ordering tercih edilmelidir.

Row lock beklemesi her zaman deadlock değildir. Contention tek yönlü bekleme olabilir; deadlock için wait-for graph'ta cycle gerekir. Production debugging'de lock holder/waiter, transaction yaşı, query shape ve retry davranışı birlikte incelenir.

### Mental model
```text
T1: lock(A) ---- waits for B
      ^              |
      |              v
T2: waits for A ---- lock(B)

wait-for graph: T1 -> T2 -> T1 = cycle
```

### Yüksek getirili soru kümeleri
- Lock wait ile deadlock farkı nedir?
- Consistent lock ordering deadlock riskini neden azaltır?
- Deadlock victim retry edilirken nelere dikkat edilir?
- Uzun transaction contention ve vacuum/operasyon maliyetini nasıl etkiler?
- `SELECT ... FOR UPDATE` ne zaman gerekir, ne zaman gereksiz serialization üretir?

### Seviye beklentisi
Mid lock/wait/deadlock ayrımını yapar. Senior transaction boundary, lock ordering, retry ve observability konuşur. Staff hotspot schema, admission control ve service-level contention politikasını tasarlar.

### Kısa alıştırma
İki hesap arasında transfer yapan iki concurrent transaction için ters lock sırasıyla deadlock senaryosu çiz; sonra hesapları ID sırasıyla kilitleyen tasarımı yaz.

### Bununla ne yapabiliriz?
`lock-contention-lab`: concurrent transfer workload'u üret; deadlock count, lock wait p95 ve throughput ölç. Habitat-benzeri metadata/control-plane tablolarında aynı resource setini güncelleyen workflow'lar için deterministic ordering uygula.

### Failure modes / trade-off
Uzun transaction, kullanıcı/network çağrısı sırasında lock tutmak, sınırsız retry, hotspot row, lock scope'u gereksiz büyütmek, deadlock'u yalnız DB problemi sanmak.

### Kaynaklar
- PostgreSQL 18 — Explicit Locking: https://www.postgresql.org/docs/18/explicit-locking.html
- PostgreSQL 18 — Lock Monitoring: https://www.postgresql.org/docs/18/view-pg-locks.html

## Paket 2 — Mid/Senior Cloud/SRE: Kubernetes Requests, Limits, QoS ve OOM
**Süre:** 20–30 dk

### Konu anlatımı
Resource request scheduler'a Pod'un yerleşim ihtiyacını anlatır; limit runtime'da tüketimin üst sınırını etkiler. CPU limiti throttling ile uygulanır. Memory limiti farklıdır: kernel memory pressure altında OOM kill ile süreci sonlandırabilir. Bu yüzden CPU saturation ile memory exhaustion aynı failure mode değildir.

Request gerçek ihtiyacın çok üstündeyse cluster utilization düşer; çok altındaysa node contention ve eviction riski artabilir. Limit çok agresifse CPU throttling latency'yi bozabilir veya memory OOM restart loop üretebilir. Capacity planning yalnız ortalamaya göre değil distribution, burst, startup ve sidecar maliyetine göre yapılmalıdır.

### Mental model
```text
Pod spec
  |-- request ---> scheduler placement / contention weight
  |-- CPU limit -> cgroup throttling
  `-- mem limit -> cgroup boundary -> pressure -> OOM kill

request != observed usage != limit
```

### Yüksek getirili soru kümeleri
- Request ile limit farkı nedir?
- CPU limit aşımı neden container'ı öldürmezken memory limit OOM'a gidebilir?
- Requests çok yüksek/düşük olursa ne olur?
- HPA CPU utilization ile request arasında nasıl ilişki kurar?
- Burstable/Guaranteed yaklaşımının node pressure açısından anlamı nedir?

### Seviye beklentisi
Junior request/limit ayrımını bilir. Mid scheduler, throttling ve OOM'u açıklar. Senior rightsizing, autoscaling, p99 latency ve eviction riskini bağlar. Staff namespace quota, multi-tenant fairness ve cost modelini tasarlar.

### Kısa alıştırma
Normalde 300m CPU/400Mi kullanan, burst'te 1.2 CPU/700Mi gören bir API için başlangıç request/limit öner; hangi metriklerle revize edeceğini yaz.

### Bununla ne yapabiliriz?
`rightsizing-lab`: CPU-bound ve memory-bound iki workload çalıştır; throttled seconds, RSS, OOM restart, p99 ve scheduling davranışını karşılaştır. Habitat adapter'larında backend tipine göre farklı resource profile tanımla.

### Failure modes / trade-off
Average-based sizing, sidecar'ı unutmak, CPU throttling'i application latency sanmak, memory leak'i limit artırarak gizlemek, request'i limit ile körlemesine eşitlemek.

### Kaynaklar
- Kubernetes — Resource Management for Pods and Containers: https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/
- Kubernetes — Resource Quotas: https://kubernetes.io/docs/concepts/policy/resource-quotas/

## Paket 3 — Staff ML/AI/LLM: Evaluation-Driven Development ve Regression Gates
**Süre:** 20–30 dk

### Konu anlatımı
LLM sisteminde 'çıktı iyi görünüyor' production kalite stratejisi değildir. Eval set; gerçek kullanım dağılımını, edge case'leri ve kritik failure mode'ları temsil eden versioned örneklerden oluşmalıdır. Her değişiklik — prompt, model, retrieval, tool schema — aynı regression setinde ölçülmelidir. Tek aggregate skor kök nedeni gizleyebileceği için task family, language, latency/cost ve safety/correctness gibi slice'lar ayrı izlenir.

Evaluator deterministik olmayabilir. Model-based grader kullanılıyorsa rubric açık olmalı, calibration örnekleri tutulmalı ve kritik correctness mümkün olduğunda programmatic assertion ile desteklenmelidir. Offline eval release gate sağlar; online telemetry gerçek dağılım drift'ini yakalar ve yeni eval vakaları üretir.

### Mental model
```text
production failures/examples
          |
          v
   versioned eval set ---> candidate change
          |                    |
          +------ run eval <---+
                    |
         quality + latency + cost
                    |
             gate / investigate
                    |
                 deploy
                    |
             online feedback
                    `----> new eval cases
```

### Yüksek getirili soru kümeleri
- Eval dataset nasıl seçilir ve nasıl versionlanır?
- LLM-as-a-judge ne zaman güvenilir değildir?
- Aggregate score neden tek başına yetersizdir?
- RAG eval'de retrieval ile generation failure nasıl ayrılır?
- Prompt/model değişikliği için regression gate nasıl tasarlanır?
- Offline ve online evaluation nasıl birbirini tamamlar?

### Seviye beklentisi
Mid temel dataset/metric kurar. Senior slice, regression ve reproducibility tasarlar. Staff evaluator governance, release gate, cost/latency-quality Pareto ve production feedback loop kurar. Principal şirket çapında eval standardı ve risk-tier politikasını belirler.

### Kısa alıştırma
Support RAG sistemi için 30 örneklik eval set şeması tasarla: answer correctness, citation support, retrieval recall proxy, refusal ve latency/cost alanlarını tanımla.

### Bununla ne yapabiliriz?
`llm-regression-gate`: prompt/retriever/model varyantlarını aynı versioned dataset üzerinde çalıştır; per-slice sonuç ve release threshold üret. Habitat-benzeri storage copilot'unda backend seçimi veya migration önerisinin policy constraints'i ihlal etmediğini deterministic checks ile doğrula.

### Failure modes / trade-off
Eval set overfitting, synthetic-only dataset, unstable grader, data leakage, tek skor, cost/latency'yi dışlamak, production drift'ten yeni case toplamamak.

### Kaynaklar
- OpenAI — Evaluation best practices: https://platform.openai.com/docs/guides/evaluation-best-practices
- OpenAI — Evals guide: https://platform.openai.com/docs/guides/evals
