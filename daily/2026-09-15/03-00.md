## Paket 1 — Senior Backend/JVM: Java Virtual Threads, Blocking I/O & Concurrency Limits
**Süre:** 20–30 dk

### Konu anlatımı
Virtual thread, Java `Thread` API'sini koruyan fakat OS thread'i yaşamı boyunca sahiplenmeyen hafif bir thread'dir. JDK scheduler çok sayıda virtual thread'i daha az sayıdaki carrier/platform thread üzerinde M:N biçiminde çalıştırır. Blocking JDK I/O sırasında virtual thread çoğunlukla carrier'dan unmount olur; carrier başka işi çalıştırabilir. Bu nedenle thread-per-request kodu yüksek I/O concurrency'de daha ekonomik hale gelebilir.

Mental modelde kritik ayrım **concurrency != parallelism**. Bir milyon virtual thread CPU'yu bir milyon kat hızlandırmaz; CPU-bound iş hâlâ core sayısı ve scheduler kapasitesiyle sınırlıdır. Ayrıca virtual thread ucuz olduğu için pool'lanmamalıdır; fakat database connection, downstream QPS ve memory gibi kıt kaynaklar hâlâ semaphore/rate limit/backpressure ile sınırlandırılmalıdır. JEP 444 ayrıca uzun/sık pinning'in scalability'yi bozabileceğini vurgular.

### Mental model
```text
10k request tasks = 10k virtual threads
        | mount / unmount
        v
+-------------------------------+
| carrier P1 | P2 | P3 | ... Pn |
+-------------------------------+
        |
        v
      CPU cores

Virtual thread cheap != downstream capacity infinite
VTs -> semaphore/bulkhead -> DB pool / remote API
```

### Yüksek getirili mülakat soruları
1. Virtual thread ile platform thread arasındaki temel fark nedir?
2. Virtual threads throughput'u hangi workload'da artırır, hangisinde artırmaz?
3. Neden virtual thread pool oluşturmak genellikle yanlış mental modeldir?
4. 100k virtual thread varken DB connection sayısını neden yine sınırlarsın?
5. Carrier pinning nedir ve production'da nasıl gözlemlersin?
6. Reactive/asynchronous model ile virtual-thread modelinin trade-off'ları nelerdir?

### Seviye beklentisi
- **Mid:** blocking I/O, platform thread ve virtual thread ayrımını açıklar.
- **Senior:** M:N scheduling, resource limits, pinning, observability ve migration risklerini tartışır.
- **Staff:** concurrency policy'yi downstream capacity, admission control, SLO ve fleet rollout ile birlikte tasarlar.

### Mini alıştırma
10.000 concurrent request alan, her request'te 100 ms DB bekleyen bir servis düşün. 50 connection'lık DB pool varken virtual thread sayısını artırmanın neyi çözüp neyi çözemediğini çiz.

### Proje fikri
`virtual-thread-load-lab`: aynı blocking HTTP/JDBC işini fixed platform-thread pool ve virtual-thread-per-task ile çalıştır; throughput, p99 latency, carrier sayısı, DB pool wait ve CPU'yu ölç.

### Failure modes / trade-off / production
Virtual thread'i CPU hızlandırıcısı sanmak, kıt downstream kaynakları limitsiz açmak, thread-local maliyetini küçümsemek, uzun blocking native/legacy kritik bölgeleri ölçmemek, benchmark'ta DB pool'u bottleneck yapıp runtime sonucuna yanlış anlam yüklemek.

## Paket 2 — Mid/Senior Frontend-Mobile: Offline-First, Local Source of Truth & Sync Conflicts
**Süre:** 20–30 dk

### Konu anlatımı
Offline-first tasarım yalnızca response cache eklemek değildir. Android'ın resmi mimari rehberinde network kullanan repository için local ve network data source ayrılır; higher layer okumalarının canonical kaynağı local data source olmalıdır. Network'ten gelen veri önce local store'u günceller, UI da observable local state'i görür. Böylece connectivity state'i UI veri erişim modelini sürekli değiştirmez.

Write stratejisi domain semantiğine bağlıdır: online-only write, queued write veya local-first/lazy write. Local-first write UX'i güçlendirir fakat reconnect sonrası conflict resolution gerektirir. Last-write-wins basittir fakat saat skew'u veya semantik veri kaybı yaratabilir; version/vector/operation tabanlı yaklaşımlar daha güçlü ama daha karmaşıktır. Sync correctness için idempotency, retry, durable queue, tombstone/deletion ve schema evolution düşünülmelidir.

### Mental model
```text
UI
 ^ observes
 |
Local DB  <---- Repository ----> Network/API
  ^              |
  | local write  +-- durable sync queue
  +--------------+          |
                             +--> retry/reconcile

Read path: local is app source of truth
Write path: product semantics choose online / queued / local-first
```

### Yüksek getirili mülakat soruları
1. Offline-first ile HTTP cache arasındaki fark nedir?
2. Neden UI doğrudan network response'u source-of-truth yapmamalı?
3. Queued write ile lazy/local-first write ne zaman seçilir?
4. İki cihaz aynı kaydı offline değiştirirse nasıl reconcile edersin?
5. Delete işlemleri sync'te neden tombstone gerektirebilir?
6. Retry edilen sync write'ları nasıl idempotent yaparsın?

### Seviye beklentisi
- **Junior/Mid:** local/network data source ve basic cache/sync akışını anlatır.
- **Senior:** durable queue, idempotency, conflict resolution, deletion ve UX durumlarını tasarlar.
- **Staff:** cross-device consistency contract, schema migration, telemetry ve backend protocol'ünü birlikte belirler.

### Mini alıştırma
Offline çalışan todo uygulamasında aynı task telefon A'da rename, tablet B'de complete edilsin. Field-level merge, LWW ve operation-log yaklaşımlarını karşılaştır.

### Proje fikri
`offline-sync-lab`: local SQLite/Room source-of-truth, durable outbox, fake API ve reconnect sync ekle; duplicate retry, conflict ve delete senaryolarını test et.

### Failure modes / trade-off / production
Network'i source-of-truth yapıp offline UI'ı kırmak, in-memory queue ile kullanıcı verisi kaybetmek, blind LWW, duplicate mutation, delete resurrection, unbounded retry, battery/data kullanımını hesaba katmamak.

### Kaynaklar
- https://developer.android.com/topic/architecture/data-layer/offline-first

## Paket 3 — Engineering Manager/CTO: DORA Metrics, Goodhart's Law & Delivery System Design
**Süre:** 20–30 dk

### Konu anlatımı
DORA'nın güncel software-delivery modeli throughput ve instability'yi birlikte ölçer. Güncel beş metrik: change lead time, deployment frequency, failed deployment recovery time, change fail rate ve deployment rework rate. Bunlar tek tek hedef puan değil, delivery system hakkında feedback sinyalidir. Örneğin deployment frequency'yi kota yapmak küçük anlamsız deploy'ları teşvik edebilir; change fail rate'i sıfıra zorlamak ise riskli değişikliklerden kaçınmayı veya incident saklamayı teşvik edebilir.

CTO/EM seviyesinde soru “metriği nasıl yükseltirim?” değil, **hangi capability darboğazı bu metriği üretiyor?** olmalıdır: batch size, CI süresi, test güvenilirliği, approval queue, deploy automation, architecture coupling, observability veya recovery pratiği. Metric takım karşılaştırma sopası değil, aynı sistemin zaman içindeki trendini ve bottleneck'ini anlamak için kullanılmalıdır. Product outcome ve reliability/SLO sinyalleriyle birlikte yorumlanmalıdır.

### Mental model
```text
Capabilities
CI/CD + small batches + tests + architecture + observability
                     |
                     v
Delivery system ---> DORA signals
                     | throughput: lead time / frequency / recovery
                     | instability: fail rate / rework
                     v
             Diagnose bottleneck
                     |
                     v
        experiment -> measure trend

Metric as target -> gaming risk
Metric as signal -> learning loop
```

### Yüksek getirili mülakat soruları
1. Güncel DORA delivery metrics nelerdir ve neden birlikte okunmalıdır?
2. Deployment frequency yüksekken change fail rate de yüksekse ne anlarsın?
3. Lead time'ı hangi value-stream aşamalarına parçalarsın?
4. Neden takımları ham DORA skorlarıyla rank etmek risklidir?
5. Goodhart's Law engineering metrics tasarımını nasıl etkiler?
6. CTO olarak delivery metric'i product outcome ve SLO ile nasıl bağlarsın?

### Seviye beklentisi
- **Senior:** metrikleri tanımlar ve temel nedenleri örnekler.
- **Staff/EM:** value-stream bottleneck, team boundaries ve improvement experiment tasarlar.
- **Principal/CTO:** metric governance, incentives, portfolio risk, product/reliability outcomes ve yatırım kararlarını bağlar.

### Mini alıştırma
Lead time 8 gün, deployment frequency haftada 1, change fail rate %5 olan bir takım için ilk 3 diagnostic soruyu ve iki improvement experiment'ini yaz. Sonra fail rate %30 olsaydı önceliğin nasıl değişirdi?

### Proje fikri
`delivery-health-dashboard`: deploy event'lerinden beş DORA metriğini çıkar; takım leaderboard'u yerine trend, confidence/data-quality notu ve bottleneck hypothesis alanları göster.

### Failure modes / trade-off / production
Metric'i hedefe dönüştürmek, takımları bağlamdan bağımsız kıyaslamak, deploy tanımını standardize etmemek, incident/hotfix verisini eksik toplamak, yalnızca velocity ölçüp reliability/product outcome'u dışarıda bırakmak, metric değişiminde causal inference yapmadan sonuç ilan etmek.
