## Paket 1 — Senior Cloud/Linux: cgroups v2 ve Resource Isolation (25 dk)

### Konu anlatımı
Linux cgroup, process'leri hiyerarşik gruplara ayırıp CPU, memory, IO ve PID gibi kaynakların dağıtımını gözlemleme ve kontrol etme mekanizmasıdır. cgroup v2 tek bir unified hierarchy kullanır. Controller'lar parent üzerinde etkinleştirilir ve child cgroup'lara kaynak kontrol arayüzü sağlar.

CPU controller iki farklı fikri ayırır: relative fairness ve absolute bandwidth. `cpu.weight`, contention olduğunda kardeş grupların göreli payını etkiler; `cpu.max` ise belirli periyotta tüketilebilecek CPU zamanını sınırlar. Memory tarafında `memory.current` mevcut kullanımı, `memory.high` reclaim/throttling için soft pressure sınırını, `memory.max` ise hard limit'i temsil eder. `memory.max` altında reclaim yeterli olmazsa cgroup içinde OOM killer devreye girebilir.

Kritik mülakat ayrımı: container bir kernel primitive değildir. Container runtime namespaces ile görünürlük/izolasyon, cgroups ile resource accounting/control, filesystem ve capability mekanizmalarıyla diğer sınırları bir araya getirir.

### Mental model
```text
host
└─ cgroup root
   ├─ api-service      cpu.weight=200  memory.max=2G
   │  ├─ worker-1
   │  └─ worker-2
   └─ batch-jobs       cpu.weight=50   memory.high=4G

contention -> controller policy -> resource distribution
```

### Yüksek getirili sorular
1. Namespace ile cgroup arasındaki fark nedir?
2. CPU limit ile CPU request/weight aynı şey midir?
3. `memory.high` ile `memory.max` neden farklıdır?
4. Container memory limitine çarpınca host mutlaka OOM olur mu?
5. CPU throttling p99 latency'yi nasıl etkileyebilir?
6. Neden sadece ortalama CPU/memory metriğine bakmak yetersizdir?

### Beklenen cevap derinliği
- **Junior/Mid:** cgroup'un kaynakları grupladığını ve limit/accounting yaptığını açıklar.
- **Senior:** weight vs quota, reclaim, OOM ve throttling etkilerini ayırır.
- **Staff:** noisy-neighbor, oversubscription, capacity policy ve latency/SLO etkilerini birlikte tartışır.

### 10 dakikalık alıştırma
Bir API, async worker ve batch job aynı 8-core/16 GiB host üzerinde. API latency kritik. Her workload için CPU weight/quota ve memory high/max stratejisi tasarla; hangi metriğin yanlış konfigürasyonu göstereceğini yaz.

### Proje fikri
`cgroup-observer`: `/sys/fs/cgroup` üzerinden `cpu.stat`, `memory.current`, `memory.events` ve pressure sinyallerini okuyup küçük bir terminal dashboard'u üret.

### Failure modes / trade-off / production
Çok agresif CPU quota tail latency'yi yükseltebilir; düşük memory hard limit restart/OOM döngüsü yaratabilir; limitsiz batch workload noisy-neighbor olabilir. Resource isolation yalnızca limit koymak değil, saturation altında hangi workload'un degrade olacağına karar vermektir.

**Birincil kaynak:** https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html

## Paket 2 — Mid/Senior Algorithms: Graph Shortest Path — BFS vs Dijkstra (25 dk)

### Konu anlatımı
Shortest-path sorusunda ilk soru algoritma değil edge modelidir. Unweighted graph'ta veya tüm edge cost'ları eşitse BFS, node'ları source'tan artan hop mesafesiyle ziyaret ettiği için shortest path verir. Non-negative fakat farklı edge weight'ları varsa Dijkstra, henüz kesinleşmemiş en düşük tentative distance'ı priority queue'dan seçer ve outgoing edge'leri relax eder.

Relaxation'ın özü: `dist[v] > dist[u] + w(u,v)` ise daha iyi yol bulduk. Binary heap ile tipik complexity `O((V+E) log V)`; sparse graph için pratikte `O(E log V)` diye ifade edilir. Negative edge varsa Dijkstra'nın greedy invariant'ı bozulur; Bellman-Ford gibi farklı yaklaşım gerekir.

### Mental model
```text
BFS:      frontier by hop count
source -> layer 1 -> layer 2 -> layer 3

Dijkstra: frontier by cheapest known distance
PQ [(0,S)] -> pop min -> relax neighbors -> push improved distances
```

### Yüksek getirili sorular
1. BFS neden unweighted shortest path verir?
2. Dijkstra'da visited node neden tekrar açılmaz?
3. Priority queue'da decrease-key yoksa ne yapılabilir?
4. Negative edge Dijkstra'yı neden bozar?
5. Grid shortest path ne zaman BFS, ne zaman Dijkstra olur?
6. Path'i sadece distance yerine nasıl reconstruct edersin?

### Beklenen cevap derinliği
- **Junior:** BFS traversal ve queue kullanımı.
- **Mid:** weighted graph'ta Dijkstra + heap + predecessor map.
- **Senior:** invariant, stale heap entry, complexity ve problem-model seçimi.

### 10 dakikalık alıştırma
Bir şehir grafında yol süresi edge weight. `A` noktasından tüm noktalara minimum süreyi ve path'i döndüren Dijkstra yaz. Sonra tüm weight'ları 1 yapınca hangi yapıyı kaldırabileceğini açıkla.

### Proje fikri
`route-lab`: aynı graph dataset'inde BFS, Dijkstra ve A* sonuçlarını visited-node sayısı, latency ve path cost açısından karşılaştır.

### Failure modes / trade-off / production
Yanlışlıkla BFS kullanmak weighted graph'ta yanlış sonuç; Dijkstra'yı negative edge ile kullanmak correctness bug'ı; priority queue'daki stale entry'leri filtrelememek gereksiz work; graph'ı tamamen memory'de tutmak büyük routing problemlerinde ölçek sorunu yaratır.

**Kaynaklar:** https://docs.python.org/3/library/heapq.html ve klasik Dijkstra makalesi: E. W. Dijkstra, *A note on two problems in connexion with graphs* (1959).

## Paket 3 — Staff/Principal/CTO: Architecture Decision Records (ADR) ve Decision Quality (25 dk)

### Konu anlatımı
Architecture kararı yalnızca seçilen teknoloji değildir; context, constraints, alternatives, trade-off ve beklenen consequence bütünüdür. ADR bu kararı küçük, version-controlled bir kayıt haline getirir. Amaç her toplantıyı belgelemek değil; gelecekte bir mühendisin “neden böyle yaptık?” sorusuna güvenilir cevap vermektir.

İyi ADR'de problem/context, decision drivers, değerlendirilen seçenekler, karar, olumlu/olumsuz consequences ve gerektiğinde revisit trigger bulunur. Kararın immutable history olarak kalması önemlidir: eski ADR'yi sessizce yeniden yazmak yerine yeni ADR eskisini supersede eder.

Staff/CTO seviyesinde asıl konu format değil decision system'dir: reversible vs irreversible decisions, blast radius, cost of delay, option value ve hangi sinyal geldiğinde kararın tekrar açılacağı.

### Mental model
```text
Context + constraints
       |
       v
Alternatives -> trade-off matrix -> Decision
                                  |
                    consequences + revisit signals
                                  |
                         future engineers
```

### Yüksek getirili sorular
1. ADR ile design doc arasındaki fark nedir?
2. Hangi karar ADR hak eder?
3. Kararı ne zaman revisit edersin?
4. Build-vs-buy ADR'sinde hangi ekonomik değişkenleri beklersin?
5. Bir karar yanlış çıktıysa ADR başarısız mıdır?
6. Architecture governance nasıl bureaucracy'ye dönüşmeden yapılır?

### Beklenen cevap derinliği
- **Senior:** alternatives ve consequences yazar.
- **Staff/Principal:** cross-team blast radius, reversibility ve migration cost ekler.
- **EM/CTO:** karar kalitesini şirket hedefleri, opportunity cost, compliance ve organizasyon kapasitesiyle bağlar.

### 10 dakikalık alıştırma
“Self-hosted Kafka mı managed event platform mu?” için 1 sayfalık ADR iskeleti yaz. 5 decision driver, 3 alternatif, 3 revisit trigger belirle.

### Proje fikri
Repo'ya `decisions/` dizini ekleyip gerçek projedeki 5 önemli kararı ADR olarak kaydet; altı ay sonra hangilerinin assumptions'ının değiştiğini inceleyen decision review üret.

### Failure modes / trade-off / production
ADR'yi karar sonrası justification belgesine çevirmek, alternatifleri karikatürize etmek, ölçülebilir revisit trigger koymamak ve her küçük tercihi ADR yapmak sistemi değersizleştirir. İyi governance karar hızını düşürmek yerine yüksek blast-radius kararlarında bellek ve accountability sağlar.

**Birincil kaynak:** https://adr.github.io/
