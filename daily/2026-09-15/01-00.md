## Paket 1 — Senior Databases: PostgreSQL Declarative Partitioning & Partition Pruning
**Süre:** 20–30 dk

### Konu anlatımı
Partitioning, mantıksal olarak tek büyük tabloyu daha küçük fiziksel parçalara ayırır. PostgreSQL declarative partitioning RANGE, LIST ve HASH yöntemlerini destekler. Parent partitioned table kendi storage'ına sahip değildir; satırlar partition key'e göre child partition'lara yönlendirilir.

Partitioning bir index alternatifi değildir. En büyük kazanç, sorgu predicate'i partition key ile hizalandığında optimizer'ın ilgisiz partition'ları **partition pruning** ile plandan veya execution sırasında çıkarmasıdır. Ayrıca retention operasyonları milyonlarca satırı DELETE etmek yerine eski partition'ı detach/drop ederek yapılabilir.

Partition key workload'dan türetilmelidir. Yanlış key çok fazla partition taramasına, planning overhead'e, operational karmaşıklığa ve global uniqueness tasarım sorunlarına yol açabilir.

### Mental model
```text
                 events (logical parent)
                         |
                 RANGE(created_at)
              /          |          \
        2026-07       2026-08       2026-09
           X              X             |
      predicate pruning             scan here
```

### Mülakat soruları
1. Partitioning ile indexing arasındaki fark nedir?
2. Partition pruning ne zaman çalışır?
3. Time-series tabloda RANGE partition neden doğaldır?
4. Çok fazla partition neden planning maliyetini artırabilir?
5. Retention için DROP/DETACH neden DELETE'den avantajlı olabilir?
6. Tenant ID ile mi tarih ile mi partition edersin? Workload'a göre tartış.

### Seviye beklentisi
- **Mid:** RANGE/LIST/HASH ve temel pruning'i anlatır.
- **Senior:** workload, retention, index-per-partition, skew ve maintenance trade-off'larını tartışır.
- **Staff:** partition lifecycle automation, migration, observability ve multi-tenant blast radius'u tasarlar.

### Mini alıştırma
`events(tenant_id, created_at, type, payload)` için aylık RANGE partition şeması tasarla. Son 7 gün sorgusu ile tek tenant'ın 2 yıllık geçmiş sorgusunun hangi partition'lara dokunacağını açıkla.

### Proje fikri
`partition-lab`: 12 aylık sentetik event datası üret; partitioned ve non-partitioned tabloları `EXPLAIN (ANALYZE, BUFFERS)` ile karşılaştır. Retention operasyonunda DELETE ile DETACH/DROP farkını ölç.

### Failure modes / production
Yanlış partition key, küçük ama binlerce partition, missing future partition nedeniyle insert failure, uneven tenant skew, bakım otomasyonunun yeni partition yaratamaması ve pruning'i engelleyen sorgu biçimleri.

## Paket 2 — Mid/Senior Kubernetes: Topology Spread Constraints & Failure Domains
**Süre:** 20–30 dk

### Konu anlatımı
Replica sayısını artırmak tek başına high availability sağlamaz. Scheduler tüm replica'ları aynı node veya zone'a koyarsa tek failure domain kaybı servisi etkileyebilir. Topology spread constraints Pod'ların node, zone veya kullanıcı tanımlı topology domain'leri arasında ne kadar dengesiz dağılabileceğini kontrol eder.

Temel kavramlar `topologyKey`, `maxSkew` ve `whenUnsatisfiable`'dır. `DoNotSchedule` sert bir availability placement constraint'i gibi davranırken `ScheduleAnyway` scheduler'a tercih sinyali verir. Constraint, kapasite ve autoscaling ile birlikte düşünülmelidir; çok sert spread kuralı boş kapasite varken bile Pod'u Pending bırakabilir.

### Mental model
```text
             Region
       +------+-------+
       |              |
     zone-a         zone-b
   node1 node2    node3 node4
     P1    P3       P2    P4

Amaç: replica'ları aynı failure domain'de yığmamak.
```

### Mülakat soruları
1. 3 replica neden otomatik olarak HA değildir?
2. topologyKey neyi temsil eder?
3. maxSkew=1 neyi sınırlar?
4. DoNotSchedule ile ScheduleAnyway farkı nedir?
5. Spread constraints ile pod anti-affinity nasıl karşılaştırılır?
6. Cluster autoscaler ile sert topology constraint nasıl etkileşir?

### Seviye beklentisi
- **Mid:** node/zone failure domain ve temel constraint alanlarını bilir.
- **Senior:** capacity, Pending pods, autoscaling ve rollout etkisini tartışır.
- **Staff:** multi-zone availability hedefini PDB, replica count, autoscaling ve topology ile birlikte tasarlar.

### Mini alıştırma
3 zone'lu cluster'da 5 replica için `topology.kubernetes.io/zone`, `maxSkew: 1` kullanan bir yerleşim çiz. Bir zone kaybolduğunda kalan kapasiteyi değerlendir.

### Proje fikri
Minik Kubernetes workload'u deploy et; zone/node label'larıyla spread davranışını gözlemle. Bir node'u cordon/drain ederek replica dağılımını ve availability etkisini raporla.

### Failure modes / production
Eksik topology label, yetersiz zone capacity, aşırı sert constraint, autoscaler'ın uygun node group oluşturamaması, rollout sırasında geçici skew ve yalnızca replica sayısına bakarak HA varsaymak.

### Kaynaklar
- https://kubernetes.io/docs/concepts/scheduling-eviction/topology-spread-constraints/

## Paket 3 — Staff AI/LLM: Tool Calling, Structured Outputs & Trust Boundaries
**Süre:** 20–30 dk

### Konu anlatımı
Tool calling'de model dış sistemi doğrudan çalıştıran güvenilir bir program değildir; model bir **intent + structured arguments** üretir, uygulama ise schema validation, authorization ve execution katmanlarını kontrol eder. Structured Outputs belirli konfigürasyonlarda argümanların tanımlı JSON Schema'ya uymasını güçlendirir; ancak semantik doğruluğu garanti etmez. Schema'ya uyan `transfer_money(amount=1000000)` hâlâ yanlış veya yetkisiz olabilir.

Bu nedenle trust boundary model ile tool executor arasındadır. Executor identity/permission kontrolü, argument bounds, idempotency, timeout, audit log ve gerekiyorsa human approval uygular. Tool sonucunun kendisi de untrusted input olabilir; prompt injection yalnızca kullanıcı mesajından değil web sayfası, belge veya tool output'undan gelebilir.

### Mental model
```text
User -> Model -> proposed tool call
                  |
             JSON/schema
                  v
          Policy / AuthZ Gate
          | validate bounds |
          | idempotency     |
          | approval?       |
                  v
              Executor
                  |
             External API
```

### Mülakat soruları
1. JSON-valid tool call neden güvenli tool call değildir?
2. Model ile executor arasındaki trust boundary nedir?
3. Tool output neden untrusted kabul edilmelidir?
4. Side-effecting tool için idempotency neden önemlidir?
5. Human approval hangi risk sınıflarında mantıklıdır?
6. Prompt injection'a karşı yalnızca system prompt neden yeterli değildir?

### Seviye beklentisi
- **Senior:** schema validation, authZ ve tool error handling'i anlatır.
- **Staff:** least privilege, approval gates, auditability, injection boundaries ve failure isolation tasarlar.
- **Principal/CTO:** risk sınıflandırması, compliance, blast radius ve organizasyon çapında tool governance standardı kurar.

### Mini alıştırma
`refund_order(order_id, amount)` tool'u için güvenlik katmanlarını tasarla: caller identity, maximum amount, duplicate request, approval threshold, timeout ve audit alanlarını belirle.

### Proje fikri
`safe-tool-gateway`: schema-valid tool çağrılarını alan fakat policy engine, idempotency key, audit log ve dry-run/approval mekanizmasından geçirmeden side effect çalıştırmayan küçük gateway yaz.

### Failure modes / production
Schema-correct fakat yanlış argüman, over-privileged credentials, tool-result prompt injection, duplicate side effect, authorization'ın modele bırakılması, audit eksikliği ve timeout/retry'nin duplicate operation üretmesi.

- https://openai.com/index/introducing-structured-outputs-in-the-api/
