## Paket 1 — Mid/Senior Backend: HTTP ETag, Conditional Requests & Lost-Update Prevention
**Süre:** 20–30 dk

### Konu anlatımı
HTTP conditional request mekanizması yalnız cache optimizasyonu değildir; state-changing API'lerde optimistic concurrency control olarak da kullanılabilir. Sunucu bir representation için `ETag` üretir. Client kaynağı okurken bu validator'ı alır ve güncellemede `If-Match` ile son gördüğü sürümü belirtir. RFC 9110'a göre `If-Match` strong comparison kullanır; current representation değişmişse origin server işlemi uygulamamalı ve tipik olarak `412 Precondition Failed` dönmelidir. Böylece iki editor aynı kaynağı paralel değiştirirken ikinci yazının birincisini sessizce ezmesi, yani lost update, engellenebilir.

`If-None-Match` çoğunlukla cache revalidation içindir; GET/HEAD'de eşleşme halinde `304 Not Modified` üretebilir. `If-None-Match: *` ise create-if-absent deseninde mevcut representation'ı yanlışlıkla overwrite etmeyi önleyebilir. ETag'in resource version mı representation version mı olduğu, content negotiation ve compression gibi representation farklarıyla birlikte tasarlanmalıdır.

### Mental model
```text
GET /doc/7
<- 200 ETag: "v41"

Client A: PUT If-Match: "v41" -> success -> ETag "v42"
Client B: PUT If-Match: "v41" -> 412
                                  |
                                  v
                             re-read/merge
```

### Yüksek getirili mülakat soruları
- `If-Match` lost update'i nasıl engeller?
- `If-Match` neden strong comparison kullanır?
- `If-None-Match` ile `If-Match` kullanım amaçları nasıl ayrılır?
- `304` ile `412` hangi durumlarda beklenir?
- ETag'i DB row version'dan üretmenin avantaj/dezavantajı nedir?
- Senior: PATCH, idempotency key ve optimistic concurrency birbirinin yerine geçer mi?

### Seviyeye göre cevap derinliği
Junior/Mid: ETag, cache validator, 304/412. Senior: optimistic concurrency, strong/weak validators, PATCH/PUT semantics ve conflict UX. Staff: representation-version modeli, proxy/cache davranışı, multi-resource transaction sınırları ve API-wide concurrency standardı.

### Kısa alıştırma
A ve B client'larının aynı profile kaydını okuyup farklı alanları güncellediği akışta ETag değerlerini ve 412 sonrasındaki merge stratejisini çiz.

### Proje fikri
`etag-concurrency-lab`: küçük REST API + version column; concurrent update testi, conditional GET ve conflict metric'i ekle.

### Failure modes / trade-off / production
ETag'i sadece cache özelliği sanmak; state-changing request'te precondition kullanmamak; weak validator'ı concurrency için kullanmak; 412'yi kör retry edip kullanıcının değişikliğini ezmek; representation varyantlarını version modelinde düşünmemek.

### Kaynaklar
- RFC 9110 — Conditional Requests: https://www.rfc-editor.org/rfc/rfc9110.html#name-conditional-requests
- RFC 9110 — If-Match: https://www.rfc-editor.org/rfc/rfc9110.html#name-if-match
- RFC 9110 — If-None-Match: https://www.rfc-editor.org/rfc/rfc9110.html#name-if-none-match

## Paket 2 — Senior/Staff Cloud/SRE: Kubernetes HPA Stabilization, Scaling Policies & Control-Loop Failure Modes
**Süre:** 20–30 dk

### Konu anlatımı
HorizontalPodAutoscaler bir control loop'tur: workload metric'lerini okuyup hedefe göre desired replica sayısı hesaplar ve scale subresource'u üzerinden kapasiteyi değiştirir. Production tasarımında yalnız target CPU seçmek yetmez. `autoscaling/v2` içindeki `behavior` alanı scale-up ve scale-down yönleri için ayrı stabilization window ve scaling policy tanımlamaya izin verir. Stabilization, dalgalanan metric'lerin replica flapping üretmesini azaltır; özellikle downscale tarafında yakın geçmişteki daha yüksek desired recommendation'ı korumak, kapasiteyi erken söküp hemen geri ekleme döngüsünü sınırlar.

HPA gecikmeli bir feedback sistemidir. Metric delay, pod startup/warm-up, load balancer convergence ve workload queueing birlikte düşünüldüğünde yanlış metric veya agresif downscale pozitif geri besleme yaratabilir. CPU-bound servis için CPU anlamlı olabilirken queue consumer için queue depth/oldest-message-age, latency-sensitive servis için concurrency veya request-rate daha iyi sinyal olabilir. HPA kapasiteyi artırabilir ama downstream bottleneck'i, database connection limitini veya external quota'yı ortadan kaldırmaz.

### Mental model
```text
traffic -> service -> metric -> HPA controller -> replicas
   ^                                      |
   |                                      v
   +------- latency / queue / load <------+

fast scale-up + cautious scale-down
startup delay + metric delay = control-loop lag
```

### Yüksek getirili mülakat soruları
- HPA neden basit threshold rule değil control loop olarak düşünülmeli?
- Stabilization window hangi flapping problemini azaltır?
- Scale-up ve scale-down neden asimetrik ayarlanabilir?
- CPU metric'i queue worker için neden yanıltıcı olabilir?
- HPA ile Cluster Autoscaler gecikmeleri nasıl etkileşir?
- Staff: DB connection ceiling varken autoscaling'i nasıl sınırlar ve load shedding ile bağlarsın?

### Seviyeye göre cevap derinliği
Mid: target metric ve replicas. Senior: stabilization, scaling velocity, metric semantics, warm-up. Staff/Principal: coupled control loops, capacity ceilings, downstream protection, SLO ve load-test calibration.

### Kısa alıştırma
10 pod'lu serviste 2 dakikalık trafik spike'ı için agresif scale-up ve 5 dakikalık downscale stabilization tasarla; pod warm-up 45 saniyeyse riskleri yaz.

### Proje fikri
`hpa-control-loop-lab`: CPU ve queue-depth tabanlı iki HPA senaryosunu load test et; p95, replicas, pending work ve oscillation sayısını karşılaştır.

### Failure modes / trade-off / production
Yanlış metric; pod startup süresini yok saymak; limitsiz scale-up ile DB'yi boğmak; metric pipeline outage davranışını test etmemek; HPA ile başka autoscaler'ların aynı kapasiteyi çelişkili yönetmesi.

### Kaynaklar
- Kubernetes — Horizontal Pod Autoscaling: https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/
- Kubernetes API — HorizontalPodAutoscaler v2: https://kubernetes.io/docs/reference/kubernetes-api/autoscaling/horizontal-pod-autoscaler-v2/

## Paket 3 — Mid/Senior Frontend/Mobile: Jetpack Compose State Hoisting, UDF & Recomposition Boundaries
**Süre:** 20–30 dk

### Konu anlatımı
Jetpack Compose declarative UI modelinde UI, state'in bir fonksiyonudur. State değiştiğinde Compose ilgili state read'lerini izleyerek gerekli işi yeniden çalıştırabilir. `remember` recomposition boyunca değeri tutar; configuration/activity recreation gibi senaryolarda korunması gereken küçük UI state için `rememberSaveable` kullanılabilir. Observable olmayan mutable collection'lar state olarak kullanılırsa değişiklik Compose tarafından görülmeyebilir ve stale UI oluşabilir.

State hoisting, state'i kullanan composable'dan uygun caller'a taşımaktır. Tipik kontrat `value` aşağı, event callback yukarı şeklindedir; bu unidirectional data flow üretir. Ama her state'i ViewModel'a taşımak doğru değildir: ephemeral UI element state ile screen/business state'in lifecycle ve ownership'i farklıdır. Hoisting seviyesi, state'i okuyanların lowest common ancestor'ı ve state'i değiştirenlerin ihtiyaçlarıyla belirlenmelidir.

### Mental model
```text
          Screen / state holder
             | state down
             v
        Stateless UI
             |
             | events up
             v
          reducer/update

single source of truth -> predictable recomposition
```

### Yüksek getirili mülakat soruları
- `remember` ile `rememberSaveable` farkı nedir?
- State hoisting hangi problemleri çözer?
- UDF'de state down/events up neden test edilebilirliği artırır?
- Mutable `ArrayList` neden stale UI yaratabilir?
- Her state ViewModel'a taşınmalı mı?
- Senior: recomposition sayısını azaltmak ile doğru state ownership arasında nasıl denge kurarsın?

### Seviyeye göre cevap derinliği
Junior/Mid: mutableState, remember, hoisting. Senior: snapshot state reads, lifecycle, ViewModel ownership, immutable UI state ve recomposition boundaries. Staff: feature architecture, state contract standardı, navigation/process restoration ve performance instrumentation.

### Kısa alıştırma
Arama kutusu + filtre + sonuç listesi ekranında query, selected filter, scroll position ve server result state'lerinin ownership seviyelerini seç.

### Proje fikri
`compose-state-lab`: stateful ve hoisted iki ekran varyantı; rotation/process recreation, UI tests ve recomposition davranışını karşılaştır.

### Failure modes / trade-off / production
Her şeyi global/ViewModel state yapmak; observable olmayan mutable collection; derived state'i duplicate source-of-truth yapmak; lifecycle'dan bağımsız coroutine başlatmak; performans sorununun kaynağını ölçmeden recomposition'ı optimize etmek.

### Kaynaklar
- Android Developers — State and Jetpack Compose: https://developer.android.com/develop/ui/compose/state
- Android Developers — Compose phases: https://developer.android.com/develop/ui/compose/phases
