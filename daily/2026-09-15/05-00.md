## Paket 1 — Junior/Mid Algorithms: Heap, Priority Queue & Top-K
**Süre:** 20–30 dk

### Konu anlatımı
Heap, her düğümün çocuklarıyla belirli bir sıralama invariant'ı taşıdığı complete binary tree modelidir. Min-heap'te kök minimumdur; array representation'da parent/child ilişkileri index aritmetiğiyle tutulur. Heap tüm elemanları sıralı tutmaz: yalnız kökün extremum olduğunu ve path boyunca invariant'ı garanti eder. Bu nedenle minimumu görmek O(1), push/pop O(log n), heapify ise O(n)'dir.

Top-K probleminde bütün n elemanı sort etmek O(n log n) iken sabit boyutlu k heap ile O(n log k) elde edilebilir. Priority queue scheduler, shortest-path frontier, merge-k-sorted-streams ve event simulation gibi production yapılarına bağlanır.

### Mental model
```text
min-heap
        2
      /   \
     5     4
    / \   /
   9   8  7

array: [2,5,4,9,8,7]
root = min
push -> append + bubble up
pop  -> root'u al, sonu köke taşı + bubble down
```

### Yüksek getirili mülakat soruları
1. Heap ile sorted array farkı nedir?
2. `heapify` neden O(n log n) değil O(n) olabilir?
3. En büyük K elemanı O(n log k) nasıl bulursun?
4. Priority update/delete neden basit heap API'sinde zor olabilir?
5. Dijkstra'da priority queue neden kullanılır?

### Seviye beklentisi
- **Junior:** heap invariant, root ve push/pop karmaşıklığını açıklar.
- **Mid:** Top-K, k-way merge ve lazy deletion pattern'ini uygular.
- **Senior:** bounded queue, stability/tie-breaker ve memory/latency trade-off'unu production bağlamına taşır.

### Mini alıştırma
1 milyon latency değerinden en yüksek 100 taneyi stream sırasında tutan algoritmayı yaz; memory ve time complexity'yi çıkar.

### Proje fikri
`top-k-stream-lab`: event stream'den tenant başına top-K latency endpoint'lerini bounded heap ile tut; batch sort ile CPU/memory karşılaştır.

### Failure modes / trade-off / production
Heap'i tamamen sorted sanmak, k küçükken tüm veriyi sort etmek, equal-priority task'larda deterministic tie-breaker kullanmamak, stale priority entry'leri temizlememek, unbounded priority queue ile memory büyütmek.

## Paket 2 — Senior Data Engineering: Apache Iceberg Small Files, Compaction & Partition Evolution
**Süre:** 20–30 dk

### Konu anlatımı
Lakehouse'ta çok sayıda küçük data file yalnız storage sorunu değildir: metadata büyür, file-open maliyeti artar ve query planning/execution verimsizleşir. Apache Iceberg data file'ları metadata üzerinden izler ve `rewriteDataFiles` ile küçük dosyaları daha büyük dosyalara compact edebilir. Compaction write amplification ve compute maliyeti yaratır; bu yüzden her write sonrası körlemesine değil workload ve file-size dağılımına göre planlanmalıdır.

Partition evolution ayrı bir güçlü özelliktir: yeni partition spec metadata üzerinden eklenebilir; eski data eski layout'ta kalırken yeni data yeni layout ile yazılır. Query engine her spec için uygun pruning planı oluşturabilir. Böylece partition değişikliği için bütün tabloyu eager rewrite etmek gerekmez.

### Mental model
```text
stream writes
  | | | | |      -> many small files
  v v v v v
[f1][f2][f3][f4][f5]
       | rewriteDataFiles
       v
[       F-big-1       ][ F-big-2 ]

partition spec v1: day(ts)   -> old files stay
partition spec v2: hour(ts)  -> new files
             \ metadata plans both /
```

### Yüksek getirili mülakat soruları
1. Small-file problem query latency'yi neden artırır?
2. Compaction neden bedava değildir?
3. Data-file compaction ile manifest rewrite aynı şey midir?
4. Partition evolution eski dosyaları neden zorunlu olarak rewrite etmez?
5. Partition granularity'yi hangi workload sinyalleriyle değiştirirsin?
6. Streaming ingestion ile compaction job birbirini nasıl etkiler?

### Seviye beklentisi
- **Mid:** small files ve partitioning problemini tanımlar.
- **Senior:** target file size, scheduling, write amplification ve pruning'i tartışır.
- **Staff:** ingestion SLA, query SLA, compute budget, catalog concurrency ve maintenance policy'yi birlikte tasarlar.

### Mini alıştırma
Saatte 100 bin adet 200 KB dosya üreten bir event table için compaction trigger, target size ve partition stratejisi öner; query pattern'in son 7 gün tenant+time range olduğunu varsay.

### Proje fikri
`iceberg-maintenance-lab`: küçük dosyalı tablo üret, file metadata dağılımını ölç, compaction uygula ve planning/query süresini önce/sonra karşılaştır.

### Failure modes / trade-off / production
Over-partitioning, sürekli compaction ile compute yakmak, concurrent writer/maintenance davranışını test etmemek, yalnız ortalama file size izlemek, partition spec değişince eski data'nın fiziksel olarak taşındığını varsaymak.

### Kaynaklar
- https://iceberg.apache.org/docs/latest/maintenance/
- https://iceberg.apache.org/docs/latest/evolution/

## Paket 3 — Senior/Staff Cybersecurity & Networking: Kubernetes NetworkPolicy, Default-Deny & Egress Control
**Süre:** 20–30 dk

### Konu anlatımı
Kubernetes NetworkPolicy pod'lar arasındaki L4 connectivity'yi pod selector, namespace selector ve IP block gibi kimliklerle sınırlar. Kritik nokta: policy objesini API server'a yazmak tek başına enforcement garantisi değildir; cluster networking implementation/CNI NetworkPolicy'yi desteklemelidir.

Default-deny yaklaşımı önce seçilen pod'ları ingress/egress için izole eder, sonra gereken akışları allow-list eder. Fakat uygulama bağımlılıkları DNS, metrics, identity provider, object storage veya external API gibi egress ihtiyaçları taşıyabilir. Egress'i körlemesine kapatmak outage yaratır; açık bırakmak ise compromised workload'un exfiltration ve command-and-control blast radius'unu büyütebilir.

### Mental model
```text
Internet
   X default deny ingress
   |
[frontend] --allow:443--> [api] --allow:5432--> [db]
                              |
                              +--allow DNS--> [resolver]
                              X other egress

NetworkPolicy object
       +
CNI enforcement
       =
actual traffic control
```

### Yüksek getirili mülakat soruları
1. NetworkPolicy neyi seçer ve neyi allow eder?
2. Policy oluşturmak neden her cluster'da enforcement anlamına gelmez?
3. Default-deny rollout'unu production'da nasıl güvenli yaparsın?
4. Namespace selector ile pod selector nasıl birleşir?
5. Egress restriction hangi saldırı blast radius'unu azaltır?
6. NetworkPolicy neden application authorization'ın yerine geçmez?

### Seviye beklentisi
- **Mid:** ingress/egress, selector ve default-deny modelini açıklar.
- **Senior:** DNS/external dependency, CNI capability ve staged rollout'u tartışır.
- **Staff:** network segmentation'ı identity, service mesh, observability, incident response ve multi-tenant threat model ile bağlar.

### Mini alıştırma
`frontend -> api -> db` uygulamasında default-deny'dan başlayıp yalnız gerekli akışları aç. API'nin DNS ve bir payment endpoint'ine egress ihtiyacını ayrıca modelle.

### Proje fikri
`netpol-lab`: üç namespace'li demo cluster kur; connectivity test matrix üret, default-deny ve allow policy'leri ekledikçe beklenen/gerçek bağlantıları CI'da doğrula.

### Failure modes / trade-off / production
CNI desteğini doğrulamamak, DNS egress'i unutmak, IP tabanlı external dependency'nin değişkenliğini hesaba katmamak, policy'yi authn/authz sanmak, gözlemlenebilirlik olmadan cluster-wide default-deny açmak, node/host networking edge case'lerini yok saymak.

### Kaynaklar
- https://kubernetes.io/docs/concepts/services-networking/network-policies/
