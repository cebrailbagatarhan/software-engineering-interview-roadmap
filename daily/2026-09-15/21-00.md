## Paket 1 — Senior/Staff Networking & Distributed Systems: QUIC Loss Detection, PTO & Congestion Control
**Süre:** 20–30 dk

### Konu anlatımı
QUIC güvenilirliği UDP üzerinde yeniden kurarken TCP'nin byte sequence-number modelini birebir kopyalamaz. Packet number her packet-number-space içinde monoton artar ve retransmission aynı packet number ile yapılmaz: kaybolan frame gerekli ise yeni bir packet içine, yeni packet number ile konur. Bu ayrım ACK yorumunu ve RTT/loss reasoning'ini sadeleştirir.

Loss detection iki ana sinyal kullanır: packet threshold ve time threshold. Daha sonra gönderilmiş bir packet ACK aldıysa ve eski packet yeterince geride kaldıysa kayıp ilan edilebilir. ACK gelmemesi durumunda PTO (Probe Timeout) devreye girer. Kritik mülakat ayrımı: PTO expiration tek başına packet loss kanıtı değildir; probe göndererek forward progress aranır. Congestion control path-level bir feedback loop'tur; loss veya ECN congestion window'u etkiler. Persistent congestion ise sıradan tek loss'tan daha sert bir sinyaldir.

### Mental model
```text
send packet #10 #11 #12 #13
       |         X       |
       |                 +--> ACK #13
       |                       |
       +--> #11 old enough? ---+
                  |
          packet/time threshold
                  |
              declare loss
                  |
       retransmit FRAME in NEW packet

no useful ACK -> PTO -> probe(s)
loss/ECN -> congestion response
persistent congestion -> minimum window
```

### Yüksek getirili mülakat soruları
- QUIC neden retransmission'da aynı packet number'ı tekrar kullanmaz?
- Packet threshold ile time threshold neyi dengeler?
- PTO expiration neden doğrudan loss demek değildir?
- RTT sample'da ACK delay neden önemlidir?
- Loss detection ile congestion control neden aynı kavram değildir?
- Staff: reordering yüksek bir mobile network'te agresif loss threshold neye yol açar?

### Seviyeye göre cevap derinliği
Mid: ACK, RTT, packet loss ve retransmission. Senior: packet-number spaces, threshold loss, PTO, bytes-in-flight ve congestion window. Staff/Principal: reordering trade-off'u, ECN, persistent congestion, path migration ve observability sinyalleri.

### Kısa alıştırma
#10–#14 gönderildiğini, #14 ACK alırken #11'in gelmediğini varsay. Packet-threshold ve time-threshold ile hangi ek bilgiye ihtiyaç duyduğunu yaz; PTO'nun bu senaryodaki rolünü ayır.

### Proje fikri
`quic-recovery-simulator`: packet send/ACK/loss/reordering event'lerini simüle edip RTT, PTO ve congestion-window zaman serisi üreten küçük bir simulator.

### Failure modes / trade-off / production
PTO'yu RTO ile birebir aynı sanmak; her PTO'da tüm unacked packet'leri lost işaretlemek; reordering'i loss sanıp spurious retransmission üretmek; ACK delay'i RTT hesabında yanlış kullanmak; transport metric'lerini yalnız application latency ile gözlemlemek. Production'da RTT distribution, loss events, PTO count, bytes-in-flight ve handshake/path değişimlerini birlikte korele et.

### Kaynaklar
- IETF RFC 9002 — QUIC Loss Detection and Congestion Control: https://www.rfc-editor.org/rfc/rfc9002.html
- IETF RFC 9000 — QUIC Transport: https://www.rfc-editor.org/rfc/rfc9000.html

## Paket 2 — Senior/Staff System Design & Databases: DynamoDB Partition Keys, Hot Partitions & Adaptive Capacity
**Süre:** 20–30 dk

### Konu anlatımı
DynamoDB tasarımında schema-first yerine access-pattern-first düşünmek yüksek getirili mental modeldir. Partition key yalnız uniqueness aracı değildir; verinin ve request load'un partition'lara nasıl dağıldığını belirleyen temel scaling primitive'dir. Düşük-cardinality veya aşırı popüler tek bir key hot partition oluşturabilir. Table toplam kapasitesi boş olsa bile tek partition/item fiziksel sınırları darboğaz olabilir.

Adaptive capacity uneven traffic'i otomatik olarak daha iyi karşılamaya çalışır ve on-demand/provisioned modlarda devrededir; fakat kötü key tasarımını sınırsız biçimde kurtaran sihir değildir. AWS dokümantasyonunda partition başına tasarım sınırı 3,000 read units/s ve 1,000 write units/s olarak verilir. Çok sıcak logical key için write sharding (`tenant#0..N`) throughput'u yayabilir; bunun bedeli read fan-out, aggregation ve daha karmaşık consistency/query mantığıdır. Sort key ise item collection içinde range/prefix access pattern'lerini taşır.

### Mental model
```text
request keys
   |
   +-- user#1 --------> partition A  HOT
   +-- user#2 --> partition B
   +-- user#3 --> partition C

hot logical key
   |
write-shard: user#1#0 ... user#1#N
   |       |             |
  P-A     P-B           P-C

trade-off: write spread <-> read fan-out
```

### Yüksek getirili mülakat soruları
- Partition key'i yalnız unique ID seçmek neden yetersizdir?
- Table kapasitesi varken neden throttling görebilirsin?
- Adaptive capacity neyi çözer, neyi çözmez?
- Write sharding hangi workload'da işe yarar?
- Composite key access pattern'i nasıl modelleyebilir?
- Staff: tenant skew ve celebrity-key problemi için migration'ı downtime olmadan nasıl yaparsın?

### Seviyeye göre cevap derinliği
Junior/Mid: partition key, sort key, Query vs Scan sezgisi. Senior: hot partition, capacity units, access patterns ve write sharding. Staff/Principal: skew ölçümü, secondary-index etkisi, migration/dual-write, cost ve consistency trade-off'ları.

### Kısa alıştırma
Tek bir `eventType=CLICK` partition key'ine saniyede çok yüksek write alan event tablosunu yeniden tasarla. En az iki key alternatifi yaz ve query maliyetini karşılaştır.

### Proje fikri
`dynamodb-hot-key-lab`: Zipf dağılımlı synthetic traffic üret; naive key ile sharded key'in throttling, latency ve read fan-out farkını ölçen load-test harness kur.

### Failure modes / trade-off / production
Low-cardinality key; timestamp'i monoton partition key yapmak; adaptive capacity'yi sınırsız sanmak; GSI key skew'ini unutmak; write sharding sonrası read fan-out maliyetini hesaba katmamak; yalnız average traffic'e göre tasarlamak. Production'da per-key/top-key distribution, throttled requests, consumed capacity, p95/p99 latency ve GSI davranışı birlikte izlenir.

- AWS — Burst and adaptive capacity: https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/burst-adaptive-capacity.html
