## Paket 1 — Senior Databases: Multicolumn B-tree Indexes & Skip Scan
**Süre:** 20–30 dk

### Konu anlatımı
B-tree çok kolonlu index'te kolon sırası yalnızca sözdizimi değildir; planner'ın index'in ne kadarını daraltabileceğini belirler. `(a,b,c)` index'inde leading kolonlardaki equality koşulları ve ilk equality olmayan kolondaki inequality genellikle taranacak index bölümünü sınırlar. PostgreSQL 18 ayrıca uygun cardinality ve predicate durumlarında skip scan optimizasyonuyla eksik leading equality için tekrar tekrar index search başlatabilir.

Mental model: index'i lexicographic telefon rehberi gibi düşün. `(tenant_id, created_at)` index'i tenant eşitliği + zaman aralığında çok güçlüdür; yalnız `created_at` filtresinde tüm yapı her zaman ideal değildir. Skip scan bu kuralı sihirli biçimde yok etmez; planner distinct leading değer sayısı ve maliyete göre karar verir.

### Mental model
```text
B-tree (a,b,c)
(a=1,b=1,...) ... (a=1,b=9,...)
(a=2,b=1,...) ... (a=2,b=9,...)

WHERE a=2 AND b>=7  -> dar contiguous range
WHERE b=7           -> leading a eksik
                         | planner uygun görürse
                         v
                 a=1,b=7 -> a=2,b=7 -> ...
                    repeated searches = skip scan
```

### Yüksek getirili mülakat soruları
1. Composite index kolon sırası neden önemlidir?
2. `(tenant_id, created_at)` hangi sorguları iyi destekler?
3. Covering index ile multicolumn search key aynı şey midir?
4. Skip scan ne zaman full index scan'den daha ucuz olabilir?
5. Neden her sorgu kombinasyonu için index eklemek kötü fikirdir?

### Seviye beklentisi
- **Mid:** leftmost/lexicographic modeli ve equality/range ayrımını anlatır.
- **Senior:** selectivity, EXPLAIN, write amplification ve skip-scan cost modelini tartışır.
- **Staff:** workload/index portfolio, storage/cache maliyeti ve schema/query contract'ını birlikte yönetir.

### Mini alıştırma
`orders(tenant_id,status,created_at,total)` için üç gerçek sorgu yaz ve en fazla iki index seç. Her sorgunun hangi index prefix'ini kullandığını açıkla.

### Proje fikri
`pg-index-lab`: milyon satırlık sentetik tabloda farklı composite index sıralarını ve skip-scan adaylarını `EXPLAIN (ANALYZE, BUFFERS)` ile karşılaştır.

### Failure modes / trade-off / production
Index kolon sırasını sezgiyle seçmek, yalnız query latency ölçüp write/storage maliyetini unutmak, low-cardinality leading kolonun etkisini ölçmemek, planner'ın skip scan yapacağını garanti sanmak, stale statistics ile yanlış çıkarım yapmak.

### Kaynaklar

## Paket 2 — Senior Backend/Observability: OpenTelemetry Context Propagation & Baggage
**Süre:** 20–30 dk

### Konu anlatımı
Distributed trace'in servisler arasında devam edebilmesi için span context process boundary'den taşınmalıdır. OpenTelemetry propagator modeli context'i HTTP headers veya message metadata gibi carrier'lara `inject`, karşı tarafta `extract` eder. Baggage ise trace context'ten ayrı, request boyunca taşınabilen key/value context'tir; span attribute'a otomatik olarak eşit değildir.

Baggage güvenlik sınırıdır: wire üzerinde taşınabilir, downstream loglanabilir ve built-in integrity garantisi yoktur. PII, credential veya authorization kararı baggage'a güvenerek taşınmamalıdır. Public ingress'te untrusted propagation header'larını sanitize/ignore etmek; egress'te internal context sızıntısını kontrol etmek gerekir.

### Mental model
```text
Service A Context
 trace/span + baggage
       |
       | inject(headers)
       v
HTTP / queue carrier
       |
       | extract(headers)
       v
Service B Context -> child span

baggage != authorization token
baggage != span attributes unless explicitly copied
```

### Yüksek getirili mülakat soruları
1. Trace context process boundary'yi nasıl geçer?
2. Inject ve extract ne yapar?
3. Baggage ile span attribute farkı nedir?
4. Neden PII/API key baggage'a konmamalıdır?
5. Async queue consumer'da parent context'i nasıl devam ettirirsin?
6. Untrusted trace headers hangi riskleri yaratır?

### Seviye beklentisi
- **Mid:** trace/span/context ve header propagation akışını açıklar.
- **Senior:** async boundaries, baggage cardinality, trust boundary ve sampling etkilerini tartışır.
- **Staff:** organization-wide propagation policy, egress filtering ve telemetry governance tasarlar.

### Mini alıştırma
HTTP -> queue -> worker zincirinde context'in nerede inject/extract edildiğini çiz; public ingress ve third-party egress güvenlik kontrollerini ekle.

### Proje fikri
`otel-propagation-lab`: iki HTTP servis + queue worker; W3C trace context'i sürdür, güvenli bir baggage alanını span attribute'a kontrollü kopyala ve dış egress'te temizle.

### Failure modes / trade-off / production
Context kaybetmek, background task'i yanlış parent'a bağlamak, baggage'a yüksek-cardinality/PII koymak, untrusted header'ı doğrulanmış business identity sanmak, her attribute'u bütün servis zincirine propagate etmek.

### Kaynaklar
- https://opentelemetry.io/docs/specs/otel/context/api-propagators/
- https://opentelemetry.io/docs/concepts/context-propagation/
- https://opentelemetry.io/docs/concepts/signals/baggage/

## Paket 3 — Senior/Staff Cloud/SRE: Kubernetes HPA Control Loop, Stabilization & Thrashing
**Süre:** 20–30 dk

### Konu anlatımı
HorizontalPodAutoscaler bir control loop'tur: gözlenen metriği hedefle karşılaştırır ve desired replica count hesaplar. Autoscaling yalnız threshold değildir; measurement delay, pod startup time, readiness, metric noise ve downstream capacity ile dinamik sistem oluşturur. `autoscaling/v2` behavior alanı scale-up/down policy, stabilization window ve tolerance ile replica değişiminin hızını ve flapping davranışını kontrol eder.

Scale-down stabilization, yakın geçmişte hesaplanan desired state'leri dikkate alıp agresif küçülmeyi yumuşatabilir. Fakat HPA capacity yaratamaz: node/GPU yoksa pod Pending kalır; DB connection veya downstream quota dar boğazsa replica artırmak sistemi daha kötü yapabilir. Queue depth gibi external metric'lerde backlog per worker ve drain time daha anlamlı olabilir.

### Mental model
```text
 traffic -> pods -> latency/CPU/queue
              ^             |
              |             v
          replicas <--- HPA controller
                         compare
                      observed/target

Fast scale-up: overload'u yakala
Slow/stable scale-down: flapping'i azalt
But: replicas -> downstream load da artabilir
```

### Yüksek getirili mülakat soruları
1. HPA'yı neden feedback control loop olarak düşünmeliyiz?
2. CPU metric'i hangi workload'larda kötü scaling signal olabilir?
3. Stabilization window hangi problemi çözer?
4. Scale-up hızlı, scale-down yavaş tasarımının gerekçesi nedir?
5. HPA + Cluster Autoscaler etkileşiminde hangi gecikmeler oluşur?
6. Replica artırmak DB outage'ını neden büyütebilir?

### Seviye beklentisi
- **Mid:** target metric -> desired replicas akışını anlatır.
- **Senior:** readiness, startup, stabilization, custom/external metrics ve downstream bottleneck'i tartışır.
- **Staff:** workload + node autoscaling, SLO, cost, capacity ceiling ve failure containment'i birlikte tasarlar.

### Mini alıştırma
Trafiği 2 dakikada 5 kat artan, pod startup'ı 45 saniye süren API için scale-up/down policy ve stabilization yaklaşımı öner. DB maksimum 200 connection ise constraint'i ekle.

### Proje fikri
`hpa-control-lab`: load generator + demo API + HPA; CPU ve queue-depth sinyallerini karşılaştır, stabilization değerleriyle replica/latency grafikleri üret.

### Failure modes / trade-off / production
Noisy metric ile thrashing, startup süresini yok saymak, Pending pod'u capacity sanmak, downstream quota'yı hesaba katmamak, min/max replica'yı capacity testinden bağımsız seçmek, yalnız ortalama CPU'ya bakmak.

### Kaynaklar
- https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/
