## Paket 1 — Senior Databases/Data Engineering: PostgreSQL Logical Replication, Slots & Failover
**Süre:** 20–30 dk

### Konu anlatımı
PostgreSQL logical replication, fiziksel block/WAL kopyalamak yerine yayınlanan tabloların mantıksal değişikliklerini publisher'dan subscriber'a taşır. `PUBLICATION` hangi tabloların ve hangi DML türlerinin yayınlanacağını tanımlar; `SUBSCRIPTION` publisher'a bağlanır ve normalde publisher tarafında bir logical replication slot kullanır. Slot, subscriber henüz tüketmemiş değişikliklerin kaybolmamasını sağlar; bunun karşılığı subscriber uzun süre geride kalırsa publisher üzerinde WAL retention ve disk baskısıdır.

Initial sync ile steady-state change streaming farklı aşamalardır. UPDATE/DELETE yayınlamak için subscriber'ın satırı eşleyebilmesi gerekir; `REPLICA IDENTITY` bu yüzden önemlidir. PostgreSQL 18'de logical slot'lar fiziksel standby'a senkronize edilerek publisher failover sonrasında subscription'ın yeni primary üzerinden devam etmesi sağlanabilir; fakat slot sync asenkron olduğundan failover readiness ayrıca doğrulanmalıdır.

### Mental model
```text
Publisher
 table -> WAL -> logical decoding -> publication
                    |
             replication slot
             retained position
                    |
                    v
               Subscriber
             apply worker -> table

slow subscriber -> slot lag -> retained WAL -> disk pressure
```

### Yüksek getirili mülakat soruları
1. Physical ve logical replication arasındaki temel fark nedir?
2. Publication ile subscription hangi sorumlulukları ayırır?
3. Replication slot neden gereklidir ve hangi production riskini yaratır?
4. UPDATE/DELETE için `REPLICA IDENTITY` neden önemlidir?
5. Initial table sync ile steady-state apply nasıl ayrılır?
6. Publisher failover sırasında logical replication continuity nasıl korunur?

### Seviye beklentisi
- **Mid:** publication/subscription ve async replication fikrini açıklar.
- **Senior:** slot retention, replica identity, lag, initial sync ve conflict failure mode'larını bağlar.
- **Staff:** failover-ready topology, slot monitoring, schema-change compatibility ve backfill/runbook tasarlar.

### Mini alıştırma
Subscriber 6 saat durmuş durumda. Publisher disk kullanımı hızla artıyor. Kontrol edeceğin dört sinyali ve güvenli recovery sırasını yaz.

### Proje fikri
`pg-logical-repl-lab`: iki PostgreSQL instance arasında publication/subscription kur; subscriber'ı durdur, slot lag/WAL büyümesini ölç, sonra kontrollü catch-up yap.

### Failure modes / trade-off / production
Replication slot'u unutmak; subscriber lag için disk alarmı koymamak; DDL'nin otomatik replike edildiğini varsaymak; replica identity eksikliğini geç fark etmek; initial copy bandwidth'ini production kapasitesine katmamak; failover slot readiness'i test etmemek.

## Paket 2 — Senior/Staff Cloud & Networking: Kubernetes Gateway API, Roles & Route Attachment
**Süre:** 20–30 dk

### Konu anlatımı
Gateway API, Kubernetes service networking için extensible, role-oriented ve protocol-aware bir API ailesidir. Ingress'in tek kaynakta topladığı altyapı ve uygulama routing sorumluluklarını daha açık kaynaklara böler: `GatewayClass` tipik olarak platform/infra sağlayıcısının controller sınıfını; `Gateway` listener ve network entry point'i; `HTTPRoute`, `GRPCRoute`, `TCPRoute` veya `UDPRoute` ise uygulama trafik kurallarını temsil eder.

Kritik mental model ownership separation'dır. Platform ekibi Gateway'i yönetebilirken uygulama ekibi kendi Route'unu yönetebilir. Route'un Gateway'e referans vermesi tek başına attachment garantisi değildir; listener'ın `allowedRoutes`, namespace/policy sınırları ve controller status/conditions sonucu belirler. Bu model multi-team cluster'da least privilege ve reusable shared gateways için değerlidir.

Gateway API bağımsız sürümlenen bir add-on'dur. 3 Ağustos 2026'da duyurulan v1.6 ile TCPRoute ve UDPRoute Standard channel'a mezun oldu; experimental API'ler ayrı `gateway.networking.x-k8s.io` grubuna taşınmaya başladı. Production'da controller'ın desteklediği feature/conformance seti kontrol edilmelidir.

### Mental model
```text
Platform owner:
GatewayClass -> Gateway -> listeners
                         ^
                         | attach if allowed
Application owner:       |
HTTPRoute / GRPCRoute ---+
        |
        v
     Service
```

### Yüksek getirili mülakat soruları
1. Gateway API neden yalnızca yeni bir Ingress syntax'ı değildir?
2. GatewayClass, Gateway ve Route ownership'i nasıl ayırır?
3. Route attachment neden iki taraflı policy problemi sayılabilir?
4. Shared Gateway multi-tenant sistemde hangi riskleri getirir?
5. Controller conformance neden API sürümünden ayrı kontrol edilmelidir?
6. Ingress'ten Gateway API'ye migration'ı nasıl kademelendirirsin?

### Seviye beklentisi
- **Mid:** Gateway/Route ilişkisini açıklar.
- **Senior:** listener, attachment, namespace policy, TLS ve controller behavior'ını bağlar.
- **Staff:** multi-team ownership, migration, conformance, blast radius ve shared-infra guardrail'ları tasarlar.

### Mini alıştırma
Platform ekibinin `payments.example.com` listener'ını yönettiği, payments namespace ekibinin route yazdığı bir ownership modeli çiz; yanlış namespace attachment'ını nasıl engelleyeceğini belirt.

### Proje fikri
`gateway-api-lab`: tek shared Gateway altında iki namespace için HTTPRoute oluştur; allowedRoutes policy, TLS ve weighted routing senaryolarını test et.

### Failure modes / trade-off / production
API objesi accepted görünmeden trafiğin hazır olduğunu varsaymak; controller feature support'u kontrol etmemek; cross-namespace attachment'ı gevşek bırakmak; shared Gateway blast radius'unu küçümsemek; migration'da DNS/TLS/observability parity testi yapmamak.

### Kaynaklar
- https://gateway-api.sigs.k8s.io/
- https://kubernetes.io/docs/concepts/services-networking/gateway/
- https://kubernetes.io/blog/2026/08/03/gateway-api-v1-6-release/

## Paket 3 — Engineering Manager/CTO: Error Budgets as Product & Reliability Governance
**Süre:** 20–30 dk

### Konu anlatımı
SLO, kullanıcı açısından önemli bir service level indicator için hedeflenen güvenilirlik seviyesidir. Error budget ise hedefin izin verdiği başarısızlık payını yönetilebilir bir karar bütçesine çevirir. Örneğin 30 günlük %99.9 availability hedefi teorik olarak yaklaşık %0.1 başarısızlık alanı bırakır; fakat gerçek policy yalnız dakika hesabı değildir: hangi SLI'ın ölçüldüğü, hangi event'lerin good/bad sayıldığı, pencere ve burn rate karar mekanizmasını belirler.

Leadership açısından amaç 'zero incidents' değildir. Error budget product velocity ile reliability investment arasında ortak, önceden tanımlanmış bir dil kurar. Budget sağlıklıyken kontrollü risk alınabilir; hızla tüketiliyorsa release policy sıkılaştırılabilir, reliability work öne çekilebilir. Kötü kullanımda metrik cezalandırma aracına dönüşür ve ekipler ölçümü optimize etmeye başlar.

### Mental model
```text
user journey -> SLI -> SLO target
                        |
                        v
                  error budget
                 /            \
          budget healthy    burn too fast
             |                 |
        ship/experiment   reliability focus
```

### Yüksek getirili mülakat soruları
1. SLA, SLO ve SLI farkı nedir?
2. Error budget neden sadece downtime dakikası değildir?
3. Burn rate neyi anlatır?
4. Product velocity ile reliability çatışmasını nasıl yönetirsin?
5. Error-budget policy nasıl Goodhart etkisine girer?
6. CTO olarak hangi durumda feature freeze uygular, hangi durumda uygulamazsın?

### Seviye beklentisi
- **Senior:** doğru SLI/SLO ve budget hesabını açıklar.
- **Staff/EM:** release policy, incident review ve reliability backlog ile bağlar.
- **CTO:** customer tier, revenue/risk, compliance, org incentives ve yatırım kararlarını aynı governance modelinde yönetir.

### Mini alıştırma
Checkout API için availability ve latency SLI'ları seç; 30 günlük SLO ve budget-exhaustion sonrası üç aşamalı policy yaz.

### Proje fikri
`error-budget-dashboard`: request-based SLI, rolling-window budget ve multi-window burn-rate alarmı üret; deploy annotation'larıyla ilişkilendir.

### Failure modes / trade-off / production
%100 SLO seçmek; user journey yerine kolay ölçülen infra metriğini SLI yapmak; budget'ı bireysel performans metriğine çevirmek; tüm müşteri tier'larına aynı hedefi dayatmak; burn rate yerine yalnız kalan budget yüzdesine bakmak.
