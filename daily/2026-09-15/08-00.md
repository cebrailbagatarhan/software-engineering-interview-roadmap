## Paket 1 — Senior Databases: PostgreSQL VACUUM, HOT Updates & Visibility Map
**Süre:** 20–30 dk

### Konu anlatımı
PostgreSQL MVCC nedeniyle UPDATE/DELETE sonrasında eski tuple sürümleri bırakabilir. Standart `VACUUM` bunların kapladığı alanı yeniden kullanılabilir hale getirir, planner statistics/visibility bilgisinin bakımına katkı sağlar ve transaction-ID wraparound riskine karşı gereklidir. `VACUUM FULL` daha fazla alan geri kazanabilir ama tabloyu yeniden yazar ve `ACCESS EXCLUSIVE` lock gerektirir; rutin çözüm değildir.

Visibility Map her heap page için all-visible/all-frozen bilgisini taşır. All-visible page, index-only scan sırasında heap'e gidip visibility kontrolü yapma ihtiyacını kaldırabilir. Data modification VM bitini temizleyebilir; VACUUM güvenli olduğunda yeniden set eder.

HOT (Heap-Only Tuple) update, indexlenen kolonlar değişmediğinde ve aynı page'de yeterli alan olduğunda gereksiz yeni index entry maliyetini azaltabilir. Düşük `fillfactor` HOT ihtimalini artırabilir fakat daha fazla disk/cache footprint trade-off'u yaratır.

### Mental model
```text
UPDATE row
 old tuple -> new tuple
     |          |
 dead later     +-- indexed columns unchanged + page space?
                     -> HOT candidate

VACUUM -> reusable space + VM maintenance + wraparound protection
                     |
                     v
              all-visible page
                     |
              index-only scan
              may skip heap fetch
```

### Yüksek getirili mülakat soruları
1. PostgreSQL neden dead tuple üretir?
2. `VACUUM` ile `VACUUM FULL` farkı nedir?
3. Visibility Map index-only scan'i nasıl hızlandırır?
4. HOT update hangi koşullarda avantaj sağlar?
5. Autovacuum geride kalırsa hangi production belirtileri görülür?
6. Fillfactor düşürmenin maliyeti nedir?

### Seviye beklentisi
- **Mid:** MVCC, dead tuple ve autovacuum ilişkisini açıklar.
- **Senior:** HOT, VM, index-only scan, bloat ve vacuum I/O trade-off'unu bağlar.
- **Staff:** write-heavy workload için per-table autovacuum/fillfactor tuning, telemetry ve capacity etkisini tasarlar.

### Mini alıştırma
Write-heavy `accounts` tablosunda indexed olmayan `last_seen_at` saniyede sık güncelleniyor. HOT oranını yükseltmek için iki değişiklik ve izleyeceğin üç metriği yaz.

### Proje fikri
`pg-vacuum-lab`: farklı fillfactor değerleriyle update workload çalıştır; `n_tup_hot_upd`, dead tuples, table/index size ve index-only scan heap fetch sayılarını karşılaştır.

### Failure modes / trade-off / production
Autovacuum'u kapatmak; bloat görünce doğrudan `VACUUM FULL` çalıştırmak; vacuum I/O etkisini yok saymak; fillfactor'ı körlemesine düşürmek; indexlenen her kolonun update maliyetini unutmak; wraparound'u yalnız disk-space problemi sanmak.

## Paket 2 — Senior/Staff Cloud/SRE: Kubernetes PodDisruptionBudget, Eviction & Safe Drain
**Süre:** 20–30 dk

### Konu anlatımı
PodDisruptionBudget (PDB), bir pod grubunda voluntary disruption sırasında eşzamanlı unavailable replica miktarını sınırlar. `minAvailable` veya `maxUnavailable` ile ifade edilir. `kubectl drain` gibi Eviction API kullanan işlemler PDB'yi dikkate alır; PDB tüm outage türlerine karşı availability garantisi değildir ve node crash gibi involuntary disruption'ı engellemez.

PDB ile Deployment rollout stratejisi farklı kontrol düzlemleridir. Çok katı PDB node maintenance'i kilitleyebilir; çok gevşek PDB bakım sırasında quorum veya serving capacity kaybına yol açabilir. Stateful/quorum workload'larda replica sayısı, failure domain, termination grace, readiness ve application-level quorum birlikte düşünülmelidir.

### Mental model
```text
replicas = 5, minAvailable = 4

healthy: [P][P][P][P][P]
                 |
             drain/evict
                 v
allowed unavailable <= 1

PDB -> voluntary eviction budget
NOT -> node crash prevention / universal HA guarantee
```

### Yüksek getirili mülakat soruları
1. Voluntary ve involuntary disruption farkı nedir?
2. PDB neden node crash'i engellemez?
3. `minAvailable` ile `maxUnavailable` nasıl seçilir?
4. PDB node drain'i neden sonsuza yakın bloklayabilir?
5. Deployment rolling-update ayarları ile PDB nasıl etkileşir?
6. 3-node quorum service için PDB tek başına yeterli midir?

### Seviye beklentisi
- **Mid:** PDB'nin amacını ve drain davranışını açıklar.
- **Senior:** readiness, termination grace, rollout ve maintenance trade-off'unu bağlar.
- **Staff:** quorum/failure-domain-aware disruption policy, maintenance automation ve alerting tasarlar.

### Mini alıştırma
5 replica API için en az 4 healthy instance zorunlu. PDB seç, aynı anda iki node drain denemesinde beklenen davranışı açıkla.

### Proje fikri
`pdb-drain-lab`: 5-replica Deployment üzerinde farklı PDB'lerle drain simülasyonu yap; availability, drain completion time ve blocked eviction ölç.

### Failure modes / trade-off / production
PDB'yi HA garantisi sanmak; selector hatası; readiness'i yanlış tanımlamak; `minAvailable: 100%` ile bakım deadlock'u; quorum semantiğini replica sayısına indirgemek; termination süresini capacity planına katmamak.

### Kaynaklar
- https://kubernetes.io/docs/tasks/run-application/configure-pdb/
- https://kubernetes.io/docs/concepts/scheduling-eviction/api-eviction/
- https://kubernetes.io/docs/reference/kubernetes-api/policy-resources/pod-disruption-budget-v1/

## Paket 3 — Senior/Staff ML/AI/LLM: Prompt Caching, Prefix Stability & Cost/Latency Design
**Süre:** 20–30 dk

### Konu anlatımı
LLM uygulamasında uzun ve tekrar eden instruction/tool/schema/context prefix'leri her istekte yeniden işlemek latency ve input-token maliyetini büyütebilir. Prompt caching, daha önce işlenmiş ortak prefix hesaplamasını yeniden kullanarak bu maliyeti azaltabilir. Temel tasarım ilkesi stable/reusable içeriği prompt'un başına, request-specific değişken içeriği sona koymaktır.

Cache hit bir correctness garantisi değildir; yalnız inference ekonomisi/latency optimizasyonudur. Prompt veya tool schema sık değişirse prefix reuse düşebilir. Production'da `cached_tokens`, uncached input, p50/p95 latency, request cost ve hit ratio birlikte izlenmelidir. 2026 GPT-5.6 builder rehberi cache TTL'nin model ailesinde en az 30 dakikaya uzatıldığını ve deterministic cache breakpoints/prompt cache key kullanımının hit rate ve latency'yi iyileştirebildiğini belirtiyor; model/API ayrıntıları değişebileceği için canlı dokümantasyon esas alınmalıdır.

### Mental model
```text
[stable system + tools + shared context] [request-specific tail]
                 |
           reusable prefix
                 |
          prompt cache hit
          /              \
 lower input work      same task semantics
 latency/cost gain     correctness unchanged
```

### Yüksek getirili mülakat soruları
1. Prompt caching ile semantic/RAG cache farkı nedir?
2. Prefix stability neden önemlidir?
3. Cache hit quality/correctness'i değiştirir mi?
4. Tool schema sırası/değişimi cache ekonomisini nasıl etkileyebilir?
5. Hangi metriklerle cache optimizasyonunu doğrularsın?
6. Multi-tenant sistemde cache key ve privacy sınırlarını nasıl düşünürsün?

### Seviye beklentisi
- **Mid:** repeated prefix ve cached token fikrini açıklar.
- **Senior:** prompt layout, cache observability ve cost/latency trade-off'unu kurar.
- **Staff:** workload segmentation, tenant isolation, cache-key strategy, rollout ve model-version migration ekonomisini tasarlar.

### Mini alıştırma
20k token ortak instruction/context + 1k token request-tail kullanan agent için prefix'i yeniden düzenle; hit/miss karşılaştırmasında izleyeceğin metrikleri yaz.

### Proje fikri
`prompt-cache-bench`: aynı agent workload'unu stable-prefix ve randomized-prefix varyantlarıyla çalıştır; cached tokens, latency ve request maliyetini karşılaştır.

### Failure modes / trade-off / production
Cache'i correctness katmanı sanmak; dynamic veriyi prefix'in başına koymak; cache hit telemetry toplamamak; tenant/security sınırlarını düşünmemek; model değişiminde eski maliyet varsayımlarını sürdürmek; sırf hit oranı için stale business context'i sabitlemek.
