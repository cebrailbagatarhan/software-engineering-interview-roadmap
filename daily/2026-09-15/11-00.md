## Paket 1 — Senior Backend/Runtime: CPython Free-Threading, GIL & Thread Safety
**Süre:** 20–30 dk

### Konu anlatımı
CPython'ın klasik build'inde Global Interpreter Lock (GIL), aynı process içinde Python bytecode çalıştıran thread'leri büyük ölçüde serialize eder. Bu yüzden thread kullanmak I/O concurrency için faydalı olsa da CPU-bound Python kodunda otomatik olarak çok çekirdekli paralellik sağlamaz. PEP 703 ile GIL'in opsiyonel olduğu free-threaded build yolu açıldı; Python 3.14'te free-threading Phase II/supported statüsüne geçti. Bu, "artık lock gerekmez" anlamına gelmez: tam tersine application-level shared mutable state için race condition tasarımı daha görünür hale gelir.

Free-threaded runtime'da interpreter'ın kendi object safety mekanizmaları, biased/deferred reference counting ve allocator değişiklikleri vardır. Ayrıca üçüncü parti C extension uyumluluğu kritik production sınırıdır; bazı extension'lar GIL'i yeniden etkinleştirebilir. Migration kararı benchmark, dependency inventory ve race testing ile verilmelidir.

### Mental model
```text
Classic CPython:
T1 -- Python bytecode --\
T2 -- Python bytecode ----> [ GIL ] -> interpreter
T3 -- Python bytecode --/

Free-threaded build:
T1 ----\
T2 -----+--> concurrent execution
T3 ----/          |
                  +--> shared mutable state still needs synchronization
```

### Yüksek getirili mülakat soruları
1. GIL neyi serialize eder, neyi etmez?
2. Thread'ler neden I/O-bound işlerde yine faydalıdır?
3. Free-threading CPU-bound workload için hangi fırsatı açar?
4. GIL kalkınca application lock'ları neden gereksiz olmaz?
5. C extension uyumluluğu migration'ı nasıl etkiler?
6. Process pool, classic threads ve free-threaded threads arasında nasıl seçim yaparsın?

### Seviye beklentisi
- **Junior/Mid:** thread, process, concurrency ve parallelism ayrımını açıklar.
- **Senior:** shared state, lock contention, extension compatibility ve benchmark tasarımını bağlar.
- **Staff:** fleet migration, dependency certification, rollback ve observability planı kurar.

### Mini alıştırma
CPU-bound bir image-processing servisi için classic threads, process pool ve free-threaded build seçeneklerini throughput, memory ve failure isolation açısından karşılaştır.

### Proje fikri
`free-threading-bench`: aynı CPU workload'unu classic CPython, process pool ve free-threaded build ile çalıştır; throughput, RSS ve CPU utilization ölç.

### Failure modes / trade-off / production
"GIL var, race olmaz" varsayımı; extension uyumluluğunu kontrol etmemek; microbenchmark'ı production workload sanmak; shared-state contention'ı gizlemek; tek-thread overhead'ini ölçmemek.

## Paket 2 — Senior Observability: OpenTelemetry Database Semantic Conventions, Cardinality & Privacy
**Süre:** 20–30 dk

### Konu anlatımı
Tracing yalnızca span üretmek değildir; farklı servis ve dillerde aynı operasyonu aynı semantik ile ifade etmek gerekir. OpenTelemetry Semantic Conventions database client operasyonları için `db.system.name`, `db.namespace`, `db.operation.name`, `db.query.summary` gibi ortak alanlar tanımlar. Database span'ı tipik olarak `CLIENT` kind'dır ve caller'ın gördüğü logical operation süresini kapsamalıdır.

Observability ile privacy/cardinality arasında doğrudan trade-off vardır. Raw query text literal veya PII taşıyabilir; güncel convention non-parameterized query text'in sanitization olmadan default toplanmamasını söyler. Query parameter değerleri de default capture edilmemelidir. `db.query.summary` düşük-cardinality grouping key olarak daha güvenli ve operasyonel olarak değerlidir. Semantic convention migration'larında eski/yeni attribute setlerini kontrollü geçirmek dashboard ve alert kırılmasını azaltır.

### Mental model
```text
DB call
  |
  v
CLIENT span
  |-- db.system.name
  |-- db.operation.name
  |-- db.query.summary   -> low-cardinality grouping
  `-- db.query.text      -> sanitize / privacy risk

telemetry value <---- trade-off ----> cost + PII + cardinality
```

### Yüksek getirili mülakat soruları
1. Semantic conventions neden gereklidir?
2. Database span neden çoğunlukla CLIENT kind'dır?
3. `db.query.summary` ile `db.query.text` farkı nedir?
4. Query parameter'larını neden default capture etmezsin?
5. High-cardinality telemetry hangi production maliyetlerini yaratır?
6. Convention version migration'ını dashboard kırmadan nasıl yaparsın?

### Seviye beklentisi
- **Mid:** trace/span/attribute ve CLIENT span fikrini açıklar.
- **Senior:** privacy, sanitization, cardinality ve sampling'i bağlar.
- **Staff:** organization-wide telemetry schema governance ve migration stratejisi tasarlar.

### Mini alıştırma
Bir checkout servisindeki PostgreSQL sorgusu için hangi span attribute'larını toplayacağını ve hangilerini privacy nedeniyle reddedeceğini yaz.

### Proje fikri
`otel-db-lab`: PostgreSQL client instrumentation kur; query summary, sanitized text ve high-cardinality varyantlarının telemetry hacmini karşılaştır.

### Failure modes / trade-off / production
Raw SQL/parameter ile PII sızdırmak; user ID'yi metric label yapmak; her retry için anlamsız duplicate logical span üretmek; semconv upgrade'inde dashboard contract'ını kırmak; telemetry maliyetini ölçmemek.

- https://opentelemetry.io/docs/specs/semconv/db/sql/
- https://opentelemetry.io/docs/specs/otel/trace/api/

## Paket 3 — Senior Data Engineering: Spark Shuffle, Data Skew & Adaptive Query Execution
**Süre:** 20–30 dk

### Konu anlatımı
Spark'ta narrow transformation'larda bir output partition sınırlı sayıda input partition'a bağlıdır; join, groupBy ve repartition gibi wide operasyonlar ise veriyi executor'lar arasında yeniden dağıtan shuffle boundary oluşturur. Shuffle network I/O, serialization, disk spill ve scheduler maliyeti getirdiği için büyük job'larda temel performans sınırlarından biridir.

Data skew, bazı partition'ların diğerlerinden çok daha büyük olmasıdır. Ortalama task süresi iyi görünürken birkaç straggler stage completion'ı belirleyebilir. Çözümler workload'a göre broadcast join, partition-key iyileştirme, salting veya skew-aware optimization olabilir. Adaptive Query Execution (AQE) runtime statistics ile planı execution sırasında uyarlayarak partition coalescing, join strategy değişimi ve skew handling gibi kararları iyileştirebilir; fakat kötü data modelini sihirli biçimde düzeltmez.

### Mental model
```text
Stage A partitions
[p1][p2][p3][p4]
      |
   shuffle by key
      v
Stage B
[small][small][HUGE][small]
               |
               `--> straggler -> stage latency

AQE: runtime stats -> adapt partitions / joins / skew handling
```

### Yüksek getirili mülakat soruları
1. Narrow ve wide transformation farkı nedir?
2. Shuffle neden pahalıdır?
3. Data skew'u Spark UI'da hangi sinyallerle görürsün?
4. Broadcast join ne zaman iyi, ne zaman tehlikelidir?
5. Salting hangi problemi çözer ve hangi karmaşıklığı ekler?
6. AQE neyi optimize eder, neyi çözemez?

### Seviye beklentisi
- **Mid:** partition, stage, shuffle ve join temelini açıklar.
- **Senior:** skew, spill, broadcast ve partition sizing'i teşhis eder.
- **Staff:** workload class, cost, cluster sizing ve data-layout kararlarını birlikte optimize eder.

### Mini alıştırma
Bir join stage'inde median task 20 sn, tek task 14 dk sürüyor. Kontrol edeceğin metrikleri ve üç olası mitigation'ı sırala.

### Proje fikri
`spark-skew-lab`: Zipf dağılımlı key üret; normal join, broadcast, salting ve AQE varyantlarında p95 task time, shuffle bytes ve total runtime ölç.

### Failure modes / trade-off / production
Partition sayısını körlemesine artırmak; broadcast threshold'u memory hesabı olmadan büyütmek; skew'u yalnızca CPU problemi sanmak; spill/network metriklerini atlamak; AQE'yi kötü key tasarımının yerine koymak.
