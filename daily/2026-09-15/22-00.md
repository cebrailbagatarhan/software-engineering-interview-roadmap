## Paket 1 — Senior/Staff Backend & Runtime: Go 1.26 Green Tea GC, Locality & GC CPU
**Süre:** 20–30 dk

### Konu anlatımı
Go'nun garbage collector'ı tracing mark-sweep ailesindedir: root'lardan erişilebilir heap object graph'ını tarar, erişilemeyen alanı daha sonra yeniden kullanılabilir hale getirir. Klasik sezgide work list object ağırlıklıdır. Go 1.26 ile varsayılan olan Green Tea yaklaşımının ana fikri ise marking/scanning işini object object zıplatmak yerine page locality etrafında düzenlemektir.

Green Tea whole page'i work item gibi ele alır; page üzerindeki `seen` ve `scanned` metadata ile hangi object'lerin gerçekten taranacağını takip eder. Page'leri FIFO benzeri sırada bekletmek aynı page üzerinde birden fazla erişilebilir object'in birikmesini sağlar. Böylece pointer chasing sırasında cache locality iyileşebilir, work-list pressure ve contention azalabilir. Yeni amd64 platformlarında küçük-object scanning için vector instructions da kullanılabilir.

Go 1.26 release notes gerçek workload'a bağlı olmak üzere GC-heavy programlarda GC overhead için yaklaşık %10–40 azalma beklendiğini belirtir; bu uygulamanın toplam CPU'sunun %10–40 düşeceği anlamına gelmez. Örneğin toplam CPU'nun yalnız %10'u GC ise, GC maliyetindeki %20 düşüş kabaca toplam CPU'da %2 mertebesindedir. Optimization değerlendirmesinde GC CPU fraction, allocation rate, heap profile, pause/tail latency ve application throughput birlikte ölçülmelidir.

### Mental model
```text
roots
  |
  v
reachable objects spread over heap pages

old intuition:  obj -> obj -> obj -> obj
                random-ish pointer chasing

Green Tea:
root -> mark object on page A
                 |
            enqueue PAGE A
                 |
       accumulate seen objects
                 |
        scan page-local batch
           /           \
       page B         page C

locality ↑ -> cache use ↑
work-list pressure ↓
GC CPU may ↓, workload-dependent
```

### İçeride ne oluyor?
Tracing GC correctness değişmez: unreachable object canlı sayılmamalı ve reachable object kaybedilmemelidir. Değişen önemli nokta traversal/work scheduling ve metadata locality'dir. Page batching, modern cache hierarchy ve wide vector registers ile daha uyumlu düzenli scanning fırsatı yaratır. Ancak heap graph'ı page başına sürekli tek object taratıyorsa batching getirisi düşebilir.

### Yüksek getirili mülakat soruları
- Mark-sweep collector'ın temel correctness invariant'ı nedir?
- Green Tea neden object yerine page locality üzerinden iş planlıyor?
- FIFO page queue locality'yi nasıl iyileştirebilir?
- GC overhead %20 düştü demek neden process CPU %20 düştü demek değildir?
- Allocation rate ile GC CPU arasında nasıl ilişki beklersin?
- Staff: yeni GC'yi production fleet'te nasıl canary eder ve regression kriterini nasıl tanımlarsın?

### Seviyeye göre cevap derinliği
Mid: heap, root, reachable/unreachable, mark-sweep. Senior: allocation rate, page locality, cache behavior, GC CPU ve benchmark yorumlama. Staff/Principal: representative workload, canary, p99/CPU/RSS regression budget, architecture-specific vectorization ve rollback/opt-out stratejisi.

### Kısa alıştırma
Bir servis CPU'sunun %15'ini GC'de harcıyor. Green Tea GC time'ı %30 azaltırsa diğer maliyetler sabit varsayımıyla toplam CPU için yaklaşık üst-seviye kazancı hesapla. Sonra bu hesabın production'da neden yalnız tahmin olduğunu üç maddeyle açıkla.

### Proje fikri
`go-gc-ab-lab`: allocation-heavy ve pointer-heavy iki workload oluştur; Go 1.26 Green Tea ile opt-out build'i karşılaştır. CPU profile, GC CPU, allocation rate, RSS, throughput ve p99 latency raporla.

### Failure modes / trade-off / production
Microbenchmark'i fleet sonucu sanmak; GC yüzde kazancını toplam CPU kazancı diye raporlamak; RSS/latency regression'ını yalnız throughput yüzünden kaçırmak; farklı CPU architecture'larını tek cohort saymak; allocation source'larını profile etmeden collector tuning'e koşmak. Production rollout'ta binary/runtime version, CPU architecture ve workload sınıfına göre segmentasyon yap.

## Paket 2 — Mid/Senior Frontend: Web Locks API, Multi-Tab Coordination & Deadlock Discipline
**Süre:** 20–30 dk

### Konu anlatımı
Modern web uygulamasının aynı origin altında birden fazla tab veya worker instance'ı aynı local resource'u kullanabilir: IndexedDB sync, token refresh, background migration veya cache rebuild. JavaScript event loop tek execution context içinde race'leri azaltıyor gibi görünse de iki tab birbirinden bağımsız context'tir. Web Locks API aynı origin içindeki tab/worker'ların isimlendirilmiş logical resource için asynchronous lock edinerek koordinasyon kurmasını sağlar.

`navigator.locks.request(name, callback)` lock verilene kadar request'i queue'lar; callback'in async işi tamamlandığında lock otomatik bırakılır. Varsayılan mode `exclusive`'dir; `shared` mode birden fazla reader benzeri kullanım için seçilebilir. API HTTPS secure context gerektirir ve Web Worker içinde de kullanılabilir. Leader-election benzeri kullanımda tüm tab'lar `net_db_sync` lock'unu ister; lock'u alan tab sync işini yürütür.

Bu API distributed lock değildir: browser/origin scope'unda coordination primitive'dir. Server-side global uniqueness, cross-device mutual exclusion veya durable ownership garantisi vermez. Birden çok lock nested ve farklı sırada istenirse klasik deadlock üretilebilir; ordering, nesting'den kaçınma ve bounded timeout/cancellation tasarımı önemlidir.

### Mental model
```text
same origin

Tab A ---- request("sync") ----+
Tab B ---- request("sync") ----+--> lock queue
Worker --- request("sync") ----+
                                |
                         exclusive owner
                                |
                           do async work
                                |
                        callback completes
                                |
                         automatic release
                                v
                           next waiter

NOT: cross-device / server distributed lock
```

### İçeride ne oluyor?
Lock adı uygulamanın seçtiği abstract resource identity'sidir. Exclusive lock aynı isimde başka compatible olmayan acquisition'ı bekletir; shared mode compatible reader'ların birlikte ilerlemesini sağlayabilir. `LockManager.query()` held ve pending lock'ları diagnostic amaçlı gözlemlemeye yardım eder. Lock callback scope'unu uzun network request'lerle gereksiz büyütmek convoy/UX gecikmesi oluşturabilir.

### Yüksek getirili mülakat soruları
- Multi-tab uygulamada tek JS thread neden coordination problemini çözmez?
- Web Lock ne zaman IndexedDB transaction'dan farklı bir problem çözer?
- Exclusive ve shared mode trade-off'u nedir?
- Leader election pattern'i nasıl kurarsın?
- Web Locks neden distributed lock yerine kullanılamaz?
- Senior: iki named lock ile deadlock nasıl oluşur ve nasıl önlersin?

### Seviyeye göre cevap derinliği
Junior/Mid: tab/worker isolation, named lock, exclusive access. Senior: queueing, shared/exclusive semantics, deadlock ordering, cancellation ve lock scope. Staff: browser lifecycle, crash/reload recovery, server idempotency ile birlikte tasarım ve observability.

### Kısa alıştırma
Üç tab'ın aynı anda token refresh başlattığını düşün. `auth-refresh` lock'u ile yalnız bir refresh yapılacak akışı çiz; bekleyen tab'ların sonucu nasıl öğreneceğini ve server idempotency'nin neden hâlâ değerli olduğunu açıkla.

### Proje fikri
`multi-tab-sync-lab`: iki tab + worker ile IndexedDB sync coordinator kur. Web Locks açık/kapalı modlarda duplicate work, latency ve queue length ölç; deliberate A→B / B→A nested lock senaryosuyla deadlock demonstrasyonu ekle.

### Failure modes / trade-off / production
Lock'u global distributed mutex sanmak; callback içinde gereksiz uzun I/O tutmak; nested lock ordering'i tanımlamamak; tab crash/reload senaryosunu test etmemek; server-side idempotency'yi kaldırmak; yalnız happy-path browser test etmek. Production'da acquisition wait, hold duration, duplicate sync ve refresh error'larını ölç.
