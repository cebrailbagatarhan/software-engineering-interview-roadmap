## Paket 1 — Mid/Senior Databases: PostgreSQL EXPLAIN, Cardinality Errors & I/O Reality
**Süre:** 20–30 dk

### Konu anlatımı
PostgreSQL query optimization için ilk mental model `SQL -> planner estimates -> plan tree -> executor reality` olmalıdır. `EXPLAIN` planner'ın seçtiği planı gösterir; `EXPLAIN ANALYZE` sorguyu gerçekten çalıştırıp node başına actual rows/time ekler. En yüksek getirili sinyal yalnız “hangi index kullanıldı?” değildir: **estimated rows ile actual rows arasındaki sapma** planın neden yanlış seçildiğini açıklayabilir. Büyük cardinality error; stale/eksik statistics, correlated columns veya veri dağılımının planner modeline uymaması gibi nedenlerden doğabilir.

Plan ağacında scan node'ları altta, join/sort/aggregate node'ları üsttedir. `loops` kritik bir çarpandır: actual rows/time değerleri execution başına ortalama olabilir; toplam iş için loops ile birlikte düşünülmelidir. `BUFFERS` shared hit/read, temp read/write gibi I/O sinyalleri verir. PostgreSQL 18'de `SERIALIZE TEXT|BINARY`, output serialization maliyetini ayrıca ölçebilir; buna rağmen network transmission maliyeti EXPLAIN tarafından ölçülmez.

`EXPLAIN ANALYZE` production'da masum bir read-only komut değildir: statement gerçekten execute edilir. UPDATE/DELETE gibi side-effect üreten statement'larda test transaction'ı + rollback yaklaşımı gerekir. Ayrıca node-level timing'in ölçüm overhead'i vardır; performans teşhisinde gözlem aracının sistemi etkilemesini hesaba katmak gerekir.

### Mental model
```text
SQL
 |
 v
statistics ---> planner estimates
                 |
                 v
             plan tree
                 |
                 v
              executor
                 |
      +----------+----------+
      |                     |
estimated rows          actual rows
      |                     |
      +---- ratio/gap -------+
                 |
        cardinality error?
                 |
        wrong join/scan/sort?

BUFFERS -> cache/I/O reality
loops   -> repeated work multiplier
```

### Yüksek getirili mülakat soruları
- `EXPLAIN` ile `EXPLAIN ANALYZE` arasındaki güvenlik/performance farkı nedir?
- Estimated 100 rows, actual 1,000,000 rows görürsen ne düşünürsün?
- Nested Loop neden küçük outer relation'da iyi, cardinality hatasında felaket olabilir?
- `shared hit` ile `shared read` neyi anlatır?
- `loops` neden plan okurken atlanmamalıdır?
- `EXPLAIN ANALYZE` neden client/network latency'yi tam ölçmez?
- Senior: correlated columns yüzünden estimate bozuluyorsa index eklemeden önce ne araştırırsın?

### Seviyeye göre cevap derinliği
Junior/Mid: plan tree, Seq/Index Scan, estimated vs actual rows. Senior: join choice, loops, BUFFERS, temp spill, statistics ve measurement overhead. Staff: workload temsiliyeti, plan regression, production sampling/auto_explain overhead ve schema/statistics stratejisi.

### Kısa alıştırma
Bir plan düşün: outer scan estimated=10/actual=50,000; inner index scan loops=50,000. Neden toplam maliyetin tek inner-node süresinden çok daha büyük olabileceğini açıkla ve ilk üç teşhis adımını yaz.

### Proje fikri
`pg-plan-regression-lab`: skewed veri üret; `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` çıktısını parse ederek estimate/actual ratio, loops ve buffer reads için küçük bir regression raporu üret.

### Failure modes / trade-off / production
“Index Scan her zaman iyidir” demek; yalnız total execution time'a bakmak; `loops` çarpanını unutmak; dev/staging küçük verisini production'a genellemek; stale statistics'i görmeden hint-benzeri workaround aramak; write statement üzerinde `EXPLAIN ANALYZE` çalıştırmanın side-effect'ini unutmak; `auto_explain.log_analyze`/timing overhead'ini hesaba katmamak.

## Paket 2 — Senior/Staff AI/LLM: Evaluation Design, Graders & Regression Gates
**Süre:** 20–30 dk

### Konu anlatımı
LLM evaluation'da temel hata “tek benchmark skoru = ürün kalitesi” varsayımıdır. Production sistemi için eval, belirsiz bir kalite hedefini test edilebilir davranışlara dönüştüren bir **specification + dataset + grader + decision rule** sistemidir. Önce gerçek kullanıcı görevlerini ve failure taxonomy'yi tanımla; sonra representative ve adversarial örnekleri dataset'e koy; mümkün olan yerde deterministic check, semantik kalite gerektiğinde rubric tabanlı model grader veya human review kullan.

Mental model iki loop'tur. Offline eval, model/prompt/tool/retrieval değişikliğini release öncesi karşılaştırır. Online monitoring ise gerçek trafik dağılımı, yeni failure mode ve drift sinyallerini toplar; bunlar offline eval setini besler. Böylece eval suite statik bir sınav değil yaşayan regression contract olur.

Model-based grader kullanırken grader'ın kendisi de bir ölçüm aracıdır: rubric belirsizliği, position/order bias, verbosity preference, self-preference ve domain kör noktaları olabilir. Kritik subset'lerde human-labeled calibration set ile grader agreement ölçülmeli; yüksek riskli karar tek bir opaque score'a bırakılmamalıdır. Deterministic check'ler JSON schema, tool-call argument, citation existence veya exact business rule gibi alanlarda daha ucuz ve reproducible olabilir.

### Mental model
```text
product goal
    |
    v
failure taxonomy
    |
    v
representative + adversarial dataset
    |
    +--> deterministic checks
    +--> model grader + rubric
    +--> human calibration
    |
    v
score by slice, not only global mean
    |
 release gate / investigate
    |
    v
production monitoring
    |
new failures ---------> eval dataset
```

### Yüksek getirili mülakat soruları
- LLM eval dataset'i nasıl oluşturursun?
- Deterministic grader ile model-based grader'ı ne zaman seçersin?
- Global accuracy yükselirken önemli bir user slice gerilerse release eder misin?
- Grader calibration neden gerekir?
- RAG sistemi için retrieval ve answer quality'yi neden ayrı ölçersin?
- Agent eval'da yalnız final answer neden yetersiz olabilir?
- Staff: eval suite'i CI/CD release gate'e bağlarken flakiness ve cost'u nasıl yönetirsin?

### Seviyeye göre cevap derinliği
Mid: dataset, expected behavior, pass/fail metric. Senior: slice-based metrics, rubric, deterministic/model/human graders, regression. Staff/Principal: production feedback loop, calibration, cost/latency, statistical confidence, red-team/adversarial subsets ve release governance. EM/CTO: eval metric'ini product KPI ve downside-risk budget ile bağlama.

### Kısa alıştırma
Bir support RAG botu için 12-case mini eval tasarla: 4 normal, 3 retrieval-hard, 2 ambiguous, 2 policy-sensitive, 1 tool failure. Her grup için grader türünü ve release threshold'unu belirt.

### Proje fikri
`llm-eval-gate`: versioned JSONL eval seti, deterministic schema/citation checks, rubric grader, per-slice dashboard ve baseline'a göre regression gate içeren küçük CI pipeline'ı.

### Failure modes / trade-off / production
Yalnız happy-path dataset; test-set leakage; global ortalamayla minority/critical slice regression'ını gizlemek; grader prompt'unu versionlamamak; model grader'ı ground truth sanmak; retrieval ve generation hatasını aynı score'da eritmek; offline score iyileşirken production latency/cost'u görmezden gelmek; gerçek incident'ları eval corpus'a geri beslememek.
