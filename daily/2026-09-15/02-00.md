## Paket 1 — Senior/Staff Cybersecurity: WebAuthn, Passkeys & Replay Resistance
**Süre:** 20–30 dk

### Konu anlatımı
WebAuthn parola bilgisini sunucuya tekrar tekrar göndermek yerine public-key credential kullanır. Registration sırasında authenticator bir credential key pair üretir; relying party (RP) credential ID ve public key gibi doğrulama verilerini saklar. Authentication sırasında RP rastgele bir challenge üretir, authenticator kullanıcı etkileşimi/doğrulaması sonrasında assertion imzalar, RP de signature, challenge, origin/RP bağlamı ve ilgili alanları doğrular.

Kritik mental model: private key RP'ye verilmez. Credential belirli bir RP scope'una bağlıdır; bu özellik phishing resistance'ın temel parçalarındandır. Challenge taze, tahmin edilemez ve server-side güvenilir ortamda üretilmelidir; aksi halde eski assertion'ın replay edilmesi riski doğar.

Passkey, discoverable WebAuthn credential için kullanılan yaygın isimdir. Synced passkey convenience ve recovery'yi iyileştirebilir; device-bound credential ise farklı assurance/lifecycle özelliklerine sahip olabilir. Staff seviyesinde authentication ceremony kadar credential enrollment, recovery, revocation, multiple credentials ve account takeover blast radius'u önemlidir.

### Mental model
```text
Registration
Browser/RP ---- challenge/options ----> Authenticator
   ^                                      |
   | credential ID + public key           | private key stays here
   +--------------------------------------+

Authentication
RP -- fresh challenge --> Browser/Authenticator
RP <-- signed assertion ------------------+
 | verify challenge + RP/origin + signature
 v
session / deny
```

### Yüksek getirili mülakat soruları
1. WebAuthn neden shared-secret password modelinden farklıdır?
2. Challenge replay attack'i nasıl önler?
3. RP ID/origin binding phishing resistance'a nasıl katkı sağlar?
4. User presence ile user verification aynı şey midir?
5. Passkey kaybolursa account recovery nasıl tasarlanmalıdır?
6. Synced ve device-bound credential için risk/UX trade-off'ları nelerdir?

### Seviye beklentisi
- **Mid:** registration/authentication akışını ve public/private key ayrımını açıklar.
- **Senior:** challenge, origin/RP validation, replay, recovery ve credential lifecycle'ı tartışır.
- **Staff/Principal:** assurance policy, account recovery, device enrollment, audit ve organization-wide authentication migration tasarlar.

### Mini alıştırma
Bir `login.example.com` servisi için registration ve authentication state machine'i çiz. Server'ın challenge için ne sakladığını, assertion geldiğinde hangi kontrolleri hangi sırada yaptığını yaz.

### Proje fikri
`webauthn-lab`: demo RP geliştir; kullanıcıya birden fazla credential kaydettir, credential listesi/revocation ekranı ekle ve replay edilmiş challenge'ın reddedildiğini test et.

### Failure modes / trade-off / production
Challenge reuse veya düşük entropy, yanlış origin/RP validation, recovery kanalının ana auth'tan daha zayıf olması, tek credential kaybında lockout, credential metadata'sını gereksiz fingerprinting için kullanmak ve passkey migration sırasında password fallback'in saldırı yüzeyini koruması.

- https://www.w3.org/news/2026/web-authentication-an-api-for-accessing-public-key-credentials-level-3-is-now-a-w3c-recommendation/

## Paket 2 — Senior Networking: QUIC, Streams & Head-of-Line Blocking
**Süre:** 20–30 dk

### Konu anlatımı
QUIC, UDP üzerinde çalışan fakat kendi reliable delivery, congestion control, connection management ve stream multiplexing mekanizmalarını tanımlayan şifreli bir transport protokolüdür. HTTP/3 QUIC üzerinde çalışır. Mülakatta önemli nokta “UDP hızlıdır” ezberi değil; QUIC'in transport semantics'i user space'te kurması ve bağımsız stream'lerin packet loss karşısındaki davranışıdır.

TCP byte stream üzerinde bir packet kaybı daha sonraki byte'ların application'a teslimini bekletebilir. HTTP/2 çoklu logical stream kullansa da hepsi aynı TCP connection'ın ordered byte stream'i üzerindedir. QUIC'te bir stream'deki kayıp diğer stream'lerin application delivery'sini aynı şekilde bloklamak zorunda değildir; yine de packet loss congestion window'u ve ortak network capacity'yi etkileyebilir.

QUIC bağlantıları connection ID ile tanımlanabildiği için IP/port değişimi gibi migration senaryolarını TCP 4-tuple modelinden farklı ele alabilir. Buna karşılık UDP filtering, observability, load-balancer routing, state ve protocol evolution yeni operational trade-off'lar getirir.

### Mental model
```text
HTTP/2 over TCP
stream A --\
stream B ---+--> one ordered TCP byte stream --> loss can block delivery
stream C --/

HTTP/3 over QUIC
stream A ---- reliable stream A --X(retransmit)
stream B ---- reliable stream B ------> can continue
stream C ---- reliable stream C ------> can continue
                 shared congestion control / path
```

### Yüksek getirili mülakat soruları
1. QUIC neden sadece “HTTP over UDP” değildir?
2. HTTP/2'nin TCP-level HOL blocking problemi nedir?
3. QUIC stream isolation packet loss etkisini nasıl değiştirir?
4. QUIC neden TLS'i transport handshake ile daha sıkı bütünleştirir?
5. Connection ID migration/load balancing için neden önemlidir?
6. QUIC kullanmak congestion control ihtiyacını ortadan kaldırır mı?

### Seviye beklentisi
- **Mid:** TCP/UDP ve multiplexing temelini açıklar.
- **Senior:** stream-level reliability, HOL blocking, handshake ve connection migration trade-off'larını tartışır.
- **Staff:** edge/load-balancer state, telemetry, UDP reachability, fallback ve fleet-wide rollout risklerini değerlendirir.

### Mini alıştırma
Aynı sayfada 20 paralel resource indiren client için HTTP/2/TCP ve HTTP/3/QUIC akışını çiz. Tek packet loss olduğunda hangi işlerin doğrudan bekleyebileceğini işaretle.

### Proje fikri
`quic-loss-lab`: HTTP/2 ve HTTP/3 destekleyen küçük servis kur; kontrollü latency/loss altında completion time ve p95/p99 sonuçlarını karşılaştır. Sonuçları “QUIC her zaman daha hızlı” iddiası yerine workload/path koşullarıyla yorumla.

### Failure modes / trade-off / production
UDP'nin bazı ağlarda kısıtlanması, fallback davranışının ölçülmemesi, connection ID routing hataları, NAT/rebinding edge case'leri, QUIC'in HOL sorununu tamamen yok ettiği sanısı ve benchmark'ta handshake/cache farklarının karıştırılması.

### Kaynaklar
- https://www.rfc-editor.org/rfc/rfc9000
- https://quicwg.org/

## Paket 3 — Senior/Staff MLOps: Model Registry, Lineage, Champion/Challenger & Rollback
**Süre:** 20–30 dk

### Konu anlatımı
Model artifact'ını object storage'a koymak tek başına model lifecycle yönetimi değildir. Registry; model version, lineage, metadata, evaluation/approval bilgisi ve deployment için kararlı referanslar arasında bir control plane sağlar. MLflow Model Registry güncel yaklaşımında model versions yanında aliases ve tags kullanır; örneğin `champion` alias'ı production'da hedeflenen versiyonu gösterebilir.

Alias'ın değeri deployment code'unu immutable version numarasına gömmek yerine kontrollü bir indirection sağlamasıdır. Ancak alias değişimi tek başına güvenli rollout değildir. Candidate evaluation, compatibility checks, shadow/canary/A-B stratejisi, monitoring ve rollback sinyalleri ayrıca tasarlanmalıdır.

Lineage “hangi model?” sorusunun ötesine geçer: hangi training code/run, data snapshot/features, parameters ve evaluation sonucu bu artifact'ı üretti? Reproducibility için registry kaydı ile training/data provenance birlikte düşünülmelidir.

### Mental model
```text
training run + data/features + code
              |
              v
        model artifact v17
              |
        Registry metadata
       /       |        \
 lineage   eval tags   aliases
                         |
               champion -> v16
               challenger -> v17
                         |
                   deploy / compare
                         |
                 monitor -> promote/rollback
```

### Yüksek getirili mülakat soruları
1. Artifact store ile model registry farkı nedir?
2. Model version ve alias neden ayrı kavramlardır?
3. Champion/challenger rollout'u nasıl tasarlarsın?
4. Offline metric iyileşirken production KPI neden kötüleşebilir?
5. Rollback için yalnızca eski model artifact'ı yeterli midir?
6. Lineage'da model dışında hangi data/code/config bilgileri tutulmalıdır?

### Seviye beklentisi
- **Mid:** versioning, registry ve deployment referansını anlatır.
- **Senior:** lineage, evaluation gates, alias, rollback ve reproducibility tasarlar.
- **Staff/Principal:** multi-team governance, environment separation, approval policy, auditability ve model/data compatibility standardı kurar.

### Mini alıştırma
Churn modelinin v16 production, v17 candidate olduğunu varsay. v17 için promotion gate'leri, shadow/canary planını, rollback trigger'larını ve registry metadata alanlarını yaz.

### Proje fikri
`model-promotion-lab`: MLflow ile iki model version kaydet; `champion`/`challenger` alias'ları, validation tags ve basit promotion script'i ekle. Promotion'ı metric threshold + schema compatibility testine bağla.

### Failure modes / trade-off / production
`latest` benzeri belirsiz referans kullanmak, alias değişimini audit etmemek, data/schema compatibility kontrol etmemek, yalnızca offline metric'e güvenmek, rollback sırasında feature pipeline versiyonunu unutmak ve registry'yi deployment'ın tek source-of-truth'u sanmak.

### Kaynaklar
- https://mlflow.org/docs/latest/ml/model-registry
- https://www.mlflow.org/docs/latest/ml/model-registry/workflow/
