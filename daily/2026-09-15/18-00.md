## Paket 1 — Senior Databases: PostgreSQL Serializable Isolation, SSI & Retry Discipline
**Süre:** 20–30 dk

### Konu anlatımı
`SERIALIZABLE`, concurrent transaction'ların sonucunu sanki transaction'lar bir seri sırada çalışmış gibi güvenli hale getirmeyi hedefler. PostgreSQL bunu Serializable Snapshot Isolation (SSI) yaklaşımıyla uygular. Kritik mental model şudur: sistem her tehlikeli etkileşimi blocking lock ile önlemek yerine, concurrent read/write bağımlılıklarını izler ve serial bir sırayla açıklanamayacak execution oluşma riski gördüğünde transaction'lardan birini serialization failure ile abort edebilir.

PostgreSQL'in predicate/SIRead lock'ları normal blocking row lock gibi düşünülmemelidir. Bunlar bir concurrent write'ın önceki bir read sonucunu etkileyip etkilemeyeceğini saptamak için dependency takibinde kullanılır; `pg_locks` içinde `SIReadLock` olarak görülebilir. Bu yüzden Serializable seçmek uygulamadaki retry sorumluluğunu ortadan kaldırmaz, tersine onu correctness protokolünün parçası yapar: serialization failure alan transaction baştan, business operation sınırından tekrar çalıştırılmalıdır. Dış side-effect'ler transaction retry'siyle iki kez oluşmamalıdır.

Uzun read-only raporlarda `SERIALIZABLE READ ONLY DEFERRABLE`, güvenli snapshot oluşana kadar başlangıçta bekleyip sonrasında serialization abort riskini azaltabilen özel bir seçenektir. PostgreSQL 18 ayrıca Serializable garantisinin hot standby/logical replica okumalarına aynı biçimde uzanmadığı konusunda uyarır.

### Mental model
```text
T1: read predicate P ----------- write A ---- commit?
          \
           \ rw dependency
            \
T2:          write matching P -- read A ----- commit?

SSI dependency graph dangerous ise
-> bir transaction abort
-> application whole transaction retry
```

### Yüksek getirili mülakat soruları
- Serializable ile Repeatable Read arasındaki temel correctness farkı nedir?
- PostgreSQL predicate/SIRead lock neden normal blocking lock değildir?
- Serialization failure neden application-level retry gerektirir?
- Retry transaction'ın hangi sınırından yapılmalıdır?
- External API çağrısı transaction içinde ise retry neden tehlikelidir?
- Staff: contention yükseldiğinde Serializable'ın abort rate/latency trade-off'unu nasıl ölçersin?

### Seviyeye göre cevap derinliği
Junior/Mid: isolation, anomaly, transaction retry. Senior: SSI, dependency, serialization failure, idempotent side effects. Staff/Principal: contention topology, retry budget/backoff, observability, replica caveat'ları ve invariant tabanlı concurrency testleri.

### Kısa alıştırma
İki doktorun aynı anda `on_call >= 1` invariant'ını okuyup kendisini off-call yaptığı write-skew senaryosunu iki transaction olarak çiz; Repeatable Read ve Serializable sonucunu karşılaştır.

### Proje fikri
`ssi-race-lab`: PostgreSQL üzerinde concurrent reservation veya on-call invariant testi; Read Committed/Repeatable Read/Serializable modlarını karşılaştır, serialization abort ve retry sayısını ölç.

### Failure modes / trade-off / production
Serializable seçip retry yazmamak; yalnız son SQL statement'ı retry etmek; transaction içinde non-idempotent external side-effect üretmek; hot standby okumasına primary Serializable garantisini varsaymak; yüksek contention altında abort rate'i gözlemlememek.

### Kaynaklar

- PostgreSQL 18 — Concurrency Control Caveats: https://www.postgresql.org/docs/18/mvcc-caveats.html
- PostgreSQL 18 — Client Connection Defaults / deferrable: https://www.postgresql.org/docs/18/runtime-config-client.html

## Paket 2 — Senior ML/MLOps: Mixed Precision Training, Gradient Scaling & Reproducibility
**Süre:** 20–30 dk

### Konu anlatımı
Mixed precision training her operation'ı kör biçimde FP16'ya çevirmek değildir. PyTorch AMP'de `autocast`, seçili operation'ları performans ve numerik davranışlarına göre uygun precision'da çalıştırır. FP16 training'de küçük gradient değerleri representable aralığın altına düşüp underflow olabilir; `GradScaler` loss'u ölçekleyerek gradient'lerin kaybolma riskini azaltır, optimizer step öncesi unscale eder ve non-finite gradient varsa step'i atlayabilir.

Performance ile reproducibility ayrı eksenlerdir. PyTorch resmi dokümantasyonu aynı seed verilse bile farklı release/platform veya CPU/GPU arasında tam reproducibility garantisi olmadığını açıkça belirtir. `torch.use_deterministic_algorithms(True)` uygun operation'larda deterministic implementation seçebilir veya yalnız nondeterministic implementation varsa hata verebilir; fakat tek başına bütün uygulamayı reproducible yapmaz. Deterministic algoritmalar daha yavaş olabilir. Production training pipeline'ında seed yanında framework/CUDA/container version, dataset snapshot, preprocessing, hyperparameters ve checkpoint provenance kaydedilmelidir.

### Mental model
```text
forward
  |
  +-- autocast -> fast lower precision where safe
  |
loss -- scale --> backward --> scaled gradients
                         |
                      unscale
                         |
                  finite? -- no --> skip step
                         |
                        yes
                         v
                   optimizer.step

reproducibility = code + data + env + RNG + algorithms
```

### Yüksek getirili mülakat soruları
- Mixed precision neden tüm op'ları FP16 yapmak değildir?
- Gradient scaling hangi numerik problemi hedefler?
- `scaler.step()` non-finite gradient gördüğünde neden step'i atlayabilir?
- Inference'ta neden GradScaler gerekmez?
- Seed vermek neden tam reproducibility garantisi değildir?
- Staff: throughput kazanımı ile deterministic regression testlerini nasıl ayırırsın?

### Seviyeye göre cevap derinliği
Mid: FP32/FP16/BF16, autocast, underflow. Senior: scaling lifecycle, clipping/unscale sırası, non-finite detection, benchmark. Staff: distributed training provenance, determinism policy, hardware/software drift ve cost-per-trained-token/step trade-off'u.

### Kısa alıştırma
Bir training loop'ta `autocast -> scale(loss).backward -> unscale/clip -> step -> update` sırasını yaz ve gradient clipping'in neden scaled gradient üzerinde kör uygulanmaması gerektiğini açıkla.

### Proje fikri
`amp-repro-lab`: aynı modelde FP32 ve AMP training'i karşılaştır; step time, peak memory, validation metric ve run-to-run variance raporla.

### Failure modes / trade-off / production
Backward'ı autocast scope mantığını anlamadan özelleştirmek; clipping öncesi unscale etmemek; NaN/Inf step skip metric'ini izlememek; seed'i tek provenance bilgisi sanmak; determinism'i production throughput gereksiniminden bağımsız zorunlu kılmak.

### Kaynaklar
- PyTorch — Automatic Mixed Precision examples: https://docs.pytorch.org/docs/main/notes/amp_examples.html
- PyTorch — Reproducibility: https://docs.pytorch.org/docs/stable/notes/randomness.html

## Paket 3 — Mid/Senior Frontend: Web Workers, Structured Clone & Transferable Objects
**Süre:** 20–30 dk

### Konu anlatımı
Web Worker, CPU-ağır JavaScript işini ana UI execution context'inden ayırarak main thread responsiveness'ını korumak için kullanılabilir. Worker ile page aynı object instance'larını genel olarak paylaşmaz; `postMessage()` ile gönderilen veriler structured clone algoritması üzerinden kopyalanır. Bu model race riskini azaltır fakat büyük payload'larda serialization/copy maliyeti oluşturabilir.

Bazı kaynaklar `transferable` olarak ownership transfer edilebilir. Örneğin `ArrayBuffer` transfer edildiğinde underlying memory kopyalanmak yerine hedef context'e taşınabilir; gönderen taraftaki buffer detached olur ve artık kullanılamaz. Bu zero/low-copy yaklaşımı büyük binary payload'larda önemlidir. Structured clone her JavaScript değerini desteklemez: Function ve DOM node gibi değerler clone edilemez ve `DataCloneError` üretebilir.

Worker kullanmak otomatik hızlanma değildir. Task küçükse startup/message overhead kazancı silebilir; UI ile çok sık mesajlaşma yeni bottleneck yaratabilir. Production'da long task süresi, input latency, payload boyutu, transfer/copy süresi ve worker pool saturation ölçülmelidir.

### Mental model
```text
Main/UI thread                    Worker
--------------                    ------
input/render
    |
postMessage(data) -- clone ------> CPU work
    |                               |
    |<--------- result clone -------+

large ArrayBuffer:
main owns buffer -- transfer --> worker owns buffer
main buffer = detached
```

### Yüksek getirili mülakat soruları
- Web Worker hangi problemi çözer, hangi problemi çözmez?
- `postMessage()` veriyi nasıl taşır?
- Structured clone ile JSON serialization farklarından biri nedir?
- Transferable object neden büyük ArrayBuffer için avantajlıdır?
- Transfer sonrası sender buffer'a ne olur?
- Senior: worker pool size, cancellation ve backpressure nasıl tasarlanır?

### Seviyeye göre cevap derinliği
Junior/Mid: main thread, worker, postMessage. Senior: structured clone, transferable ownership, overhead, cancellation. Staff: worker pool, workload partitioning, observability, browser capability/fallback ve end-user responsiveness SLO'ları.

### Kısa alıştırma
50 MB `ArrayBuffer` işleyen bir image/data transform için clone ve transfer akışını çiz; sender'ın buffer'ı tekrar kullanması gereken durumda trade-off'u yaz.

### Proje fikri
`worker-transfer-lab`: CPU-heavy transform'u main thread, worker+clone ve worker+transfer ile çalıştır; long task, wall time ve UI responsiveness karşılaştır.

### Failure modes / trade-off / production
Her işi worker'a atmak; büyük buffer'ı sürekli clone etmek; transfer sonrası detached buffer'ı kullanmak; worker error/cancellation protokolü kurmamak; çok sayıda worker ile CPU contention yaratmak.
