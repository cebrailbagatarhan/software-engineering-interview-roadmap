## Paket 1 — Senior Backend/Runtime: Python 3.14 InterpreterPoolExecutor & Subinterpreters
**Süre:** 20–30 dk

### Konu anlatımı
Python 3.14 ile `InterpreterPoolExecutor`, `ThreadPoolExecutor` benzeri bir API altında worker başına ayrı interpreter kullanır. Her worker kendi thread'i ve interpreter'ı içinde çalışır; interpreter'ların ayrı GIL'leri olduğu için CPU-bound saf Python işi bir process açmadan birden çok çekirdekte gerçekten paralel çalışabilir. Bunun bedeli izolasyondur: `sys.modules`, import edilmiş modüller ve mutable runtime state interpreter'lar arasında normal thread'lerdeki gibi ortak değildir. Gönderilen callable/argument/result sınırları serialization ve extension-module uyumluluğu açısından düşünülmelidir.

Subinterpreter yaklaşımı multiprocessing'in birebir yerine geçmez. Aynı process içinde bulunmak bazı kaynakların process-wide kalabileceği anlamına gelir; C extension'ların multi-interpreter güvenliği kritik olabilir. Production kararı workload, dependency compatibility, serialization overhead, crash isolation ve memory footprint birlikte ölçülerek verilmelidir.

### Mental model
```text
process
  |-- thread A -> interpreter A -> GIL A -> core 1
  |-- thread B -> interpreter B -> GIL B -> core 2
  `-- thread C -> interpreter C -> GIL C -> core 3

isolation boundary: modules / mutable Python objects
shared process reality: OS resources + native-extension caveats
```

### Yüksek getirili mülakat soruları
- `ThreadPoolExecutor`, `InterpreterPoolExecutor` ve `ProcessPoolExecutor` ne zaman ayrılır?
- Ayrı interpreter GIL'i CPU-bound Python koduna ne kazandırır?
- Interpreter isolation hangi programlama modelini zorunlu kılar?
- C extension uyumluluğu neden production riski olabilir?
- Serialization maliyeti hangi task granularity'sinde faydayı yok eder?
- Staff: rollout öncesi dependency compatibility ve fallback planını nasıl tasarlarsın?

### Seviyeye göre cevap derinliği
Mid: GIL, thread/process farkı. Senior: interpreter isolation, serialization, native-extension ve benchmark. Staff/Principal: runtime standardı, compatibility matrix, canary ve crash/isolation trade-off'u.

### Kısa alıştırma
CPU-bound bir fonksiyonu thread, interpreter ve process pool ile 1/2/4 worker'da benchmark edecek deney planı yaz; warm-up ve serialization etkisini ayrı ölç.

### Proje fikri
`python-parallelism-lab`: aynı workload'u üç executor ile çalıştır; throughput, p95 task latency, RSS ve startup maliyetini karşılaştır.

### Failure modes / trade-off / production
Küçük task'larda serialization overhead; desteklemeyen native extension; process-level crash isolation'ını interpreter isolation sanmak; benchmark yapmadan worker sayısını CPU sayısına eşitlemek.

- Python 3.14 — Multiple interpreters: https://docs.python.org/3.14/library/concurrent.interpreters.html

## Paket 2 — Senior Data Engineering: Apache Flink Checkpoint Barriers, Exactly-Once & Sink Semantics
**Süre:** 20–30 dk

### Konu anlatımı
Flink fault tolerance'ın çekirdeğinde distributed stream ve operator state'in consistent snapshot'ları vardır. Checkpoint barrier'ları source'lardan stream'e enjekte edilir ve kayıtları geçmeden akış boyunca ilerler. Multi-input operator aligned checkpoint'te bir input'un barrier'ı geldikten sonra diğer input'un aynı checkpoint barrier'ını bekleyerek snapshot sınırını tutarlı hale getirir. Bu alignment backpressure altında latency yaratabilir; unaligned checkpoint yaklaşımı in-flight data'yı snapshot'a dahil ederek recovery-state boyutu karşılığında alignment gecikmesini azaltabilir.

`EXACTLY_ONCE` ifadesini dikkatli kullanmak gerekir. Flink operator/user state'i failure/recovery sonrasında her record'un state'e bir kez yansımış olduğu semantiğe getirebilir; bu, record'un fiziksel olarak yalnız bir kez taşındığı anlamına gelmez. End-to-end exactly-once için source ve özellikle sink'in checkpoint protokolüyle işbirliği yapması gerekir; transactional veya idempotent sink davranışı belirleyicidir.

### Mental model
```text
source A: a1 a2 |B42| a3 ----\
                              +--> keyed state --> sink
source B: b1    |B42| b2 ----/

checkpoint 42 = source positions + operator state
recovery -> restore snapshot + resume source positions
end-to-end EO -> sink must participate too
```

### Yüksek getirili mülakat soruları
- Barrier neden record'ları overtake etmez?
- Aligned checkpoint multi-input operator'da neyi garanti eder?
- Exactly-once state ile exactly-once external side effect farkı nedir?
- Backpressure checkpoint duration'ı nasıl etkiler?
- Unaligned checkpoint hangi trade-off'u yapar?
- Staff: Kafka→Flink→external DB hattında guarantee'i uçtan uca nasıl ispatlarsın?

### Seviyeye göre cevap derinliği
Mid: state, checkpoint, restore. Senior: barrier alignment, source offsets, sink semantics ve backpressure. Staff: state backend/storage, recovery RTO, transactional sinks, checkpoint SLO ve upgrade/savepoint stratejisi.

### Kısa alıştırma
İki input'lu join operator'ünde bir input 20 saniye geriden geliyorsa aligned checkpoint davranışını çiz; latency ve recovery trade-off'unu yaz.

### Proje fikri
`flink-checkpoint-lab`: Kafka source + stateful aggregation + sink kur; failure inject ederek duplicate/state correctness ve checkpoint duration metriklerini karşılaştır.

### Failure modes / trade-off / production
`EXACTLY_ONCE` etiketini sink'i incelemeden tüm pipeline'a genellemek; checkpoint storage'ı dayanıksız tutmak; alignment duration alarmı olmaması; state büyümesini ve restore süresini kapasite planına katmamak.

### Kaynaklar
- Apache Flink — Stateful Stream Processing: https://nightlies.apache.org/flink/flink-docs-stable/docs/concepts/stateful-stream-processing/
- Apache Flink — Checkpointing: https://nightlies.apache.org/flink/flink-docs-stable/docs/ops/state/checkpoints/
- Apache Flink — Connector Fault Tolerance Guarantees: https://nightlies.apache.org/flink/flink-docs-stable/docs/connectors/datastream/guarantees/

## Paket 3 — Senior/Staff Cybersecurity: WebAuthn Level 3, Passkeys & Account-Recovery Threat Model
**Süre:** 20–30 dk

### Konu anlatımı
W3C, WebAuthn Level 3'ü 25 Ağustos 2026'da Recommendation olarak yayımladı. WebAuthn web uygulamalarına Relying Party'ye scoped public-key credential oluşturma ve kullanma API'si verir. Private key authenticator tarafında kalır; RP public key ile challenge'a verilen imzayı doğrular. Credential'ın RP/origin bağlamına cryptographic olarak bağlanması, password/OTP gibi kullanıcının sahte siteye tekrar yazabileceği shared-secret modelinden farklıdır ve phishing resistance'ın temelidir.

Passkey rollout'unun en zayıf noktası çoğu zaman login protokolü değil recovery ve fallback'tir. Passkey kullanan hesaba SMS/OTP veya zayıf help-desk recovery ile tam erişim veriliyorsa saldırgan güçlü primary authenticator'ı bypass edebilir. Synced ve device-bound passkey'ler availability/assurance açısından farklı ürün kararları getirir. Attestation ise her consumer uygulamada zorunlu değildir; privacy, device-policy ve enterprise assurance ihtiyacına göre değerlendirilmelidir.

### Mental model
```text
registration:
authenticator -> keypair
private key stays client-side
public key + credential id -> RP

login:
RP challenge -> authenticator signs -> RP verifies
                   ^
             RP/origin scoped

security floor = min(primary auth, recovery, fallback)
```

### Yüksek getirili mülakat soruları
- WebAuthn password modelinden kriptografik olarak nasıl ayrılır?
- RP ID/origin binding phishing resistance'a nasıl katkı verir?
- Synced vs device-bound passkey trade-off'u nedir?
- User Presence ile User Verification farkı nedir?
- Attestation ne sağlar ve privacy trade-off'u nedir?
- Staff/CTO: recovery kanalının auth assurance'ını düşürmesini nasıl engellersin?

### Seviyeye göre cevap derinliği
Mid: public/private key, challenge-response, RP scope. Senior: authenticator, UV/UP, synced/device-bound, recovery. Staff/CTO: assurance tiers, enterprise attestation policy, migration, support fraud ve account-recovery governance.

### Kısa alıştırma
Password+SMS kullanan bir SaaS'ı passkey'e geçir: enrollment, fallback, lost-device recovery ve high-risk action re-auth akışlarını çiz.

### Proje fikri
`webauthn-threat-model-lab`: küçük RP demo + STRIDE benzeri threat table; phishing proxy, stolen session, lost device ve help-desk recovery senaryolarını test et.

### Failure modes / trade-off / production
Passkey ekleyip password fallback'i sınırsız bırakmak; recovery'yi daha zayıf yapmak; session theft'i passkey'in çözdüğünü sanmak; attestation'ı gereksiz yere zorunlu kılıp compatibility/privacy maliyeti yaratmak.

- W3C announcement: https://www.w3.org/news/2026/web-authentication-an-api-for-accessing-public-key-credentials-level-3-is-now-a-w3c-recommendation/
