## Paket 1 — Senior/Staff Cloud/SRE & Distributed Systems: Kubernetes etcd RangeStream, Large LIST Reads & Memory Amplification
**Süre:** 20–30 dk

### Konu anlatımı
Kubernetes API server çoğu LIST/WATCH isteğini watch cache üzerinden servis eder; fakat cache başlangıçta veya re-initialization sırasında etcd'den resource collection'ın tamamını okumak zorundadır. Kubernetes v1.37 ile etcd v3.7 RangeStream desteği Beta'ya çıktı. Amaç büyük collection okumalarında API server ve etcd tarafındaki peak memory kullanımını daha öngörülebilir hale getirmektir.

Eski unary Range yaklaşımında pagination key count ile sınırlıydı; object boyutu değişkense tek page yine çok büyük olabilir. etcd page'i tamamen materialize eder, API server da decode ederken payload'ı tutar; böylece aynı büyük veri iki tarafta aynı anda memory pressure yaratabilir. Streaming yaklaşım byte akışını parçalara ayırarak materialization amplification'ını azaltır.

```text
etcd storage
   |
   | unary Range: [large page fully materialized]
   v
etcd memory ===== payload =====> apiserver memory -> decode -> watch cache

RangeStream:
etcd -> chunk -> chunk -> chunk -> apiserver incremental decode
         lower / more predictable peak memory
```

Mental model: pagination her zaman bounded memory değildir. Boundary key sayısıysa object-size variance peak byte kullanımını patlatabilir; stream backpressure ve bounded buffers daha iyi bir byte-level control surface sağlar.

### Yüksek getirili mülakat soruları
- LIST ile WATCH Kubernetes control plane'de nasıl ilişkilidir?
- Key-count pagination neden byte-count memory bound sağlamaz?
- Unary response neden sender ve receiver'da memory amplification yaratabilir?
- Streaming throughput ile peak memory arasındaki trade-off nedir?
- Backpressure olmazsa streaming neden yine risklidir?
- Senior: watch-cache reinitialization sırasında OOM riskini nasıl ölçersin?
- Staff: çok büyük CRD fleet'inde object-size distribution kapasite planını nasıl değiştirir?
- CTO: control-plane headroom için scale-up mı, payload governance mı, protocol improvement mı?

### Beklenen cevap derinliği
Junior: LIST/WATCH ve pagination. Mid: buffers, object size, streaming. Senior: memory amplification, backpressure, cache re-init ve observability. Staff: CRD/object-size governance ve fleet capacity. Principal/CTO: reliability economics, upgrade strategy ve platform guardrails.

### Kısa alıştırma
1000-object page varsay. Ortalama object 20 KiB fakat p99 400 KiB. Key-count pagination'ın neden güvenilir peak-memory tahmini vermediğini iki workload dağılımıyla göster.

### Proje fikri
`list-read-memory-lab`: unary page ve chunked stream simülatörü yaz; object-size skew, concurrency ve consumer speed değiştikçe sender/receiver peak RSS ve completion time ölç.

### Failure modes / trade-off / production
Streaming'i ücretsiz sanmak; consumer backpressure'ı yok saymak; yalnız average object size kullanmak; CRD payload büyümesini sınırlamamak; cache re-init'i load test etmemek. Production'da apiserver/etcd RSS, GC, LIST latency, bytes/read, watch-cache init time, object-size histogram ve OOM/restart izlenmelidir.

## Paket 2 — Senior/Staff ML/AI/LLM & Leadership: Model Lifecycle, Retirement Risk & Capability Routing
**Süre:** 20–30 dk

### Konu anlatımı
LLM production sistemi bir model adına değil capability contract'a bağlanmalıdır. Model family'leri hız, kalite, maliyet, context/tool capability ve lifecycle açısından farklılaşır; provider retirement veya pricing değişimi hard-coded model ID kullanan workflow'ları operasyonel riske dönüştürür.

OpenAI 14 Eylül 2026 release note'unda GPT-5.5'in ChatGPT, ChatGPT Work ve Codex'te 14 Ekim 2026'da retire edileceğini duyurdu ve Codex sign-in kullanan konfigürasyonların `gpt-5.6-sol`'a taşınmasını önerdi. GPT-5.6 ailesi Sol/Terra/Luna capability-cost katmanları sunuyor. Bu güncel örnek model routing'in yalnız latency optimizasyonu değil lifecycle governance problemi olduğunu gösterir.

```text
request
  |
capability policy
  |-- high reasoning ---> Sol
  |-- balanced ---------> Terra
  |-- fast/cheap --------> Luna
  |
 eval + cost + latency telemetry
  |
 lifecycle registry: active -> deprecated -> retired
```

Mental model: uygulama `model = X` dememeli; `capability = coding-high, latency <= budget, tools required` demeli. Router bunu mevcut model inventory'sine map eder. Böylece migration merkezi, ölçülebilir ve rollback edilebilir olur.

### Yüksek getirili mülakat soruları
- Model routing ile load balancing farkı nedir?
- Capability contract neden model ID'den daha dayanıklıdır?
- Eval gate olmadan model migration neden risklidir?
- Fallback model kaliteyi sessizce nasıl bozabilir?
- Prompt caching model economics'i nasıl etkiler?
- Senior: model retirement migration planını nasıl tasarlarsın?
- Staff: task-class bazlı router hangi sinyalleri kullanmalı?
- CTO: quality-per-dollar, vendor lock-in ve migration cost nasıl birlikte yönetilir?

### Beklenen cevap derinliği
Junior: model/latency/cost. Mid: routing ve fallback. Senior: evals, shadow traffic, budget ve rollback. Staff: capability registry, policy engine, telemetry ve multi-provider abstraction. CTO: vendor strategy, lifecycle governance, compliance ve unit economics.

### Kısa alıştırma
Üç task sınıfı tanımla: extraction, coding review, deep research. Her biri için quality floor, latency SLO ve max cost koy; router decision table oluştur.

### Proje fikri
`llm-capability-router`: model registry + policy engine + offline eval + shadow routing; retirement tarihine yaklaşan model için migration readiness raporu üret.

### Failure modes / trade-off / production
Hard-coded model IDs; fallback'te eval yapmamak; yalnız token fiyatına bakmak; retirement inventory'si tutmamak; cached prompts ve tool capability farklarını gözden kaçırmak. Production'da success/eval score, p95 latency, cost/task, fallback rate, model-version distribution ve retirement exposure izlenmelidir.
