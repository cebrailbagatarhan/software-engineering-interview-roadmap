## Paket 1 — Junior → Senior Algorithms & Data Structures: Topological Sort, DAG Scheduling & Cycle Detection
**Süre:** 20–30 dk

### Konu anlatımı
Topological sort, directed acyclic graph (DAG) içindeki düğümleri her `u -> v` kenarında `u` önce gelecek şekilde lineer sıralar. Birden fazla geçerli sıra olabilir; cycle varsa topological order yoktur. Bu ayrım mülakatta kritiktir: topological sort genel graph sıralaması değil, dependency relation'ın lineerleştirilmesidir.

Kahn algoritması her düğümün indegree değerini hesaplar, indegree=0 düğümleri queue'ya koyar ve seçilen düğümün outgoing edge'lerini kaldırıyormuş gibi komşuların indegree'lerini azaltır. İşlenen düğüm sayısı `V`'den küçük kalırsa geriye cycle bağımlılığı kalmıştır. Karmaşıklık adjacency-list ile `O(V+E)` time, `O(V+E)` storage'dır.

DFS alternatifi düğümü tüm descendants tamamlandıktan sonra output'a ekler; white/gray/black state ile gray düğüme geri kenar cycle gösterir. Kahn scheduling mental modeline, DFS dependency traversal mental modeline daha yakındır.

```text
A ---> C ---> E
 \     ^
  \   /
   > B ---> D

indegree=0 frontier: [A]
A çıkar -> B açılır
B çıkar -> C,D açılabilir
...

cycle eklenirse: E -> B
frontier tükenir ama tüm nodes işlenmez => cycle
```

### Yüksek getirili mülakat soruları
- Topological order hangi graph'larda tanımlıdır?
- Neden bir DAG'ın birden fazla geçerli topological order'ı olabilir?
- Kahn algoritmasında indegree neyi temsil eder?
- İşlenen node sayısı neden cycle detector olarak kullanılabilir?
- DFS ile Kahn yaklaşımının trade-off'ları nelerdir?
- Mid: lexicographically smallest order istenirse queue yerine ne kullanırsın?
- Senior: milyonlarca dependency ve incremental edge update varsa full recomputation ne zaman pahalı olur?
- Senior: build scheduler'da topological validity tek başına neden yeterli değildir?

### Beklenen cevap derinliği
Junior: DAG, indegree ve queue ile doğru `O(V+E)` çözüm. Mid: cycle detection, multiple valid orders, min-heap varyantı ve DFS alternatifi. Senior: scheduling concurrency, critical path, incremental dependency updates, memory layout ve failure propagation.

### Kısa alıştırma
`A->C, B->C, C->D, B->E` graph'ı için Kahn adımlarını elle çıkar. Sonra `D->B` ekleyip cycle'ın hangi invariant ile yakalandığını göster.

### Proje fikri
`dag-build-runner`: YAML dependency graph oku, cycle'ı reddet, ready task'ları paralel worker pool'a ver, failed dependency'nin downstream task'larını skip et ve critical-path süresini raporla.

### Failure modes / trade-off / production
Graph'ı DAG varsaymak; duplicate edge ile indegree'i yanlış saymak; disconnected components'i unutmak; deterministic output gereksinimini belirtmemek. Production'da CI build graph, package manager, workflow engine ve data pipeline scheduler'larında dependency correctness yanında concurrency limit, retry/idempotency ve failure propagation da gerekir.

## Paket 2 — Mid → CTO Distributed Systems & System Design: Consistent Hashing, Virtual Nodes & Rendezvous Hashing
**Süre:** 20–30 dk

### Konu anlatımı
Basit `hash(key) % N` partitioning hızlıdır fakat node sayısı değiştiğinde modulus değiştiği için key'lerin büyük bölümü başka node'a taşınır. Consistent hashing'in amacı membership değişikliğinde remapping blast radius'unu azaltmaktır.

Ring modelinde hem node'lar hem key'ler aynı hash uzayına yerleştirilir; key saat yönünde ilk node'a atanır. Bir node eklenince esas olarak predecessor aralığındaki key'lerin bir kısmı yeni node'a geçer. Virtual node'lar fiziksel node başına çok sayıda ring position kullanarak load distribution'ı düzeltir ve heterojen capacity için ağırlıklandırmaya izin verir; bedeli metadata ve rebalance operasyonudur.

Rendezvous/Highest-Random-Weight hashing ring tutmadan her key-node çifti için deterministic score üretip en yüksek skorlu node'u seçer. Membership değişiminde minimal remapping özelliği sağlar ve küçük/orta membership setlerinde basit olabilir; ancak naive lookup her key için tüm candidate node'ları score ettiği için `O(N)` maliyetlidir.

```text
hash ring
0 -------------------------------- 2^m
     N1        N2       N3
      ^         ^        ^
      |         |        |
    keys move mainly across adjacent ownership ranges

modulo:       H(key) % N
membership N -> N+1 => widespread remap

rendezvous:   owner(key) = argmax score(key,node)
```

### Yüksek getirili mülakat soruları
- `hash(key) % N` neden elastic cluster'da problem yaratır?
- Consistent hashing hangi guarantee'i verir, hangisini vermez?
- Virtual node neden load balance'ı iyileştirir?
- Replication factor ring üzerinde nasıl uygulanabilir?
- Hot key problemi consistent hashing ile otomatik çözülür mü?
- Senior: node eklenirken cache hit-rate ve backend load nasıl korunur?
- Staff: weighted capacity ve failure-domain awareness nasıl eklenir?
- CTO: client-side sharding, proxy-based routing ve managed service arasında hangi organizational trade-off'lar vardır?

### Beklenen cevap derinliği
Junior: hash partitioning ve remapping problemi. Mid: ring, successor ownership ve vnode. Senior: replication, rebalance, hot key, cache warm-up ve observability. Staff: weighted placement, rack/AZ awareness, membership dissemination ve control-plane correctness. Principal/CTO: operational ownership, cost, portability ve managed-vs-build kararı.

### Kısa alıştırma
4 cache node'u ve 100k key için modulo ile consistent-hash ring'i simüle et. Beşinci node eklendiğinde remap yüzdesini ve node başına key-count varyansını karşılaştır.

### Proje fikri
`hash-placement-lab`: modulo, consistent ring + vnodes ve rendezvous hashing implement et; add/remove node, weighted node, replication factor ve hot-key workload senaryolarında remap/load dağılımını ölç.

### Failure modes / trade-off / production
Consistent hashing'i perfect balance sanmak; az vnode; membership view'larının ayrışması; replica'ları aynı failure domain'e koymak; rebalance sırasında backend'i overload etmek; hot key'i yalnız partitioning problemi sanmak. Production'da ownership skew, remap rate, rebalance bandwidth, cache hit-rate, node saturation ve membership convergence izlenmelidir.
