## Paket 1 — Senior → CTO Cloud/DevOps/SRE & Leadership: Self-hosted CI Runner Version Enforcement, Fleet Hygiene & Brownouts
**Süre:** 20–30 dk

### Konu anlatımı
Self-hosted CI runner yalnız bir worker değildir; SaaS control plane ile sürekli uyumlu kalması gereken bir execution-plane ajanıdır. GitHub Actions, GitHub Enterprise Cloud için minimum self-hosted runner version enforcement'ını 25 Eylül 2026'da tam olarak devreye alacak. Güncel politika, bir runner'ın mevcut update'lerden 30 günden fazla geri kalması halinde job almamasına; kritik security update durumunda ise update uygulanana kadar job queueing'in durmasına izin veriyor. Enforcement öncesi brownout'lar eski runner'larda registration ve job execution'ı geçici olarak engelleyerek eksik fleet hygiene'ı görünür kılıyor.

Bu bir patch-management sorunu kadar capacity ve business-continuity problemidir. Eski runner'ları bir anda kaybetmek queue depth, lead time ve deployment recovery time'ı bozabilir. Doğru tasarım immutable runner image, version inventory, staged rollout, spare capacity ve break-glass/rollback runbook'u içerir.

```text
GitHub control plane
        |
 min-version policy
        |
   job scheduler
    /        \
new runners  old runners
  healthy      X / brownout
    |             |
 workloads     queued jobs

fleet hygiene -> capacity -> delivery reliability
```

### Yüksek getirili mülakat soruları
- Hosted ve self-hosted runner trade-off'ları nelerdir?
- Runner version drift neden yalnız security problemi değildir?
- Brownout neyi test eder?
- Immutable runner image neden pet runner'dan daha yönetilebilirdir?
- Senior: runner upgrade canary'sinde hangi SLI'ları izlersin?
- Staff: 5.000 runner'lık multi-org fleet için rollout waves nasıl tasarlanır?
- CTO/EM: enforcement deadline'ı feature delivery ile nasıl dengelenir?

### Beklenen cevap derinliği
Junior/Mid: runner, queue ve version kavramları. Senior: canary, capacity, rollback, image lifecycle. Staff: fleet inventory, blast radius, policy ve multi-org governance. CTO/EM: business continuity, ownership, security ve engineering economics.

### Kısa alıştırma
1.000 runner'ın %20'si enforcement günü job alamazsa kapasite etkisini kabaca hesapla. Queue latency'yi korumak için ne kadar spare capacity ve hangi rollout gate'lerini seçersin?

### Proje fikri
`runner-fleet-controller`: runner version inventory topla, minimum-version policy ile karşılaştır, outdated pool'ları drain et ve replacement image rollout'unu canary → wave modeliyle simüle et.

### Failure modes / trade-off / production
Golden image içinde eski runner binary; long-lived pet runners; eksik inventory; tüm fleet'i tek dalgada upgrade etmek; capacity headroom bırakmamak; yalnız registration'a bakıp job execution'ı ölçmemek. Production'da runner version coverage, registration failure, queued jobs, pickup latency, job success, utilization ve replacement time izlenmelidir.

## Paket 2 — Mid → Staff Cybersecurity & Backend: Dependabot Private Registry Auth, Least Privilege & Credential Elimination
**Süre:** 20–30 dk

### Konu anlatımı
Dependency bot'un private registry'ye erişimi klasik olarak uzun ömürlü PAT/registry secret gerektirebilir. Her static credential rotation, scope ve exfiltration yüzeyi getirir. GitHub 8 Eylül 2026'da Dependabot'ın GitHub-hosted private registries için repository/package access grant'lerini kullanarak `GITHUB_TOKEN` üzerinden `packages: read` talep edebilmesini yeniden etkinleştirdi. Explicit registry credentials ve normal routing önceliğini korurken automatic GitHub Packages credential fallback olarak kullanılıyor.

Mental model: credential sayısını azaltmak tek başına least privilege değildir. Identity'nin hangi resource'a, hangi operation için ve ne kadar süreyle eriştiğini daraltmak gerekir. Repository access grant + ephemeral job token, shared PAT'e göre blast radius'u küçültebilir; fakat yanlış package access grant'i yine privilege creep yaratır.

```text
Dependabot job
     |
 ephemeral GITHUB_TOKEN
     |  packages:read
     v
repository/package access grant
     |
 GitHub Packages registry

shared PAT removed -> secret rotation/exfiltration surface down
but access grants still need governance
```

### Yüksek getirili mülakat soruları
- Authentication ve authorization burada nasıl ayrılır?
- Static PAT ile ephemeral job token trade-off'u nedir?
- Least privilege yalnız token scope mudur?
- Private registry dependency-confusion riski nasıl oluşur?
- Senior: fallback credential routing'i nasıl test edersin?
- Staff: yüzlerce repo/package için access grant governance nasıl kurulur?
- Security lead: credential elimination programının başarısını hangi metriklerle ölçersin?

### Beklenen cevap derinliği
Junior/Mid: token, scope, read/write ayrımı. Senior: ephemeral identity, routing, dependency confusion ve auditability. Staff: org-wide package ownership, grant lifecycle ve policy-as-code. Leadership: secret inventory, migration economics ve residual risk.

### Kısa alıştırma
Üç repo ve iki private package için minimum access matrix'i çıkar. Shared PAT modelinden repository grant + ephemeral token modeline geçiş adımlarını yaz.

### Proje fikri
`registry-auth-matrix`: repo-package permission graph'i çıkaran, unused grants ve write-where-read-suffices ihlallerini raporlayan küçük bir policy checker geliştir.

### Failure modes / trade-off / production
Overbroad package grants; stale access; explicit credential ile fallback davranışını karıştırmak; public/private registry routing hatası; token'ı loglamak. Production'da auth failures, package access denials, active static secret count, grant age, dependency update success ve audit anomalies izlenmelidir.
