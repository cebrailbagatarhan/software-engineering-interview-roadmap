## Paket 1 — Senior/Staff Cloud & SRE: Kubernetes 1.37 Memory QoS, cgroup v2 & Reclaim Economics
**Süre:** 20–30 dk

### Konu anlatımı
Kubernetes v1.37'de Memory QoS Beta'ya geçti ve feature gate varsayılan açık. Ancak varsayılan kubelet configuration memory throttling veya reservation'ı otomatik etkinleştirmiyor; `memory.high`, `memory.min` ve `memory.low` değerleri ancak ilgili policy/configuration kullanıldığında cgroup v2'ye yazılıyor. Bu ayrım mülakatta önemlidir: feature availability ile active resource policy aynı şey değildir.

Mental model: CPU kolayca zaman dilimlerine bölünebilirken memory reclaim stateful ve baskı altında daha sert failure mode'lara sahiptir. `memory.min` hard protection, `memory.low` best-effort protection, `memory.high` ise throttling/reclaim pressure boundary olarak düşünülebilir. Tiered reservation'da Guaranteed pod'lar `memory.min`, Burstable pod'lar `memory.low` alabilir. Fakat policy node-wide'dır; pod bazında opt-out yoktur. Ayrıca page cache de cgroup'a charge edildiğinden büyük file-read yapan bir workload beklenenden fazla protected memory tutabilir.

```text
node memory pressure
        |
        v
 +-------------------+
 | cgroup v2 memory  |
 +-------------------+
   |       |       |
 min      low     high
 hard   best-effort throttle/
 protect protect    reclaim
   |
   +--> QoS / reservation policy

protection ↑  -> reclaim freedom ↓ -> neighbor risk ↑
```

### Yüksek getirili mülakat soruları
- Kubernetes request/limit ile cgroup v2 memory protection aynı şey midir?
- `memory.min`, `memory.low` ve `memory.high` kavramsal olarak nasıl ayrılır?
- Guaranteed ve Burstable workload'ların reclaim davranışı neden farklı tasarlanabilir?
- Page cache neden memory reservation hesabını şaşırtabilir?
- Node-wide reservation policy'nin multi-tenant cluster trade-off'u nedir?
- Senior: OOM azalırken p99 latency neden yine kötüleşebilir?
- Staff: mixed workload node pool'larını nasıl segment edersin?
- Principal/CTO: daha fazla memory headroom ile daha yüksek utilization arasında nasıl ekonomik karar verirsin?

### Beklenen cevap derinliği
Junior: request/limit, OOM ve QoS. Mid: cgroup v2 ve reclaim. Senior: working set, page cache, throttling ve tail latency. Staff: node-pool segmentation, workload classes ve rollout. Principal/CTO: utilization, reliability ve cloud cost.

### Kısa alıştırma
Aynı node'da 8 GiB working-set'li latency-sensitive API, 20 GiB file-scanning batch job ve telemetry sidecar çalışıyor. Hangi workload için hard/best-effort protection isteyeceğini ve hangi metriği rollback kriteri yapacağını yaz.

### Proje fikri
`memory-qos-lab`: cgroup v2 kullanan küçük Kubernetes cluster'da Guaranteed/Burstable pod'lar, file-cache pressure ve synthetic allocation ile `memory.min/low/high`, reclaim, PSI ve p99 latency ilişkisini ölç.

### Failure modes / trade-off / production
Feature gate açık diye policy aktif sanmak; `memory.min` ile aşırı koruma yapıp reclaimable pool'u tüketmek; page cache'i hesaba katmamak; yalnız OOM saymak; node-wide policy'nin heterojen workload etkisini görmezden gelmek. Production'da working set, RSS/cache breakdown, PSI, reclaim, OOM, throttling, p95/p99 ve node allocatable headroom birlikte izlenmelidir.

## Paket 2 — Senior/Staff Cybersecurity & Linux: Kubernetes Rootless Nodes, User Namespaces & Privilege Boundaries
**Süre:** 20–30 dk

### Konu anlatımı
Kubernetes v1.37'de `KubeletInUserNamespace` (rootless mode) Beta'ya geçti. Bu modelde kubelet, CRI/OCI runtime, CNI plugin'leri ve kube-proxy host üzerinde root olmayan bir kullanıcı olarak Linux user namespace içinde çalışabilir. Ama bunu pod user namespaces ile karıştırmamak gerekir: `hostUsers: false` pod'u user namespace'e alır; rootless node ise node component'lerinin host privilege boundary'sini değiştirir. İki özellik birlikte de kullanılabilir.

User namespace temel olarak namespace içindeki UID/GID ile host UID/GID arasında mapping kurar. Namespace içindeki UID 0, host'ta gerçek root olmak zorunda değildir. Böylece container/node component compromise'ının host üzerindeki doğrudan yetkisi azaltılabilir. Bunun bedeli networking, storage, device access, observability ve operasyon araçlarında compatibility yüzeyinin büyümesidir.

```text
host
+------------------------------------------------+
| unprivileged UID range                         |
|   +----------------------------------------+   |
|   | node user namespace                    |   |
|   | kubelet / CRI / CNI / kube-proxy       |   |
|   |                                        |   |
|   |   +-------------------------------+    |   |
|   |   | optional pod user namespace   |    |   |
|   |   | container UID 0 != host root  |    |   |
|   |   +-------------------------------+    |   |
|   +----------------------------------------+   |
+------------------------------------------------+
```

### Yüksek getirili mülakat soruları
- Linux user namespace hangi security boundary'yi değiştirir?
- Container içindeki UID 0 neden host UID 0 olmak zorunda değildir?
- Rootless kubelet ile `hostUsers: false` arasındaki fark nedir?
- Rootless mode neden sandbox/VM ile eşdeğer isolation değildir?
- CNI, storage veya device plugin'lerinde hangi compatibility sorunları çıkabilir?
- Senior: privileged workload ihtiyacını nasıl değerlendirirsin?
- Staff: rootless node pool migration'ını nasıl canary edersin?
- CTO: privilege reduction'ın operasyon maliyetine değip değmediğini nasıl ölçersin?

### Beklenen cevap derinliği
Junior: UID/GID ve root privilege. Mid: namespaces/capabilities. Senior: host escape surface, networking/storage compatibility. Staff: fleet rollout, workload classification ve exception governance. Principal/CTO: threat model, compliance ve platform cost.

### Kısa alıştırma
Bir build-runner cluster'ında untrusted CI jobs çalışıyor. Rootless node, pod user namespace ve VM isolation seçeneklerini threat model, compatibility ve cost açısından üç sütunda karşılaştır.

### Proje fikri
`rootless-node-lab`: rootless Kubernetes node üzerinde normal pod, `hostUsers:false` pod ve kontrollü host-volume/network senaryoları çalıştır; UID mapping, capability ve erişim farklarını test et.

### Failure modes / trade-off / production
Rootless'i tam sandbox sanmak; host mount/device erişimini görmezden gelmek; CNI/CSI compatibility test etmemek; debug/observability araçlarının privilege varsayımlarını kaçırmak; exception'ları kalıcı hale getirmek. Production'da privileged workload count, rootless scheduling failures, CNI/CSI errors, denied operations, exception inventory ve node escape/privilege audit sinyalleri izlenmelidir.
