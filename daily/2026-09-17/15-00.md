## Paket 1 — Mid → Staff Cloud/SRE & Observability: OpenTelemetry Kubernetes Metadata Enrichment, Cardinality & Stable Semantics
**Süre:** 20–30 dk

### Konu anlatımı
Telemetry yalnız timestamp ve value değildir; production debugging için sinyalin hangi workload, namespace, pod ve node'dan geldiğini bilmek gerekir. OpenTelemetry Collector'daki Kubernetes Attributes Processor, telemetry resource'larını Kubernetes metadata ile zenginleştirir. 16 Eylül 2026'da processor v1.0.0'a yükseldi; proje bunu stable kriterlerini karşılama, stable Kubernetes semantic conventions'a geçiş ve API breakage olmadan redistribution açısından bir milestone olarak tanımlıyor.

Enrichment bir join problemidir: gelen telemetry'deki connection/resource ipuçları Kubernetes API'den izlenen pod metadata'sıyla eşleştirilir. Bu yüzden correctness yalnız `label eklemek` değildir; association rule, RBAC, cache freshness, deployment topology ve cardinality birlikte düşünülür. Her label'ı telemetry'ye kopyalamak maliyet ve privacy riskidir: tenant/user/request gibi unbounded değerler metric series patlaması yaratabilir.

```text
apps -- OTLP --> Collector
                  |
                  +--> k8sattributes
                  |      |
                  |      +--> pod cache <--- Kubernetes API
                  |      |
                  |      +--> resource attrs
                  |
                  +--> batch/filter --> backend

identity quality ↑   debugging ↑
metadata volume ↑    cardinality/cost/privacy risk ↑
```

### Yüksek getirili mülakat soruları
- Resource attribute ile metric label arasındaki ilişki nedir?
- Kubernetes metadata enrichment neden bir join problemidir?
- Pod association yanlışsa hangi debugging hataları doğar?
- High-cardinality label neden metrics backend'i zorlar?
- DaemonSet collector ile gateway collector enrichment açısından nasıl farklıdır?
- Senior: RBAC eksikliği veya API-server outage sırasında nasıl degrade olursun?
- Staff: organizasyon çapında metadata allowlist ve semantic-convention migration nasıl yönetilir?

### Beklenen cevap derinliği
Junior/Mid: resource metadata ve cardinality. Senior: association, RBAC, cache, topology ve cost. Staff: semantic-contract governance, multi-tenant privacy, rollout ve fleet-wide telemetry economics.

### Kısa alıştırma
`namespace,pod,deployment,node,team,customer_id,request_id` alanlarını metric enrichment için değerlendir. Hangilerini default allowlist'e alacağını ve nedenlerini yaz.

### Proje fikri
`otel-k8s-enrichment-lab`: küçük Kubernetes cluster'da app -> agent/gateway Collector -> backend hattı kur; pod restart, label change ve RBAC removal senaryolarında metadata doğruluğu/cardinality ölç.

### Failure modes / trade-off / production
Her annotation/label'ı export etmek; unbounded cardinality; stale pod cache; yanlış association; aşırı API-server watch yükü; PII sızıntısı. Production'da series cardinality, telemetry bytes, enrichment miss rate, API watch errors, collector CPU/RSS ve backend ingest cost izlenmelidir.

## Paket 2 — Senior → CTO Backend & System Design: WASI 0.3 Native Async, Component Boundaries & Portable Services
**Süre:** 20–30 dk

### Konu anlatımı
WebAssembly Component Model, core Wasm module'lerinin üzerinde typed interface ve composition katmanı sağlar. WASI 0.3, 11 Haziran 2026'da ratify edildi ve native async'i Component Model Canonical ABI'ye taşıdı. `async func`, `stream<T>` ve `future<T>` artık component boundary'nin standart primitives'idir; önceki `wasi:io` pollable yaklaşımının önemli kısmı ABI seviyesine taşındı.

Sistem tasarımı açısından ana fikir şudur: async yalnız language runtime detayı değil, component contract'ının parçası olduğunda host farklı dillerdeki component'lerin readiness/backpressure ilişkisini koordine edebilir. Bu plugin platformu, edge runtime veya polyglot service composition için güçlüdür; ancak runtime/toolchain maturity, WIT version pinning, debugging ve ecosystem compatibility yeni operasyonel boundary'ler yaratır.

```text
caller component
      |
 async WIT interface
      v
Canonical ABI
 stream<T> / future<T>
      |
      v
host runtime / scheduler
   |              |
component A    component B
(Rust)          (JS/...)

contract portable; execution still host-governed
```

### Yüksek getirili mülakat soruları
- Core Wasm module ile Component Model component farkı nedir?
- WIT neyi tanımlar?
- Native async neden component composition'ı kolaylaştırır?
- `future<T>` ile `stream<T>` mental olarak nasıl ayrılır?
- Backpressure component boundary'de neden önemlidir?
- Senior: WIT/toolchain version mismatch nasıl rollout problemi yaratır?
- Staff: Wasm component ile container/microservice boundary ne zaman seçilir?
- CTO: portability kazanımı runtime maturity ve hiring/operability maliyetini ne zaman haklı çıkarır?

### Beklenen cevap derinliği
Junior/Mid: module/component, interface ve async temel modeli. Senior: ABI, backpressure, cancellation, version pinning ve observability. Staff: polyglot composition, sandbox boundary ve platform architecture. Principal/CTO: portability, ecosystem maturity, vendor risk ve organizational capability.

### Kısa alıştırma
Bir image-processing pipeline'ını `source -> transform -> sink` üç component'e böl. Hangi interface'in stream, hangisinin future olması gerektiğini ve downstream yavaşladığında backpressure davranışını açıkla.

### Proje fikri
`wasi03-async-pipeline`: iki dilde component üret; WIT ile async stream contract tanımla, Wasmtime host'ta compose et, slow-consumer ve cancellation testleri ekle.

### Failure modes / trade-off / production
0.2/0.3 contract mismatch; toolchain/WIT pin drift; unbounded buffering; cancellation propagation eksikliği; runtime-specific behavior; container replacement'i gibi aşırı genelleme. Production'da queue depth, stream throughput, cancellation latency, component instantiation failures, version mismatch ve host CPU/RSS ölçülmelidir.
