## Paket 1 — Mid/Senior Backend & Cybersecurity: Node.js Permission Model, Least Privilege & Sandbox Boundaries
**Süre:** 20–30 dk

### Konu anlatımı
Node.js Permission Model, process'in filesystem ve bazı diğer kaynaklara erişimini allow-list mantığıyla sınırlayan bir runtime guardrail'dir. Güncel Node.js v26 dokümantasyonunda model stable'dır. `--permission` açıldığında izin verilmeyen erişimler varsayılan olarak `ERR_ACCESS_DENIED` ile engellenir; filesystem için read/write izinleri ayrı verilebilir. Yeni audit mode ise erişimi kesmeden ihlalleri diagnostics channel üzerinden gözlemlemeye izin verir; bu, production rollout'ta önce gözlemle sonra enforce et desenini mümkün kılar.

Kritik güvenlik mental modeli: Permission Model bir sandbox değildir. Node.js dokümantasyonu bunu açıkça bir “seat belt” olarak tanımlar ve malicious code'a karşı güvenlik garantisi vermediğini söyler. Uygulamanın çalıştırdığı kod trusted kabul edilir; native addon, child process, alternate API veya tasarım dışı yollar threat model'i değiştirebilir. Dolayısıyla gerçek isolation gerekiyorsa OS/container boundary, seccomp/AppArmor, namespace, VM veya ayrı service hesabı gibi daha güçlü katmanlarla defense-in-depth gerekir.

```text
application code
      |
 Node permission checks
   /             \
allowed          denied/audited
   |                 |
 runtime API      telemetry/error
   |
OS / container / IAM boundary
   |
real resource

permission model = guardrail
OS/IAM boundary   = stronger isolation layer
```

### Yüksek getirili mülakat soruları
- Least privilege nedir?
- Runtime permission modeli ile OS sandbox arasındaki fark nedir?
- Audit mode neden rollout için değerlidir?
- Read ve write permission'larını ayırmak hangi riski azaltır?
- Neden “permission model açık, arbitrary dependency güvenlidir” denemez?
- Senior: mevcut serviste deny-by-default'a nasıl geçersin?
- Staff: container, IAM ve runtime permission katmanlarını nasıl bölersin?
- Principal/CTO: platform standardı olarak enforcement ne zaman zorunlu olmalı?

### Beklenen cevap derinliği
Junior: permission/allow-deny ve least privilege. Mid: filesystem scope ve audit/enforce. Senior: threat model, bypass surface ve rollout. Staff: defense-in-depth, platform policy ve exception governance. Principal/CTO: supply-chain risk, developer velocity ve fleet-wide controls.

### Kısa alıştırma
Bir image-processing worker yalnız `/input` okuyacak, `/output` yazacak ve config'i okuyacak. Minimum runtime izinlerini yaz; sonra malicious native dependency varsayımında neden bunun yeterli isolation olmadığını açıkla.

### Proje fikri
`node-permission-lab`: aynı servisi unrestricted, audit ve enforce modlarında çalıştır. Filesystem read/write ihlalleri üret; diagnostics channel'dan telemetry topla ve container-level read-only filesystem ile karşılaştır.

### Failure modes / trade-off / production
Permission Model'i sandbox sanmak; wildcard izinlerle least privilege'i bozmak; audit telemetry toplamadan enforce etmek; native addon/child-process boundary'sini unutmak; generated reports/temp paths gibi runtime ihtiyaçlarını kaçırmak. Production'da denied/audited operation sayısı, path/category dağılımı, startup failure, dependency değişiklikleri ve exception sayısı izlenmelidir.

## Paket 2 — Senior/Staff Frontend & Leadership: Chrome Two-Week Release Cadence, Compatibility Risk & Progressive Delivery
**Süre:** 20–30 dk

### Konu anlatımı
Chrome 8 Eylül 2026'da Chrome 153 ile stable release cadence'ini dört haftadan iki haftaya indirdi. Browser platformunda daha hızlı release cadence yalnız “feature'lar daha hızlı gelir” anlamına gelmez; frontend/platform ekiplerinin compatibility detection, automated browser matrix, feature rollout, enterprise policy ve rollback varsayımlarını da değiştirir. Bir dependency veya browser davranışı daha sık değişiyorsa değişiklik başına risk aynı kalsa bile yıl içindeki change-event sayısı artar.

Progressive delivery mental modeli burada frontend'e uygulanır: yeni browser özelliğini capability detection ile kullan, mümkünse standards-based fallback tut, telemetry ile gerçek kullanım ve error rate'i gözle, rollout'u cohort/feature flag ile büyüt. User-agent version sniffing kırılgandır; davranış/capability detection çoğu durumda daha dayanıklıdır. Platform ekibi release notes'u insan gözüyle okumaya ek olarak CI browser matrix ve synthetic journeys ile risk sinyali üretmelidir.

```text
browser stable release
        |
 compatibility CI matrix
        |
 capability / regression signal
      /       \
   healthy    broken
      |          |
 progressive   fallback /
 rollout       flag off
      |
 RUM + errors + business KPI
```

### Yüksek getirili mülakat soruları
- Faster browser cadence frontend riskini nasıl değiştirir?
- Feature detection neden version sniffing'den genellikle daha iyidir?
- Polyfill ile progressive enhancement farkı nedir?
- Browser matrix nasıl seçilir; her sürümü test etmek gerekir mi?
- RUM ile synthetic monitoring hangi farklı soruları cevaplar?
- Senior: yeni web API rollout'unu nasıl canary edersin?
- Staff/EM: compatibility incident ownership'i browser/platform/product ekipleri arasında nasıl kurarsın?
- CTO: test maliyeti ile supported-browser revenue coverage arasında nasıl karar verirsin?

### Beklenen cevap derinliği
Junior: browser compatibility ve fallback. Mid: feature detection, test matrix. Senior: RUM, progressive rollout ve rollback. Staff/EM: support policy, ownership ve CI governance. Principal/CTO: revenue coverage, enterprise constraints, platform investment ve risk economics.

### Kısa alıştırma
Trafiğin %72'si Chromium, %18'i Safari, %8'i Firefox, %2'si diğer. Yeni bir web API yalnız güncel Chromium'da hazır. Launch planı, fallback ve abort metric'lerini tasarla.

### Proje fikri
`browser-compat-gate`: Playwright tabanlı küçük browser matrix, capability probes, synthetic checkout journey ve feature-flag rollout gate. Browser/version bazında error ve conversion farkını raporla.

### Failure modes / trade-off / production
Sadece latest Chrome test etmek; UA sniffing'e aşırı güvenmek; fallback'i test etmemek; browser error rate'i business KPI'dan ayırmak; enterprise-managed eski sürümleri yok saymak. Production'da JS error rate, Core Web Vitals, capability coverage, conversion/task success ve browser-version dağılımı birlikte izlenmelidir.
