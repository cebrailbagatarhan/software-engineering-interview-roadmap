## Paket 1 — Mid/Senior Networking & Backend: HTTP 103 Early Hints, Preload & Speculative Latency Reduction
**Süre:** 20–30 dk

### Konu anlatımı
HTTP `103 Early Hints`, origin final response'u üretirken istemciye bazı response header alanlarını daha erken göndermeyi sağlar. RFC 8297'nin temel kullanım örneği `Link: ...; rel=preload`: browser final `200` ve HTML'i beklerken kritik CSS/font/script gibi kaynakları spekülatif olarak fetch etmeye başlayabilir. Ama 103 final response değildir; hint'ler final response'un semantics'ini değiştirmemeli ve istemci bunları yalnız optimization amacıyla değerlendirmelidir.

Kazanç mental modeli critical path overlap'tir. Server think time 300 ms ve kritik CSS fetch'i 150 ms ise, CSS keşfi ancak HTML geldikten sonra başlarsa süreler seri hale gelir. 103 CSS keşfini server think time ile overlap edebilir. Fakat yanlış preload bandwidth'i tüketir, cache/CDN/proxy davranışı karmaşıklaşabilir ve gereksiz speculative work mobil ağlarda pahalı olabilir.

```text
without 103:
request -> [server think 300ms] -> 200/HTML -> [CSS 150ms] -> render

with 103:
request -> 103 preload CSS -> [CSS 150ms]
          [server think 300ms] -> 200/HTML -> render

win ≈ overlapped critical-path work, not “free bandwidth”
```

### Yüksek getirili mülakat soruları
- 1xx informational response nedir?
- 103 ile 200 arasındaki semantic fark nedir?
- `preload`, `prefetch` ve normal discovery nasıl ayrılır?
- Early Hints hangi latency bileşenini azaltır?
- Yanlış preload neden performansı kötüleştirebilir?
- Senior: CDN/proxy/browser zincirinde 103 rollout'unu nasıl doğrularsın?
- Staff: RUM ile gerçek kullanıcı faydasını nasıl ölçersin?
- Principal/CTO: birkaç ms kazanım için operasyonel complexity ne zaman haklıdır?

### Beklenen cevap derinliği
Junior: request/response ve preload. Mid: critical path ve speculative fetch. Senior: CDN/cache, connection reuse, bandwidth contention ve measurement. Staff: rollout, RUM ve compatibility. Principal/CTO: latency-to-business KPI ve complexity economics.

### Kısa alıştırma
Server think time 400 ms, kritik CSS fetch'i 180 ms. CSS normalde HTML geldikten sonra keşfediliyor. İdeal overlap varsayımıyla 103'ün teorik critical-path kazancını hesapla; sonra gerçek kazancı düşürecek üç neden yaz.

### Proje fikri
`early-hints-lab`: aynı sayfayı 103 kapalı/açık servis et. Yapay 300–500 ms server think time ekle; waterfall, LCP, bytes transferred ve unused preload oranını ölç. CDN/proxy üzerinden de aynı testi çalıştır.

### Failure modes / trade-off / production
Her asset'i preload etmek; final response semantics'i 103'e bağlamak; cache/CDN desteğini varsaymak; bandwidth-constrained kullanıcıları göz ardı etmek; lab metric'ini business impact sanmak. Production'da LCP/TTFB, resource start time, unused preload, transfer bytes, browser/CDN breakdown ve task success izlenmelidir.

### Kaynaklar
- https://www.rfc-editor.org/rfc/rfc8297
- https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/103

## Paket 2 — Senior/Staff Frontend & Leadership: Chrome Two-Week Release Cadence, Compatibility Risk & Progressive Delivery
**Süre:** 20–30 dk

### Konu anlatımı
Chrome 8 Eylül 2026'da Chrome 153 ile stable release cadence'ini dört haftadan iki haftaya indirdi. Browser platformunda daha hızlı release cadence yalnız “feature'lar daha hızlı gelir” anlamına gelmez; frontend/platform ekiplerinin compatibility detection, automated browser matrix, feature rollout, enterprise policy ve rollback varsayımlarını da değiştirir. Bir dependency veya browser davranışı daha sık değişiyorsa değişiklik başına risk aynı kalsa bile yıl içindeki change-event sayısı artar.

Progressive delivery mental modeli burada frontend'e uygulanır: yeni browser özelliğini capability detection ile kullan, mümkünse standards-based fallback tut, telemetry ile gerçek kullanım ve error rate'i gözle, rollout'u cohort/feature flag ile büyüt. User-agent version sniffing kırılgandır; davranış/capability detection çoğu durumda daha dayanıklıdır. Platform ekibi release notes'u insan gözüyle okumaya ek olarak CI browser matrix ve synthetic journeys ile risk sinyali üretmelidir.

```text
browser stable release
        |
 compatibility CI matrix
        |
 capability / regression signal
      /       \
   healthy    broken
      |          |
 progressive   fallback /
 rollout       flag off
      |
 RUM + errors + business KPI
```

### Yüksek getirili mülakat soruları
- Faster browser cadence frontend riskini nasıl değiştirir?
- Feature detection neden version sniffing'den genellikle daha iyidir?
- Polyfill ile progressive enhancement farkı nedir?
- Browser matrix nasıl seçilir; her sürümü test etmek gerekir mi?
- RUM ile synthetic monitoring hangi farklı soruları cevaplar?
- Senior: yeni web API rollout'unu nasıl canary edersin?
- Staff/EM: compatibility incident ownership'i browser/platform/product ekipleri arasında nasıl kurarsın?
- CTO: test maliyeti ile supported-browser revenue coverage arasında nasıl karar verirsin?

### Beklenen cevap derinliği
Junior: browser compatibility ve fallback. Mid: feature detection, test matrix. Senior: RUM, progressive rollout ve rollback. Staff/EM: support policy, ownership ve CI governance. Principal/CTO: revenue coverage, enterprise constraints, platform investment ve risk economics.

### Kısa alıştırma
Trafiğin %72'si Chromium, %18'i Safari, %8'i Firefox, %2'si diğer. Yeni bir web API yalnız güncel Chromium'da hazır. Launch planı, fallback ve abort metric'lerini tasarla.

### Proje fikri
`browser-compat-gate`: Playwright tabanlı küçük browser matrix, capability probes, synthetic checkout journey ve feature-flag rollout gate. Browser/version bazında error ve conversion farkını raporla.

### Failure modes / trade-off / production
Sadece latest Chrome test etmek; UA sniffing'e aşırı güvenmek; fallback'i test etmemek; browser error rate'i business KPI'dan ayırmak; enterprise-managed eski sürümleri yok saymak. Production'da JS error rate, Core Web Vitals, capability coverage, conversion/task success ve browser-version dağılımı birlikte izlenmelidir.
