## Paket 1 — Senior/Staff MLOps: PyTorch Distributed Checkpointing, Async Save & Recovery Economics
**Süre:** 20–30 dk

### Konu anlatımı
Büyük distributed training işlerinde checkpoint yalnız serialization değildir; failure recovery ile training throughput arasındaki ekonomik kontrol noktasıdır. PyTorch Distributed Checkpoint (DCP), model ve optimizer state'ini birden fazla rank'ten paralel kaydedip yükleyebilir ve load-time resharding destekler. Böylece checkpoint bir world-size/topology'de yazılıp farklı bir topology'de yüklenebilir.

Synchronous checkpoint'te GPU'lar state'in persistent storage'a yazılmasını bekler. Async checkpointing kritik yolu ikiye ayırır: önce gerekli state GPU'dan CPU'ya staging edilir; ardından training devam ederken CPU thread'leri/storage path arka planda persist eder. Bu yöntem toplam serialization işini yok etmez; GPU-visible downtime'ı azaltır. PyTorch/Meta ve Crusoe'nun 2025 ölçümünde 1,856 H200 GPU'lu bir Llama3-70B koşusunda async DCP background processing süresi yaklaşık 436 saniyeden 67 saniyeye düşürüldü; bu sonuç workload-specific bir benchmark'tır, genel 6x garanti değildir.

```text
training step N
     |
     v
GPU state --stage--> CPU snapshot ----async----> durable storage
     |                    |                          |
     +--> resume train ---+                     commit/complete

failure cost ~= checkpoint interval + restart/load time
checkpoint cost ~= visible pause + background CPU/I/O pressure
```

### Yüksek getirili mülakat soruları
- `torch.save` ile distributed checkpointing kavramsal olarak nasıl ayrılır?
- Load-time resharding neden elasticity için önemlidir?
- Async checkpoint neden toplam I/O maliyetini sıfırlamaz?
- CPU staging memory pressure yaratırsa ne olur?
- Checkpoint completion neden atomic/commit semantiğine ihtiyaç duyar?
- Senior: checkpoint interval'ını failure rate ve save cost ile nasıl seçersin?
- Staff: object storage bandwidth'i training traffic ile çakışıyorsa nasıl izole edersin?
- Principal/CTO: daha sık checkpoint'in GPU utilization, recovery loss ve storage cost etkisini nasıl fiyatlarsın?

### Beklenen cevap derinliği
Junior: model state ve checkpoint amacı. Mid: rank/shard ve save/load. Senior: async staging, consistency, restart ve bandwidth. Staff: topology değişimi, object storage, capacity ve failure domains. Principal/CTO: GPU-hour kaybı, storage maliyeti ve recovery SLO.

### Kısa alıştırma
Her 60 dakikada ortalama failure yaşayan bir training job için 5, 15 ve 30 dakikalık checkpoint interval'larını karşılaştır. Visible checkpoint pause 8 saniye, restart+load 4 dakika kabul ederek beklenen kayıp training süresini kaba olarak hesapla.

### Proje fikri
`dcp-failure-lab`: 4 local process/rank ile sharded state kaydet; synchronous ve async save sürelerini ölç; process kill enjekte et; farklı world-size ile reload/reshard dene. Visible pause, CPU memory, checkpoint bytes ve recovery time ölç.

### Failure modes / trade-off / production
Checkpoint yazıldı sanıp incomplete state'i restore etmek; storage bandwidth saturation; CPU staging OOM; tüm rank'lerin aynı failure domain'inde olması; checkpoint interval'ını yalnız save süresine göre seçmek; restore yolunu test etmemek. Production'da visible checkpoint pause, background completion time, bytes/checkpoint, storage throughput, failed/incomplete checkpoint, restore duration ve lost training steps birlikte izlenmelidir.

## Paket 2 — Mid/Senior Algorithms & Data Structures: Bloom Filters, False Positives & Memory Economics
**Süre:** 20–30 dk

### Konu anlatımı
Bloom filter, bir elemanın bir kümede **kesinlikle olmadığını** veya **muhtemelen olduğunu** söyleyen space-efficient probabilistic veri yapısıdır. Bit array ve birden fazla hash fonksiyonu kullanır. Insert sırasında `k` hash'in gösterdiği bitler 1 yapılır; lookup sırasında bu bitlerden biri 0 ise eleman kesin yoktur. Hepsi 1 ise eleman olabilir: false positive mümkündür, klasik Bloom filter'da false negative beklenmez.

Temel trade-off memory `m`, eklenen eleman sayısı `n` ve hash sayısı `k` arasındadır. Yaklaşık false-positive olasılığı `p ≈ (1 - e^(-kn/m))^k`; sabit `m,n` için optimum `k ≈ (m/n) ln 2`. Mülakatta formülü ezberlemekten daha değerlisi şu invariant'tır: filtre authoritative store değildir; pahalı negative lookup'ları ucuzca elemek için ön kapıdır.

```text
request(key)
    |
    v
 Bloom filter
   /      \
 any 0    all 1
  |         |
definitely  maybe present
 absent     |
  |         v
 skip     DB/cache lookup

false positive = extra lookup
false negative = correctness bug (classic design'da olmamalı)
```

### Yüksek getirili mülakat soruları
- Bloom filter neden false positive üretir?
- Neden klasik Bloom filter false negative üretmemelidir?
- Bit array doldukça ne olur?
- `k` hash sayısını sınırsız artırmak neden iyi değildir?
- Delete neden klasik Bloom filter için zordur?
- Counting Bloom filter neyi değiştirir?
- Senior: cache penetration probleminde Bloom filter'ı nereye koyarsın?
- Staff: distributed shard başına mı global mi filter tutarsın?

### Beklenen cevap derinliği
Junior: bit array/hash ve membership. Mid: false positive/negative, memory trade-off. Senior: sizing, saturation, deletion ve rebuild. Staff: sharding, replication, stale filter ve observability. Principal/CTO: RAM maliyeti ile backend I/O/DB maliyeti karşılaştırması.

### Kısa alıştırma
10 milyon key için key başına 10 bit ayırdığını varsay. Optimum `k` değerini yaklaşık hesapla ve false-positive oranını formülle tahmin et. Sonra 20 milyon key aynı filtreye girerse ne olacağını açıklayarak capacity alarmı öner.

### Proje fikri
`bloom-frontdoor`: küçük Bloom filter implementation + SQLite/HTTP backing store. Var/yok workload'larında filter'sız ve filter'lı DB lookup sayısı, latency ve false-positive rate ölç; filter saturation arttıkça grafiğini çıkar.

### Failure modes / trade-off / production
Filtreyi source of truth sanmak; kapasiteyi aşmak; hash bağımsızlığını kötü varsaymak; delete'i bit sıfırlayarak yapmak; stale rebuild sırasında yeni key'leri kaçırmak; observed false-positive rate'i ölçmemek. Production'da fill ratio, estimated/observed FP rate, avoided backend lookup, rebuild duration, memory bytes ve downstream QPS izlenmelidir.
