## Paket 1 — Senior/Staff Networking & Cybersecurity: TLS 1.3 HelloRetryRequest, Key Exchange Agility & Post-Quantum Migration
**Süre:** 20–30 dk

### Konu anlatımı
TLS 1.3 istemcisi ilk `ClientHello` içinde desteklediği grupları ve genellikle bir veya daha fazla `key_share` gönderir. Sunucu kabul edilebilir bir key share bulamazsa `HelloRetryRequest` (HRR) ile başka bir grup ister; istemci ikinci `ClientHello` gönderir. Güvenlik açısından doğru olan bu mekanizma performans açısından ekstra round trip demektir.

8 Eylül 2026'da Cloudflare, origin bağlantılarında key-exchange seçimini statik tahmin yerine gözlemlenen origin capability'sine göre otomatikleştirdiğini açıkladı. Şirket, eski tek-seçim yaklaşımının ölçtüğü origin bağlantılarının yaklaşık %30'unda suboptimal olduğunu belirtiyor. Güncel bağlam post-quantum migration'ı daha da önemli kılıyor: daha büyük hybrid/PQ key-share'lar packet size, CPU ve compatibility maliyetini değiştirir.

```text
Client                  Server
  | ClientHello + share A |
  |----------------------->|
  |    HelloRetryRequest B |
  |<-----------------------|
  | ClientHello + share B  |
  |----------------------->|
  | ServerHello ...        |
  |<-----------------------|

Doğru ilk tahmin: 1 RTT handshake path
HRR: +1 network round trip
```

Mental model: cryptographic agility yalnız algoritma listesi değildir; capability discovery + policy + latency + fallback problemidir. Bir algoritmayı güvenlik nedeniyle tercih etmek, her peer'in onu aynı anda desteklediği anlamına gelmez.

### Yüksek getirili mülakat soruları
- TLS 1.3'te `supported_groups` ile `key_share` farkı nedir?
- HelloRetryRequest hangi durumda oluşur?
- HRR neden tail latency'yi etkiler?
- Algorithm agility neden hard-coded preference listesinden fazlasıdır?
- Post-quantum/hybrid key exchange packet size ve CPU'yu nasıl etkileyebilir?
- Senior: capability cache stale olursa nasıl güvenli fallback yaparsın?
- Staff: milyonlarca origin için öğrenilmiş preference state'ini nasıl expire/observe edersin?
- CTO: PQ migration'da security deadline ile compatibility riskini nasıl dengelersin?

### Beklenen cevap derinliği
Junior: handshake ve RTT. Mid: key share/HRR/fallback. Senior: latency, cache invalidation ve safe negotiation. Staff: fleet-wide capability learning, observability ve rollout. Principal/CTO: cryptographic migration, compliance, performance budget ve ecosystem readiness.

### Kısa alıştırma
Client→origin RTT 45 ms. HRR oranı %30'dan %2'ye düşerse yalnız network round-trip açısından ortalama handshake gecikmesindeki kaba kazancı hesapla. Sonra p99 için neden ortalamanın yetersiz olduğunu açıkla.

### Proje fikri
`tls-negotiation-simulator`: peer capability set'leri üret; static preference, cached capability ve adaptive policy'yi HRR rate, handshake RTT, cache staleness ve fallback açısından karşılaştır.

### Failure modes / trade-off / production
Stale capability cache; downgrade-benzeri unsafe fallback; yalnız average latency izlemek; PQ payload büyüklüğünü yok saymak; middlebox/legacy peer compatibility'sini test etmemek. Production'da HRR rate, handshake p50/p95/p99, negotiated group, failure/fallback rate, cache age ve CPU izlenmelidir.

## Paket 2 — Senior/Staff Backend & Leadership: Rust Miscompilation, Compiler Trust & Regression-Safe Toolchain Rollout
**Süre:** 20–30 dk

### Konu anlatımı
Compiler correctness production correctness'in parçasıdır. Kaynak kod borrow checker'dan geçmiş, testleri geçmiş ve memory-safe görünüyor olabilir; fakat compiler yanlış machine code üretirse dil seviyesindeki varsayımlar bozulabilir.

Rust ekibi 3 Eylül 2026'da Rust 1.98.1'i yayımladı. Point release, Rust 1.98.0'da belirli koşullarda trait-object vtable generation sırasında function pointer yerine null pointer üretilebilen bir miscompilation'ı düzeltti. Resmi açıklama bunun emitted code'da undefined behavior'a yol açabildiğini belirtiyor.

```text
source code
    |
 type / borrow checks
    |
 compiler IR + optimizations
    |
 code generation ---- bug ----> wrong vtable
    |                           |
 binary                         null fn ptr
    |                           |
 tests / canary ----------> runtime failure / UB
```

Mental model: compiler/toolchain bir supply-chain dependency ve deployment artifact'inin üreticisidir. `latest stable` otomatik olarak `fleet-wide immediately` demek değildir. Reproducible builds, pinned toolchain, canary compilation/deployment, differential tests ve hızlı rollback toolchain riskini yönetir.

### Yüksek getirili mülakat soruları
- Miscompilation ile source-code bug farkı nedir?
- Undefined behavior neden yalnız segfault anlamına gelmez?
- Trait-object vtable ne işe yarar?
- Toolchain neden supply-chain dependency sayılır?
- Lockfile dependency pinlerken compiler'ı pinlememek hangi riski bırakır?
- Senior: compiler upgrade canary'sinde neyi karşılaştırırsın?
- Staff: yüzlerce repo için toolchain rollout policy nasıl tasarlanır?
- CTO/EM: security fix ile regression riskini aynı release kararında nasıl yönetirsin?

### Beklenen cevap derinliği
Junior: compiler ve runtime ayrımı. Mid: vtable, UB ve reproducible build. Senior: pinning, canary, differential test ve rollback. Staff: org-wide toolchain governance ve blast radius. CTO/EM: developer velocity, security, incident cost ve release policy.

### Kısa alıştırma
200 servislik bir organizasyonda yeni Rust toolchain rollout planı yaz: %5 canary → %25 → %100. Her aşama için en az iki promotion gate ve bir rollback trigger tanımla.

### Proje fikri
`toolchain-differential-ci`: aynı test corpus'unu N ve N+1 Rust toolchain ile derle; test sonucu, binary size, benchmark, sanitizer/Miri sonuçları ve artifact hash metadata'sını karşılaştır.

### Failure modes / trade-off / production
Unpinned toolchain; release note okumadan fleet rollout; yalnız unit test'e güvenmek; generated binary davranışını gözlemlememek; rollback artifact'i tutmamak. Production'da crash/segfault, canary error rate, compiler warnings, binary size/perf delta, toolchain version coverage ve rollback time izlenmelidir.
