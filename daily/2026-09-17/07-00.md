## Paket 1 — Mid/Senior Backend & Runtime: Go 1.27 Size-Specialized Allocation, Escape Analysis & GC Economics
**Süre:** 20–30 dk

### Konu anlatımı
Go 1.27 küçük heap allocation'ları için size-specialized allocator yolları ekledi. Go ekibinin 16 Eylül 2026 tarihli teknik yazısına göre 80 byte'tan küçük belirli allocation'lar %20–30 daha hızlı olabilir; allocation-heavy programların toplam hızlanması ise örnek workload'larda yaklaşık %1'e kadar çıkabilir. Buradaki kritik mülakat ayrımı şudur: allocator microbenchmark kazanımı ile application latency/throughput kazanımı aynı şey değildir.

Compiler bir değerin stack'te güvenle yaşayıp yaşayamayacağını escape analysis ile belirler. Heap'e kaçan değerler allocator ve daha sonra GC maliyeti yaratabilir. Dolayısıyla optimizasyon sırası çoğu zaman `allocation'ı daha hızlı yap` değil, önce `gereksiz allocation var mı?`, sonra `kaçınılmaz allocation'ın maliyeti nedir?` olmalıdır.

```text
source object
    |
escape analysis
  /        \
stack     heap
cheap      |
       size-specialized path (<80 B cases)
            |
        heap bytes / objects
            |
           GC

application win = allocation share × allocator improvement - side effects
```

### Yüksek getirili mülakat soruları
- Stack ve heap allocation farkı nedir?
- Escape analysis neyi çözmeye çalışır?
- Daha hızlı allocator neden otomatik %20 application speedup değildir?
- Allocation rate GC CPU ve pause davranışını nasıl etkiler?
- Object pooling ne zaman fayda, ne zaman zarar getirir?
- Senior: benchmark'ta `allocs/op`, `B/op`, ns/op ve p99'u birlikte nasıl yorumlarsın?
- Staff: runtime upgrade performans iddiasını servis filosunda nasıl canary edersin?
- Principal: CPU tasarrufu ile complexity/maintainability arasında nasıl karar verirsin?

### Beklenen cevap derinliği
Junior: stack/heap ve GC. Mid: escape analysis ve benchmark. Senior: allocation profile, GC pressure, cache locality ve tail latency. Staff: representative workload, canary ve fleet economics. Principal/CTO: performance-per-dollar ve upgrade risk budget.

### Kısa alıştırma
Bir endpoint request başına 40.000 küçük allocation yapıyor ve CPU'nun %12'si allocation yolunda harcanıyor. Allocator'ın bu bölümünü %25 hızlandırdığını varsay. Amdahl sezgisiyle toplam CPU kazancının neden yaklaşık %3 mertebesinde olduğunu hesapla; sonra GC etkisinin sonucu neden değiştirebileceğini yaz.

### Proje fikri
`go-small-alloc-lab`: 16/32/64/128-byte object workload'ları üret; Go 1.26 ve 1.27 ile `ns/op`, `allocs/op`, `B/op`, GC CPU ve service p99 ölç. Escape analysis çıktısıyla heap'e kaçan iki kod yolunu refactor et.

### Failure modes / trade-off / production
Microbenchmark'ı production sonucu sanmak; allocation sayısını azaltmadan yalnız allocator'a güvenmek; pooling ile memory retention yaratmak; GC ve p99'u ölçmemek; compiler/runtime upgrade'ını representative traffic olmadan yaymak. Production'da allocation bytes/sec, objects/sec, GC CPU, heap live size, p95/p99 ve CPU/request birlikte izlenmelidir.

## Paket 2 — Senior/Staff Databases & Leadership: PostgreSQL Minor Upgrades, Security Fixes & Regression-Safe Rollout
**Süre:** 20–30 dk

### Konu anlatımı
Database patching yalnız `en yeni sürümü kur` problemi değildir; security exposure ile regression riskini birlikte yönetme problemidir. PostgreSQL sürüm politikasında minor release'ler bug fix, düşük riskli düzeltme, security ve data-corruption düzeltmelerini taşır ve proje current minor release'i kullanmayı önerir. Ancak gerçek operasyon dünyasında patch'in kendisi de regression yaratabilir: Şubat 2026'daki 18.2/17.8/16.12/15.16/14.21 güncellemesindeki regressions nedeniyle 26 Şubat'ta out-of-cycle düzeltme planlandı.

13 Ağustos 2026'da PostgreSQL 18.6 yayımlandı; 18.5 post-wrap regression nedeniyle hiç yayımlanmadı. Aynı release 28 security vulnerability ve 110'dan fazla bug için fix içeriyordu ve bazı kullanıcıların ek configuration/data cleanup/reindex aksiyonu alması gerekiyordu. Mülakatta güçlü cevap patch cadence'i değil; risk classification, staging fidelity, replica-first/canary rollout, rollback sınırı ve data-integrity doğrulamasını birlikte anlatır.

```text
new minor release
      |
 security + bug impact triage
      |
 release-note migration actions
      |
 staging / representative replay
      |
 replica or canary cohort
      |
 metrics + integrity checks
   /                 \
healthy             regression
  |                     |
expand             stop / rollback*

* rollback binary-safe mi? data/catalog değişti mi? önce doğrula
```

### Yüksek getirili mülakat soruları
- Major ve minor PostgreSQL upgrade riskleri nasıl ayrılır?
- Neden `minor = risksiz` denemez?
- Security patch'i bekletmenin opportunity cost'u nedir?
- Replica-first rollout hangi riskleri azaltır, hangilerini azaltmaz?
- Reindex/data cleanup gerektiren release note neden runbook'a girmelidir?
- Senior: rollback'in güvenli olduğunu nasıl kanıtlarsın?
- Staff/EM: CVSS, exploitability, workload exposure ve regression probability ile patch SLA nasıl belirlersin?
- CTO: database patch governance'ını compliance ve availability hedefleriyle nasıl bağlarsın?

### Beklenen cevap derinliği
Junior: version/backup/restore. Mid: staging ve release notes. Senior: replica/canary, query regression, integrity ve rollback. Staff/EM: risk-based SLA, fleet waves, exception process. Principal/CTO: security exposure, downtime economics, compliance ve platform ownership.

### Kısa alıştırma
500 PostgreSQL instance'lık filoyu P0/P1/P2 workload olarak sınıflandır. Critical security fix için 24 saatlik hedef var. İlk 6 saatte hangi cohort'ları patch edeceğini, hangi abort metric'lerini kullanacağını ve rollback yerine failover gerektirecek durumu yaz.

### Proje fikri
`pg-patch-gate`: release-note checklist, compatibility tests, representative query replay, replica health ve post-upgrade integrity checks üreten küçük bir rollout gate. Cohort bazlı promote/abort kararı üret.

### Failure modes / trade-off / production
Release note okumadan patch; yalnız smoke test; backup var diye restore süresini ölçmemek; extension compatibility'yi unutmak; query-plan regression'ını kaçırmak; security severity'yi workload exposure'dan bağımsız değerlendirmek. Production'da connection errors, replica lag, query p95/p99, crash/restart, corruption/integrity checks, extension health ve rollback/failover time izlenmelidir.
