## Paket 1 — Mid/Senior Backend: Python 3.14 Free-Threading, GIL & Concurrency Economics
**Süre:** 20–30 dk

### Konu anlatımı
Python 3.14 serisinde free-threaded CPython artık deneysel değil, resmi olarak desteklenen opsiyonel bir build modudur (PEP 779). Klasik CPython'da GIL aynı process içindeki Python bytecode execution'ını büyük ölçüde tek thread'e sınırlar; I/O sırasında GIL bırakılabildiği için thread'ler yine I/O-bound işlerde faydalıdır. Free-threaded build ise GIL olmadan birden fazla thread'in Python kodunu aynı anda çalıştırabilmesini hedefler.

Bu, `threading = otomatik hızlanma` demek değildir. Shared mutable state artık daha gerçek paralel yarışlara açıktır; lock contention, allocator/cache davranışı ve C extension uyumluluğu önem kazanır. Python 3.14 C-extension dokümantasyonuna göre extension free-threading desteğini açıkça bildirmezse import sırasında uyarı verilebilir ve GIL runtime'da yeniden etkinleştirilebilir. Dolayısıyla migration'ın bir parçası dependency/wheel envanteridir.

```text
classic CPython:
T1 ---- Python ----|I/O|------ Python
T2 ........wait....|run|...... wait
             one GIL

free-threaded:
T1 ---- Python -------- Python ----
T2 ---- Python -- lock? -- Python -
       real parallel execution

speedup <= useful parallel work / contention / cores
```

### Yüksek getirili mülakat soruları
- GIL nedir; neyi kilitler, neyi kilitlemez?
- Thread'ler klasik CPython'da I/O-bound workload'a neden yine yardımcı olabilir?
- Free-threading CPU-bound workload'u neden hızlandırabilir?
- Neden 8 core otomatik 8x speedup değildir?
- Race condition ile GIL arasındaki yanlış mental model nedir?
- C extension free-threading desteği bildirmezse ne olabilir?
- Senior: multiprocessing, async I/O ve free-threading arasında nasıl seçim yaparsın?
- Staff: büyük Python servis filosunda migration/canary planını nasıl kurarsın?

### Beklenen cevap derinliği
Junior: process/thread ve GIL sezgisi. Mid: CPU-bound vs I/O-bound, async/thread/process. Senior: race, lock contention, extension compatibility ve benchmark. Staff: fleet rollout, dependency inventory, observability ve rollback. Principal/CTO: compute cost, latency, ecosystem maturity ve platform standardization.

### Kısa alıştırma
CPU-bound bir işin %80'i paralelleşebilir varsay. 8 thread ile Amdahl sezgisi kullanarak teorik speedup üst sınırını hesapla: `1 / (0.2 + 0.8/8)`. Sonra lock contention ve extension fallback'in neden gerçek sonucu düşüreceğini açıkla.

### Proje fikri
`py-free-thread-bench`: aynı CPU-bound workload'u classic CPython, free-threaded CPython ve multiprocessing ile çalıştır. 1/2/4/8 worker için throughput, p95 latency, CPU utilization, RSS ve lock contention proxy'lerini kaydet; bir C-extension dependency'sini compatibility matrise ekle.

### Failure modes / trade-off / production
GIL'in tüm race condition'ları önlediğini sanmak; benchmark'ı I/O ile karıştırmak; extension compatibility'yi test etmemek; thread sayısını core sayısından bağımsız büyütmek; yalnız throughput ölçüp tail latency/RSS'i kaçırmak. Production'da throughput/core, p95/p99, CPU, RSS, context switching, lock wait ve extension fallback/uyumluluk birlikte izlenmelidir.

## Paket 2 — Senior/Staff SRE & Performance Engineering: OpenTelemetry Profiles, eBPF & Cross-Signal Correlation
**Süre:** 20–30 dk

### Konu anlatımı
Metrics `ne kadar?`, traces `hangi request yolu?`, logs `hangi olay?` sorularını güçlü biçimde cevaplar; fakat CPU'nun hangi stack'te yandığı veya thread'in nerede off-CPU beklediği için profiling gerekir. OpenTelemetry Profiles signal 26 Mart 2026'da public Alpha'ya geçti. Amaç continuous production profiling'i traces, metrics ve logs ile aynı telemetry ekosisteminde standardize etmektir.

Profiling stack'in zor kısımları yalnız sampling değildir: stack collection, symbolization, process/thread context, cardinality, storage cost ve correlation gerekir. OpenTelemetry duyurusu eBPF profiling agent ve Collector 0.148.0+ desteğini test etmeye çağırıyor; aynı zamanda signal Alpha olduğu için kritik production workload'larda henüz stabil kontrat varsayılmaması gerektiğini açıkça belirtiyor. Cross-signal hedefi, örneğin `p99 trace'ler sırasında hangi off-CPU stack'ler arttı?` sorusunu cevaplayabilmektir.

```text
processes
   |
 eBPF / runtime profiler
   |
 stack samples + context
   v
OTel Profiles ---> symbolization ---> profile store
      |                                  |
      +--- trace/span/resource IDs ------+
                         |
             latency -> code path
```

### Yüksek getirili mülakat soruları
- Metrics/traces varken profiling neden gerekir?
- Sampling profiler instrumentation profiler'dan nasıl ayrılır?
- On-CPU ve off-CPU profile ne anlatır?
- eBPF neden production profiling için çekicidir?
- Symbolization neden ayrı bir sistem problemidir?
- Alpha telemetry signal'ını production'a almakta risk nedir?
- Senior: profile cardinality/storage maliyetini nasıl kontrol edersin?
- Staff: trace-to-profile correlation ile incident workflow'u nasıl tasarlarsın?

### Beklenen cevap derinliği
Junior: CPU profile ve stack trace. Mid: sampling, overhead, flame graph mental modeli. Senior: eBPF, off-CPU, symbolization, cardinality. Staff: cross-signal correlation, collector pipeline, retention ve incident workflow. Principal/CTO: observability cost, vendor portability, standards maturity ve developer productivity.

### Kısa alıştırma
Bir servis p99 latency regression gösteriyor ama CPU ortalaması değişmiyor. Üç hipotez kur: lock/off-CPU wait, belirli endpoint'te CPU hotspot, downstream wait. Her hipotez için trace/profile/metric'ten hangi kanıtı arayacağını yaz.

### Proje fikri
`otel-profile-lab`: CPU hotspot ve lock wait enjekte edilen küçük servis kur. Trace, metric ve profile üret; profile örneklerini endpoint/span context ile korele edip `latency -> span -> stack` drill-down prototipi oluştur.

### Failure modes / trade-off / production
Alpha signal'ı stable sanmak; symbol kaybı; aşırı sampling overhead; yüksek-cardinality label; profile'ı trace context'ten kopuk tutmak; yalnız on-CPU bakıp lock/I/O wait'i kaçırmak. Production'da profiler overhead, sample loss, symbolization success, ingest bytes, storage/cardinality, correlated-profile ratio ve query latency izlenmelidir.
