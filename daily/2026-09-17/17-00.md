## Paket 1 — Mid → Staff Cybersecurity & Backend: CodeQL Data Flow, Taint Tracking & Query Precision
**Süre:** 20–30 dk

### Konu anlatımı
Static analysis'in yüksek getirili mental modeli `source → propagation → sink → sanitizer/barrier` zinciridir. Source saldırganın kontrol edebildiği veriyi, sink tehlikeli operasyonu, propagation verinin program boyunca nasıl aktığını, sanitizer ise belirli bir threat model altında akışı güvenli hale getiren dönüşümü temsil eder. Interprocedural analysis fonksiyon sınırlarını; framework modeling ise runtime'da anlamlı olan controller, ORM veya template davranışını modele taşır.

CodeQL bu modeli kodu sorgulanabilir bir veritabanına çevirerek uygular. 3 Eylül 2026 tarihli CodeQL 2.26.4, Spring R2DBC `DatabaseClient` ve R2DBC SPI için SQL-injection sink modelleri ekledi; Rust data-flow alert location'larını source/sink node'larına daha hassas bağladı. 9 Eylül'deki 2.27.0 ise Linux ARM64 desteği ve ek framework/query iyileştirmeleri getirdi. Ders: analyzer doğruluğu yalnız query mantığı değil, language/framework model coverage problemidir.

```text
untrusted request
      |
    SOURCE
      |
 propagation / calls / fields
      |
  [sanitizer?] ---- yes ---> safe path
      |
      no
      v
     SINK
 SQL / command / template / path
      |
 alert + path explanation
```

### Yüksek getirili mülakat soruları
- Static analysis ile dynamic analysis farkı nedir?
- Source, sink, sanitizer ve taint propagation nedir?
- False positive ve false negative neden oluşur?
- SQL parameterization neden string escaping'den daha güçlü bir boundary'dir?
- Senior: framework model eksikliği hangi tür false negative üretir?
- Staff: custom query pack'leri nasıl versionlar ve rollout edersin?
- Security lead: alert volume değil risk reduction nasıl ölçülür?

### Beklenen cevap derinliği
Junior/Mid: source-sink ve injection. Senior: interprocedural flow, sanitizer semantics, precision/recall. Staff: custom modeling, query lifecycle, baseline ve CI governance. Leadership: remediation SLA, developer friction ve coverage economics.

### Kısa alıştırma
Bir HTTP handler → service → repository zinciri çiz. User input'un raw SQL'e aktığı yolu işaretle; parameterized query eklenince hangi edge'in güvenli boundary olduğunu açıkla.

### Proje fikri
`mini-taint-lab`: küçük bir web uygulamasında üç source, üç sink ve iki sanitizer tanımla; intentionally vulnerable örnekler için CodeQL/custom static-analysis test corpus'u ve regression CI kur.

### Failure modes / trade-off / production
Her string'i tainted saymak; sanitizer'ı context-independent kabul etmek; framework-generated flow'u modellememek; yeni analyzer sürümünde alert churn'ü gerçek regression sanmak; yalnız alert count ölçmek. Production programında exploitable path, severity, fix latency, recurring pattern, query coverage ve suppression age izlenir.

## Paket 2 — Senior → CTO ML/AI/LLM & System Design: Long-Running Agent Harnesses, Tool Boundaries & Durable Execution
**Süre:** 20–30 dk

### Konu anlatımı
Uzun süren agent işi tek bir model çağrısı değildir. Production agent sistemi; model reasoning'i, context yönetimi, tool execution, çalışma ortamı, ara durum, retry/timeout, subagent koordinasyonu ve gözlemlenebilirliği bir harness içinde birleştirir. Temel ayrım control plane ile execution plane arasındadır: control plane işi planlar ve state transition'ları yönetir; execution plane dosya, kod, browser veya harici API gibi yan etkili araçları çalıştırır.

OpenAI 10 Eylül 2026'da Agents API'yi public beta olarak duyurdu ve uzun süre çalışan agent'lar için context/tool/subagent koordinasyonu ile günlerce sürebilen işler için managed environments ve intermediate-result persistence ihtiyacını vurguladı. Mülakatta ürün isminden daha önemli soru şudur: bir agent 9 saat sonra crash ederse güvenli biçimde nereden devam eder? Bunun cevabı durable checkpoints, idempotent tool calls, explicit side-effect ledger ve resumable state machine'dir.

```text
request
  |
agent control plane
  |--- context/state store
  |--- planner/model
  |--- subagent coordinator
  |
  +--> tool gateway --> files / code / APIs
           |
      side effects
           |
 checkpoint + result ledger
           |
 retry / resume / compensate
```

### Yüksek getirili mülakat soruları
- Agent harness ile model arasındaki sorumluluk sınırı nedir?
- Tool call neden sıradan function call değildir?
- Retry sırasında duplicate side effect nasıl önlenir?
- Checkpoint'e hangi state yazılmalıdır?
- Senior: timeout, cancellation ve partial result nasıl modellenir?
- Staff: subagent fan-out'ta budget/backpressure nasıl uygulanır?
- CTO: managed agent platformu build-vs-buy kararında hangi riskleri değiştirir?

### Beklenen cevap derinliği
Junior/Mid: model, tool ve state ayrımı. Senior: idempotency, checkpoint, timeout, observability. Staff: orchestration, concurrency budgets, isolation ve recovery semantics. Principal/CTO: platform boundary, cost, security, auditability ve vendor portability.

### Kısa alıştırma
`research → code change → test → deploy request` agent akışı için state machine çiz. Deploy tool'u timeout verdikten sonra retry öncesi hangi kaydı kontrol edeceğini belirt.

### Proje fikri
`durable-agent-runner`: SQLite/Postgres state store kullanan küçük bir orchestrator yaz; idempotency key, checkpoint, tool-result ledger, cancellation ve crash-after-side-effect fault injection ekle.

### Failure modes / trade-off / production
Prompt'u durable state sanmak; side effect sonrası checkpoint'i geciktirmek; sınırsız subagent fan-out; tool permission'larını model kararına bırakmak; retry storm; stale context; human approval gerektiren adımı otomatik geçmek. Production'da task completion, resume success, duplicate-side-effect count, tool error rate, token/compute budget, wall-clock latency ve approval bypass denemeleri izlenir.
