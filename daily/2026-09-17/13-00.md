## Paket 1 — Senior/Staff Backend & SRE: Python 3.14 GC Rollback, Runtime Upgrades & Production Memory Regressions
**Süre:** 20–30 dk

### Konu anlatımı
Runtime upgrade yalnız yeni feature almak değildir; garbage collector gibi runtime policy değişiklikleri uygulama kodu değişmeden latency, RSS ve throughput profilini değiştirebilir. Python 3.14.0–3.14.4 ile gelen incremental garbage collector, production ortamlarından gelen ciddi memory-pressure raporları nedeniyle Python 3.14.5'te 3.13'teki generational GC yaklaşımına geri döndürüldü. Güncel 3.14.7 maintenance release'i 5 Ağustos 2026'da yayımlandı.

Bu olay önemli bir production mental modeli verir: runtime internals uygulamanın görünmez dependency'sidir. Upgrade testinde yalnız correctness testleri değil, allocation rate, live-set, RSS, collection pause ve workload-specific tail latency de karşılaştırılmalıdır. Canary yalnız binary'nin çalışıp çalışmadığını değil, resource envelope'un değişip değişmediğini doğrulamalıdır.

```text
application workload
       |
 allocations / object graph
       |
 runtime GC policy
   |            |
 reclaim      pauses
   |            |
 RSS/CPU <--> latency
       |
 container limit / OOM
```

### Yüksek getirili mülakat soruları
- Garbage collection ile memory leak aynı şey midir?
- RSS neden live Python object size'dan büyük olabilir?
- GC policy değişikliği throughput ve latency'yi nasıl farklı etkiler?
- Unit test neden memory regression yakalamaya yetmez?
- Senior: runtime upgrade canary'sinde hangi metrikleri karşılaştırırsın?
- Staff: yüzlerce servis için runtime rollout policy nasıl tasarlanır?
- CTO/EM: yeni runtime feature'ı ile fleet stability arasındaki karar nasıl verilir?

### Beklenen cevap derinliği
Junior: allocation, reachable object ve GC. Mid: generations, pause ve RSS. Senior: workload benchmark, container limit, canary ve rollback. Staff: fleet telemetry, rollout waves ve compatibility matrix. CTO/EM: upgrade velocity, security/support lifecycle ve incident economics.

### Kısa alıştırma
Aynı servis için eski/yeni runtime altında p50/p99 latency, RSS p95, CPU ve request throughput ölçen bir promotion gate tasarla. Hangi iki metrikte regression rollout'u durdurmalı?

### Proje fikri
`runtime-upgrade-canary`: allocation-heavy ve object-churn workload üret; iki Python runtime'ını container memory limit altında karşılaştır; RSS, GC ve latency raporu çıkar.

### Failure modes / trade-off / production
Microbenchmark'ı production workload sanmak; yalnız average RSS izlemek; memory limit altında test etmemek; canary süresini GC cycle'larını görmeyecek kadar kısa tutmak; rollback artifact'i saklamamak. Production'da RSS/working set, OOM kill, GC collections/pause, allocation rate, CPU ve p95/p99 latency izlenmelidir.

## Paket 2 — Senior/Staff Databases & Leadership: Redis Rolling Upgrades, Mixed-Version Protocol Boundaries & Availability
**Süre:** 20–30 dk

### Konu anlatımı
Rolling upgrade'in temel vaadi bütün cluster'ı aynı anda durdurmadan version değiştirmektir; fakat bu, mixed-version durumunun semantik olarak güvenli olduğu anlamına gelmez. Redis Software'ın Eylül 2026 release notes'u, Redis Search tarafında 8.4 version boundary'sini geçen mixed-version cluster'larda belirli `parallel_shards_upgrade` konfigürasyonunda query failure oluşabileceğini ve tüm node'lar upgrade edilene kadar Search downtime görülebileceğini açıkça belgeliyor.

Bu vaka genel bir distributed-systems dersidir: rolling upgrade aslında geçici bir heterogeneous protocol deployment'tır. Wire/internal protocol, persisted format, module API, command semantics ve feature negotiation backward/forward compatibility gerektirir. Upgrade runbook'u yalnız `node N'i değiştir` sırası değil, allowed-version skew ve capability matrix içermelidir.

```text
vOld shard ---- internal protocol ---- vNew shard
     |                                  |
 old capability                     new capability
     +---------- mixed fleet -----------+
                    |
          compatibility invariant
                    |
             query availability
```

### Yüksek getirili mülakat soruları
- Rolling upgrade ile zero-downtime upgrade aynı şey midir?
- Version skew neden distributed protocol problemidir?
- Backward ve forward compatibility farkı nedir?
- Feature flag mixed-version güvenliğini nasıl etkiler?
- Senior: upgrade sırasında query failure görürsen rollback mi roll-forward mı seçersin?
- Staff: compatibility matrix ve preflight checker nasıl tasarlanır?
- CTO/EM: STS/LTS seçimi operasyon maliyeti ve feature velocity'yi nasıl etkiler?

### Beklenen cevap derinliği
Junior: rolling vs stop-the-world upgrade. Mid: version skew ve compatibility. Senior: canary shard, drain, rollback/roll-forward ve observability. Staff: protocol invariants, fleet policy ve automated preflight. CTO/EM: support window, change budget, business availability ve upgrade economics.

### Kısa alıştırma
6 shard'lı cluster için 8.2 → 8.6 rollout state machine çiz. Her transition için health gate, abort condition ve rollback feasibility yaz.

### Proje fikri
`mixed-version-upgrade-lab`: iki protocol version'ı simüle eden shard'lar oluştur; compatibility matrix, canary rollout ve incompatible feature activation testleri ekle.

### Failure modes / trade-off / production
`rolling = kesintisiz` varsayımı; mixed-version query test etmemek; unsupported module/feature'i preflight'ta bulmamak; rollback format compatibility'sini doğrulamamak. Production'da version distribution, query error rate, shard health, replication/sync state, latency ve upgrade-stage duration izlenmelidir.
